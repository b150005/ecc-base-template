# Spec ファイル名規約の明文化 (`NN-slug.md`)

## ステータス

Approved

**オーナー:** product-manager / implementer
**対象リリース:** template v3.10.0

## 問題

ADR-014 の Spec 予約ルールは、Roadmap のすべての行が行作成時にパス `specs/NN-slug.md` を使った決定論的な `spec:` リンクを持つことを定めている。実際には、現時点までに作成された 8 つの Spec ファイル (`specs/01-*.md` から `specs/08-*.md`) はいずれもこのパターンに従っている ── 2 桁ゼロ埋めの行番号、kebab-case のスラッグ、`.md` 拡張子、そして二言語対応のための `.ja.md` 兄弟ファイル。したがって予約ルールはファイル名規約を **暗に含んでいる** が、その規約は名前のある明示的なルールとして宣言されたことがない。

ギャップ: `NN-slug.md` の標準形を強制要件として宣言したドキュメントが存在しない。このテンプレートをフォークした派生リポジトリは、継承または強制すべき固定されたルールを持たない。Roadmap 行 #09〜#100+ に取り組む将来のマイルストーン作成者は、ゼロ埋め、スラッグ形式、または `.ja.md` 兄弟ルールについて不確かなときに参照できる規範的なソースを持たない。ADR-016 が導入した `specs/NN-progress.md` 状態ファイルも同じ `NN` プレフィックスを使うが、異なるライフサイクル目的のために存在する ── その規約との関係も未記述のままである。

結果として、先例によって今は機能しているが、新しい貢献者には見えず CI でも強制できない暗黙の規約が存在する。マイルストーン #09 はこの規約を明示的・宣言的・規範的なものにする。既存のファイルの名前変更は行わない。

## ゴール

- Spec ファイルの標準ファイル名形式 (`specs/NN-slug.md`、最小 2 桁ゼロ埋め行番号、kebab-case スラッグ、`.md` 拡張子) を、Spec 作成ステップでエージェントと人間の貢献者が出会える規範的な場所に明示的・名前付きの規約として宣言する。
- 日本語兄弟ファイル (`specs/NN-slug.ja.md`) と EN 原文との必須見出しツリーパリティをカバーするよう規約を拡張し、二言語対応 CI (マイルストーン #06) がファイル存在と見出し構造のレベルですでに強制していることを形式化する。
- ADR-016 状態ファイル (`specs/NN-progress.md`) の規約との関係を明記する: 同じ `NN` プレフィックスを共有するが、`NN-slug.md` 命名要件から除外される ── 進捗ファイルのライフサイクル (セッション境界で作成、◐→☑ フリップで削除) は ADR-016 によって完全に管理されており、この規約によるものではないため。
- ゼロ埋め 2 桁が Roadmap 行 01〜99 をカバーすることを確認し、行 100+ の拡張ルールを明記する。
- 宣言された規約が Spec 作成ステップがすでに必要とするファイル以外のファイルを読まずに出会えるよう、どこに存在するかを特定する (正確な配置は architect に委ねる; リスク R-01 参照)。

## ゴール対象外

- 既存 Spec ファイルの名前変更。作成済みの 8 つの Spec ファイル (`specs/01-*.md` から `specs/08-*.md`) はすでに適合している; 一括名前変更作業は不要であり、スコープ外である。
- Spec ファイルが置かれるディレクトリの変更。ディレクトリ場所はマイルストーン #10 ("Spec/ADR directory location pin in CLAUDE.md") の対象 ── 明確に隣接する別のマイルストーン。#09 は **ファイル名** 規約のみ; #10 は **ディレクトリ** 規約のみ。2 つは MECE である。
- ファイル名適合性を機械的にチェックする新しい CI ディテクターの追加。そのような CI チェックを追加するかどうかは architect に委ねた構造的決定である (リスク R-01 参照)。#09 はドキュメント/規約宣言マイルストーンであり; CI 強制はオプションの帰結であってこのマイルストーンの成果物ではない。
- Spec 予約ルールの変更。ADR-014 の予約ルール (Roadmap 行が行作成時に `spec:` パスを持つ) は正しく変更されない。#09 はその予約パスのファイル名部分を規範的にする ── 予約ルール自体を変更するものではない。
- 見出しツリーパリティルールの変更。EN と JA ファイル間のパリティはすでに二言語対応 CI (マイルストーン #06、ADR-018) によって強制されている。#09 はそのルールをすでに有効なものとして参照する; 再定義または拡張はしない。
- ADR ファイルの命名規約の指定。ADR ファイルは `.claude/meta/adr/` 配下で 3 桁ゼロ埋めプレフィックス (`001-`) を使う; その規約は ADR 作成慣行によって完全に管理されており、Spec ファイルとナンバリング名前空間を共有しない。

## 受け入れ基準

- **Given** Roadmap 行 `NN` に対して新しい Spec が作成される **when** `product-manager` がファイルに名前を付ける **then** 標準形式は `specs/NN-slug.md` であり、ここで `NN` は最小 2 桁にゼロ埋めした行番号 (01、02、…、09、10、…、99) であり、`slug` は Roadmap 行の予約された `spec:` パスで使われたスラッグに一致するマイルストーン名の kebab-case 要約である。
- **Given** Roadmap 行番号が 3 桁に達する (100+) **when** 新しい Spec に名前を付ける **then** 追加パディングなしに番号を記述する (100、101、…) ── 最小 2 桁ルールは 1 桁の行 (1→01) にのみ適用され、すでに複数桁の行には適用されない。
- **Given** JA パリティが必要な二言語プロジェクト **when** EN Spec が作成される **then** JA 兄弟は `specs/NN-slug.ja.md` という名前にする ── 同じ `NN` とスラッグに `.md` の前に `.ja` を挿入 ── そして JA ファイルの見出しツリーは二言語対応 CI (マイルストーン #06、ADR-018) が強制するように EN ファイルとレベル・位置のパリティを持つ。
- **Given** ADR-016 クロスセッション永続化メカニズムによって作成された `specs/NN-progress.md` 状態ファイル **when** `NN-slug.md` 規約に適合するかどうかを評価する **then** 明示的に除外される: 進捗ファイルは規約によって `NN-progress.md` という名前にする (ここで `NN` は in-progress Roadmap 行に一致する) そしてそのライフサイクルは ADR-016 によって完全に管理される; 進捗ファイルは Spec ファイルではなく、`progress` 以外の kebab-case スラッグサフィックスを必要としない。
- **Given** 宣言された規約 **when** architect の決定によって決定された場所に文書化される **then** Spec 作成ステップを実行するエージェントはそのステップがすでに必要とするファイル以外のファイルを読まずに規約に出会う (正確な場所は architect に委ねる; リスク R-01 参照)。 <!-- ref-allow: forthcoming architect decision for #09; authored when #09 moves to implementation -->
- **Given** 8 つの既存 Spec ファイル (`specs/01-*.md` から `specs/08-*.md`) **when** 宣言された規約を遡及的に適用する **then** 8 つすべてが適合している ── これが一括名前変更マイルストーンではなく規約宣言マイルストーンであることを確認する。
- **Given** 本 Spec に述べられた MECE 境界 **when** 将来のマイルストーン作成者が新しい懸念が #09、#04、#05、または #10 に属するかを評価する **then** 境界は明確である: #04 はコミット時に散文のパス参照を検証する; #05 はコミット時に Roadmap グリフ値と双方向 ADR リンクコントラクトを検証する; #09 は Spec ファイルの **ファイル名** 規約についてである; #10 は Spec と ADR ファイルが存在する **ディレクトリの場所** についてである。

## 主なインタラクション

1. **ADR-014 Spec 予約ルールとのインタラクション。** ADR-014 はすべての Roadmap 行が行作成時にパス `specs/NN-slug.md` を使った決定論的な `spec:` リンクを持つことを要求する。マイルストーン #09 はその予約パスのファイル名コンポーネントを、明示的な規約として宣言することで規範的にする。予約ルールは変更されない; #09 は予約パスのファイル名がすでに満たしている名前付きルールを追加する。
2. **マイルストーン #10 (Spec/ADR ディレクトリ場所ピン) とのインタラクション。** #10 は Spec と ADR ファイルが置かれるディレクトリ (`specs/`、`.claude/meta/adr/`) をピンする。#09 は `specs/` ディレクトリ内のファイル名形式をピンする。2 つのマイルストーンは MECE である: #09 はファイル名を管理し; #10 はディレクトリを管理する。どちらも他方を包含しない。ディレクトリ場所について不確かな将来の作成者は #10 を読む; ファイル名形式について不確かな将来の作成者は #09 を読む。
3. **マイルストーン #04 (ダングリング参照ディテクター) とのインタラクション。** #04 ディテクターはコミット時にドキュメントの散文のパス参照が既存のファイルに解決することを検証する。architect の #09 決定が CI ファイル名形式チェックを導入する場合、それはトリガーとスコープの両方で #04 とは別のチェックである: #04 は参照パスが存在するかどうかを確認し; #09 CI チェックは既存のファイル名が形式に適合するかどうかを確認する。2 つは重複しない。
4. **マイルストーン #05 (Roadmap drift-detection CI) とのインタラクション。** #05 ディテクターはコミット時に Roadmap グリフの整形性と双方向 ADR リンクコントラクトを検証する。architect の #09 決定が CI ファイル名形式チェックを導入する場合、それはスコープで #05 とは別である: #05 は Roadmap テーブルの構造的整合性を検証し; #09 CI チェックは `specs/` ディレクトリの内容を検証する。2 つは重複しない。
5. **マイルストーン #06 (二言語対応パリティディテクター、ADR-018) とのインタラクション。** #06 CI はすでに EN と JA Spec ファイル間の見出しレベルと見出し位置のパリティを強制する。本 Spec の受け入れ基準に述べた JA 兄弟命名ルール (`NN-slug.ja.md`) は補完的である: #06 はファイルコンテンツの構造的パリティを強制し; #09 の規約は兄弟のファイル名形式を強制する。適合した二言語 Spec には両方が成立しなければならない。
6. **ADR-016 (クロスセッション進捗永続化) とのインタラクション。** ADR-016 は `specs/NN-progress.md` を ◐ in-progress マイルストーンの状態キャリアとして定義する。これらのファイルは Spec ファイルと `specs/` ディレクトリを共有し、同じ `NN` プレフィックスを使う。本 Spec はそれらを `NN-slug.md` 規約から明示的に除外し、`progress` が ADR-016 のライフサイクルの下での予約済みスラッグサフィックスであり、汎用の kebab-case スラッグではないことを確認する。
7. **構造的な HOW は architect に委ねる。** 規約が CLAUDE.md (Roadmap Rules ブロック、新しい「Spec ファイル名規約」箇条書き、または `product-manager` エージェントプロンプト) に、spec-template の `## このテンプレートの使い方` ブロックに、またはその組み合わせとして述べられるかどうか; CI ファイル名形式チェックが必要かどうか (新しいディテクター + 新しい MECE 境界 => 新しい ADR-019、または ADR-014 の予約ルール決定の帰結明確化 => ADR-014 amendment ── architect は ADR-018 Alternative-B の判別子を適用する); および正確な MECE 境界ドキュメント ── すべて architect の forthcoming decision に委ねる。 <!-- ref-allow: forthcoming architect decision for #09; authored when #09 moves to implementation -->

## メトリクス

- **先行指標:** 本マイルストーン出荷後、`product-manager` が作成するすべての新しい Spec が過去の Spec ファイル名から形式ヒントを参照せずに `NN-slug.md` 形式を使う ── セッショントランスクリプトで検証可能。
- **先行指標:** Roadmap 行 #09 以降の `specs/` でのゼロのファイル名形式逸脱、git 履歴で観察可能。
- **遅行指標:** 規約が継承された規範的な場所に明示的に述べられることで、派生リポジトリでの「この Spec に何という名前を付けるべきか?」という質問の削減。

### リスク R-02: #10 (ディレクトリ場所) へのスコープクリープ

**説明。** マイルストーン #10 は Spec と ADR ファイルが置かれるディレクトリをピンする。将来の作成者またはレビュアーが「ファイルがどこに置かれるか」(#10) と「ファイルがどのように名前付けられるか」(#09) を混同する可能性がある。隣接性は実在する: 完全な標準パスは `specs/NN-slug.md` であり、ディレクトリ (#10 のスコープ) とファイル名 (#09 のスコープ) を組み合わせる。

**緩和策。** MECE 境界は本 Spec の非ゴール、ゴール、主なインタラクションセクションに述べられている。受け入れ基準はファイル名コンポーネントに厳密にスコープされている。architect の決定は規約の配置ドキュメントで境界を繰り返すべきである。将来の作成者が #09 にディレクトリルールを追加することを提案した場合、正しい応答は #10 にルーティングすることである。

### リスク R-03: "スラッグ" 定義の曖昧さ

**説明。** "kebab-case スラッグ" は一般に理解される用語だが、ここで形式的に定義されていない。将来の作成者が `09-spec-filename-convention-alignment-nn-slug-md.md` (過度に長い) や `09-sfca.md` (不透明な略語) や `09-Spec_Filename.md` (間違いのケーシング) を作成する可能性がある。

**緩和策。** 受け入れ基準は「Roadmap 行の予約された `spec:` パスで使われたスラッグに一致するマイルストーン名の kebab-case 要約」と述べている。スラッグは Roadmap 行の `spec:` リンクが予約される行作成時に固定されるため、ピックアップ時に作成の曖昧さはない: `product-manager` は Roadmap 行から予約パスを読み、そのスラッグを正確に使う。リスクは行作成時に軽減され、architect の決定が必要であれば追加のスラッグ長または形式制約を追加することができる。

## スコープ対象外

- 既存 Spec ファイル (`specs/01-*.md` から `specs/08-*.md`) の名前変更 ── すべてすでに適合している。
- Spec ファイルが置かれるディレクトリの変更 ── それはマイルストーン #10 である。
- CI ファイル名形式チェックの追加 ── architect に委ねた構造的決定。
- ADR ファイル名規約の変更 (`.claude/meta/adr/NNN-slug.md`、3 桁プレフィックス) ── ADR ファイルは別の名前空間と規約を使う。
- 規約宣言の派生リポジトリドキュメントへの翻訳 ── フォーク時に派生リポジトリで technical-writer が行うタスク。
