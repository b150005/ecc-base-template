# 実装/設計検証ドメインのオプトイントリガーガイダンス

## ステータス

Approved

**オーナー:** product-manager / implementer
**対象リリース:** template v3.12.0

## 問題

フォークメンテナーが `.claude/verification.yml` (またはその `.example` コンパニオン) を読むと、`implementation.enabled: false` と `design.enabled: false` が、コスト注記のみ ── 「変更ごとのトークン消費量がおよそ 2 倍になる」── と共に存在し、その 2 倍のコストがいつ支払う価値があるかについてのガイダンスがない状態を発見する。コメントには「派生プロジェクトはここでオプトインする」とあるが、フォークメンテナーがオプトインが適切であるかどうかを判断するのに役立つプロジェクト特有のシグナルが提供されていない。

このギャップは、ドメイン `protocol.md` ファイルのランタイムトリガーとは異なる。それらのドキュメントが答えるのは「プロジェクトがオプトインした後に、どの特定の変更でクリティックが生成されるか?」という問いである。マイルストーン #11 は、より前の、プロジェクトレベルの問いに答える: 「自分のプロジェクトのどのような特性の下で、`implementation.enabled` と `design.enabled` をそもそも `true` に設定すべきか?」テンプレート内の既存のドキュメントは、プロジェクト開始時またはレビュー時にポリシーを決定するフォークメンテナーのためにこの問いに答えるものがない。

## ゴール

- `implementation.enabled: true` の具体的なフォーク向けプロジェクト特性トリガーを述べる ── チームサイズ、変更リスクプロファイル、テストオラクル所有権など、フォークメンテナーが個々の変更を精査することなく評価できるシグナルを名付ける。
- `design.enabled: true` の具体的なフォーク向けプロジェクト特性トリガーを述べる ── ADR ケイデンス、可逆性ホライズン、複数チームコンシューマー数など、同様のシグナルを名付ける。
- プロジェクト採用ガイダンスと `implementation/protocol.md` と `design/protocol.md` (`## When to invoke`) の変更ごとのランタイムトリガーを区別する ── 2 つは補完的であり、冗長ではない。
- フォークメンテナーが採用ステップですでに必要とするファイルを超えた追加ファイル読み取りなしに出会える場所にガイダンスを配置する (正確な配置は architect に委ねる; リスク R-01 参照)。
- `.claude/verification.yml` のアクティブデフォルトを変更しない (`implementation.enabled: false`、`design.enabled: false`)。デフォルトオフは ADR-010 の受け入れられたポスチャーであり; ガイダンスはそのポスチャーを説明するものであり、変更するものではない。

## ゴール対象外

- フォークが有効にしているドメインを強制または监査する CI ディテクターやチェックの追加。新しいディテクターは #11 の新しい MECE パーティションを作成し、ADR-014:1800 の「ドキュメント/規約」分類に違反する。これはスコープ外であり、本マイルストーンの帰結として提案されてはならない。
- `implementation/protocol.md` または `design/protocol.md` (`## When to invoke`) からの変更ごとのランタイムトリガーの複製。これらのトリガーは「特定の変更において、プロジェクトがオプトインした後にクリティックは生成されるか?」に答える。#11 は前の採用レベルの問いに答える。2 つのドキュメントは非冗長でなければならない。
- `.claude/verification.yml` のアクティブデフォルトの変更。デフォルトオフは ADR-010 の意図的かつ受け入れられたポスチャーである。本マイルストーンはフォークメンテナーが十分な情報に基づくオプトイン決定を下すのを助けるドキュメントを追加する; 任意のプロジェクトの初期状態を変更しない。
- ガイダンスが配置される正確なファイルまたはセクションの指定。それは architect が所有する構造配置決定である (リスク R-01 参照)。受け入れ基準は最終配置にかかわらず検証可能である。
- `implementation/protocol.md` または `design/protocol.md` の変更ごとのランタイムトリガー基準の変更。これらのトリガーは正確であり、本マイルストーンのスコープ内にない。
- `research` ドメインまたは `citation_discipline` のガイダンスの提供 ── 両方ともデフォルトオンであり、その動作はすでに `verification.yml` と `SKILL.md` の既存のドキュメントで説明されている。

## 受け入れ基準

- **Given** フォークメンテナーが #11 のガイダンスが配置された場所を読む (正確なファイルとセクションは architect が決定する) **when** `implementation.enabled: true` を設定するかどうかを評価する **then** ガイダンスは `implementation` ドメインの少なくとも 3 つの具体的なプロジェクト特性トリガーを名付ける (例: 非自明なカスタムアルゴリズム、独立したレビュアー多様性が限られた小さなチーム、Generator によるテストオラクル所有権の一部) ── 変更ごとの「クリティックを今生成するか?」トリガーとは異なる。

- **Given** フォークメンテナーが #11 のガイダンスが配置された場所を読む **when** `design.enabled: true` を設定するかどうかを評価する **then** ガイダンスは `design` ドメインの少なくとも 3 つの具体的なプロジェクト特性トリガーを名付ける (例: 高い ADR ケイデンス、長いアーキテクチャ可逆性ホライズン、複数の独立したチームにまたがるダウンストリームコンシューマー) ── 変更ごとの「クリティックを今生成するか?」トリガーとは異なる。

- **Given** 各ドメインのプロジェクト採用ガイダンス **when** 読者が `implementation/protocol.md` と `design/protocol.md` の `## When to invoke` セクションと比較する **then** ガイダンスが異なる問いに答えていることが明確である: プロジェクトレベルポリシー (「このプロジェクトはドメインを有効にすべきか?」) と変更レベル呼び出し (「この特定の変更において、クリティックは動作するか?」)。

- **Given** 両ドメインのガイダンス **when** レビュアーが検査する **then** どちらのセクションも `implementation/protocol.md` または `design/protocol.md` の `## When to invoke` セクションからの変更ごとのランタイムトリガーを参照または複製しない。

- **Given** #11 出荷後の `.claude/verification.yml` **when** レビュアーがアクティブファイルを確認する **then** `implementation.enabled` は `false` のまま、`design.enabled` は `false` のまま ── ガイダンスがドキュメントのみであり、デフォルトポスチャーを変更していないことを確認する。

- **Given** ガイダンスの配置 **when** フォークメンテナーが採用のために検証レイヤー設定を評価している **then** 採用ステップですでに必要とするファイルを超えた追加ファイル読み取りなしにプロジェクト採用ガイダンスに出会う (つまり、ガイダンスは設定または Skill の概要と同一場所にある ── 正確な同一場所化は architect の決定だが、ガイダンスは採用ステップがすでに必要とする以外の 3 番目のファイル参照を必要としてはならない)。

- **Given** `implementation` ドメインのガイダンス **when** ディテクターまたは CI 強制言語について検査する **then** 一切含まない ── #11 がドキュメント/規約レイヤーにあり、ADR-014:1800 と不整合な新しい MECE パーティションを導入していないことを確認する。

- **Given** `design` ドメインのガイダンス **when** ディテクターまたは CI 強制言語について検査する **then** 一切含まない ── #11 (採用ガイダンス)、#04 (パス解決 CI)、#05 (Roadmap 構造 CI)、およびプロトコルファイルの変更ごとのランタイムトリガー間の MECE 境界が、将来のマイルストーン作成者がスコープルーティングを評価するのに明確である。

## 主なインタラクション

1. **`implementation/protocol.md` と `design/protocol.md` (`## When to invoke`) とのインタラクション。** これらのファイルの変更ごとのランタイムトリガーは「この特定の変更において、プロジェクトがすでにオプトインした後にクリティックは生成されるか?」に答える。マイルストーン #11 は上流の問いに答える: 「どのようなプロジェクト特性の下で、フォークは `enabled: true` を設定すべきか?」2 つは補完的である。プロジェクト採用ガイダンスは変更ごとのトリガーを複製してはならない; 代わりに読者を後続の問いのためにそれらのファイルに誘導すべきである。

2. **`.claude/verification.yml` と `verification.yml.example` とのインタラクション。** アクティブな設定ファイルのコメントブロックは、コスト注記のみで「派生プロジェクトはここでオプトインする」と述べている。例ファイルは「ユーザーは ADR-010 受け入れ時にこのコストを明示的に受け入れることを選択した; 派生プロジェクトはここでオプトインする」と述べている。どちらもプロジェクト特性シグナルを提供していない。#11 のガイダンスはこのギャップを埋める ── architect の配置決定 (リスク R-01) がそれらのコメントを修正するか、`SKILL.md` にセクションを追加するか、別の場所にするかを決定する。

3. **`SKILL.md` (`## When to invoke`) とのインタラクション。** `SKILL.md` の `## When to invoke` は「ドメインごと。各ドメインの `protocol.md` が独自のトリガーを述べている」と述べている。これは変更ごとのランタイム呼び出しに対して正確だが、プロジェクト採用の問いには対応していない。#11 のガイダンスはこのセクションを補完するか、または同一場所に置かれる ── architect が決定する。

4. **ADR-010 (検証レイヤー一般化) とのインタラクション。** ADR-010 は「派生プロジェクトがオプトインする」という根拠で `implementation` と `design` をデフォルトオフとして確立した。#11 はそのポスチャーを変更しない。オプトイン決定を ADR-010 の Decision または Consequences を変更することなく情報に基づくものにするドキュメントを追加する。

5. **ADR-014:1800 (MECE 境界) とのインタラクション。** ADR-014:1800 の MECE テーブルは #11 を「ドキュメント/規約」と分類する。この分類は実装に対する制約である: #11 は CI ディテクター、新しい Roadmap 構造ルール、または新しい MECE パーティションを作成するメカニズムを導入してはならない。非ゴールセクションはこの制約を成文化している。

6. **architect に委ねた構造的 HOW。** ガイダンスが `SKILL.md` の新しいセクション (`## Project adoption triggers`)、`verification.yml` と `verification.yml.example` のコメントブロックへの修正、新しいスタンドアロン参照ファイル、CLAUDE.md の `## Development Workflow` ステップ 3 への追加、またはその組み合わせとして配置されるかどうか ── すべて architect の forthcoming decision に委ねる。architect は ADR-018 Alternative-B 判別子を適用する: 配置が新しい構造的規約または新しい MECE パーティションを必要とする場合、新しい ADR (ADR-019) が必要であり; ADR-010 の受け入れられた「派生プロジェクトがオプトインする」決定の帰結明確化または拡張である場合、ADR-010 amendment で十分である。 <!-- ref-allow: ADR-019 is a forthcoming reserved number cited as a possible outcome of the architect's decision; it does not yet exist by design -->

## メトリクス

- **先行指標:** 本マイルストーン出荷後、検証レイヤードキュメントを採用決定のために読んでいるフォークメンテナーが、変更ごとのプロトコルファイルを開かずに `implementation` と `design` の明示的なプロジェクト特性トリガーに出会う ── 配置されたガイダンステキストから検証可能。
- **先行指標:** ゼロの「なぜこれを有効にすべきか?」という質問が、プロジェクトレベルポリシー問いに答えるために `implementation/protocol.md` または `design/protocol.md` を完全に読む必要がある。
- **遅行指標:** 派生リポジトリの検証レイヤー設定ミスの削減 (コストを正当化するプロジェクト特性なしにドメインが有効化されているか、明らかに一致する特性があるにもかかわらずドメインが無効のまま) ── 時間の経過によるフォーク監査を通じて観察可能。

## リスクとオープンクエスチョン

### リスク R-01: architect に委ねた構造的決定 ── ガイダンス配置、ADR 戦略

**説明。** 本 Spec はガイダンスがカバーしなければならない *こと* (2 つのデフォルトオフドメインそれぞれの具体的なプロジェクト特性トリガー、変更ごとのランタイムトリガーとの区別、CI 強制なし、アクティブデフォルトの変更なし) と適合したガイダンスの受け入れ基準を述べる。構造的な *どのように* を明示的に委ねる: フォークメンテナーが追加ファイル読み取りなしに採用時に出会えるようにガイダンスが配置される場所; 配置が新しい ADR (ADR-019) または ADR-010 amendment を必要とするかどうか (ADR-018 Alternative-B 判別子の適用: 新しい構造的規約または新しい MECE パーティション → 新しい ADR-019; ADR-010 の「派生プロジェクトがオプトインする」Decision の帰結明確化/拡張 → ADR-010 amendment; ADR-018 が最後に使用された番号、ADR-019 は未使用); およびエージェントプロンプト、`SKILL.md`、`verification.yml`、`verification.yml.example`、または `protocol.md` ファイルが配置の一部として編集を必要とするかどうか。これは `specs/10-spec-adr-directory-pinning.md`、`specs/09-spec-filename-convention.md`、`specs/08-orchestrator-row-guard.md`、および先行構造 Spec が使用した R-01 パターンをミラーする。 <!-- ref-allow: ADR-019 is a forthcoming reserved number cited as a possible outcome of the architect's decision; it does not yet exist by design -->

**architect に渡す緩和制約。** architect の forthcoming decision は以下を指定しなければならない: (a) フォークメンテナーが採用ステップですでに必要とするファイルを超えた追加ファイル読み取りなしに採用ガイダンスに出会えるようにプロジェクト採用ガイダンスが置かれる正確なファイルとセクション; (b) 配置が新しい ADR-019 か ADR-010 amendment か (Alternative-B 判別子); (c) ガイダンスが 1 つの場所に自己完結しているか `SKILL.md`、`verification.yml.example`、および/または `protocol.md` ファイルにまたがって分割されているか (分割の場合、読者がどのように誘導されるか); (d) 配置が新しい CI ディテクターを導入しないか、または ADR-014:1800 の #11 の「ドキュメント/規約」分類と不整合な新しい MECE パーティションを作成しないという明示的な記述。その決定が存在するまで、本 Spec で特定されたギャップ (コスト注記のみ、プロジェクト特性トリガーなし) が運用状態のままである。 <!-- ref-allow: ADR-019 is a forthcoming reserved number cited as a possible outcome of the architect's decision; it does not yet exist by design -->

**注意:** forthcoming architect decision を参照する行の `<!-- ref-allow: -->` 抑制は本 Spec ファイル (`specs/11-verification-domain-opt-in-guidance.md`) のみに存在し、`specs/10-spec-adr-directory-pinning.md` と `specs/09-spec-filename-convention.md` が確立した先例に従っている。抑制は `CLAUDE.md` に現れない。

### リスク R-02: 変更ごとのランタイムトリガーへのスコープクリープ

**説明。** プロジェクト採用決定のガイダンスと `implementation/protocol.md` と `design/protocol.md` の変更ごとのランタイムトリガーは隣接する問いに対応する。将来の作成者またはレビュアーが「このプロジェクトはこのドメインを有効にすべきか?」と「この特定の変更においてクリティックは生成されるか?」を混同し、2 つを単一の統一されたトリガーリストにマージすることを提案する可能性がある。

**緩和策。** 本 Spec の非ゴール、ゴール、および主なインタラクションセクションが境界を明示的に引いている。受け入れ基準 (AC-3 と AC-4) はこの区別について具体的に検証可能である。将来の作成者がトリガーのマージを提案した場合、正しい応答は変更ごとのガイダンスをプロトコルファイルの既存の場所にルーティングし、#11 のために architect が選んだ場所にプロジェクト採用ガイダンスを保持することである。

### リスク R-03: ガイダンスの具体性とプロジェクト多様性

**説明。** プロジェクト特性トリガーが過度に具体的であれば有効なオプトインシナリオを除外する可能性がある; 過度に一般的であればフォークメンテナーが決定を下すのを助けない可能性がある。ガイダンスは実行可能なほど具体的でありながら、偽陰性を作成するほど狭くてはならない。

**緩和策。** 受け入れ基準は最小具体性バーとしてドメインごとに少なくとも 3 つの具体的なトリガーを要求する。implementer はトリガーを「オプトインの価値を高めるシグナル」として組み立て、「必要十分条件」としてではなくすべきであり、リストが加算的でフォークメンテナーが部分一致をゲートではなくガイドとして使用できるようにする。

## スコープ対象外

- `.claude/verification.yml` または `verification.yml.example` のアクティブデフォルトの変更 ── 両ファイルの `implementation.enabled` と `design.enabled` は本マイルストーン出荷後も `false` のまま。
- フォークの検証ドメイン設定を検査する CI ディテクター、監査チェック、またはリンティングルールの追加。
