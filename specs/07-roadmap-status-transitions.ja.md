# Roadmap ステータス遷移オーナーシップ割り当て

## ステータス

Approved

**オーナー:** product-manager / implementer
**対象リリース:** template v3.8.0

## 問題

ADR-014 は Roadmap 行コンテンツに対する明示的な書き込みオーナーシップを割り当てている: `product-manager` が行と `spec:` リンクを作成/更新し、`architect` が `adr:` リンクを追加し、`orchestrator` は読むだけである。ADR-014 が割り当てて **いない** のは、行の *ステータスグリフ* (☐ / ◐ / ☑ / ✗) を変更する権限を持つ者と、Development Workflow のどの手順でその変更が正しい行動かである。

ADR-014 §帰結 → ネガティブはこのギャップを逐語的に認めている: 「形式的なステータス遷移状態機械は本 ADR の対象外。それまでは、成果物生成者によるオーナーシップが暫定的な唯一の安全策である。」暫定慣行がマイルストーン #03、#05、#06 にわたって有機的に生まれた: `product-manager` が Spec を作成した瞬間に ☐→◐ に変更する (着手の瞬間); クオリティゲートのクローズアウト担当者がクオリティゲート通過後に ◐→☑ に変更する。この慣行は首尾一貫しており、合理的であり、ADR-014 の成果物生成者の原則と整合している ── しかし文書化されておらず、名前で割り当てられておらず、したがって初めてマイルストーンを着手するエージェントには見えない。

結果: ADR-014 を忠実に遵守するエージェント (行 + spec: リンク = product-manager; adr: リンク = architect; orchestrator は読むだけ) は、グリフ次元のガイダンスを持たない。すべてのマイルストーン着手で「誰が ◐ を設定するか?」を宣言されたルールからではなく過去セッションのトランスクリプトを読んで再導出することになる。ドリフトリスクは、エージェントが Spec 作成後も行を ☐ のままにしたり、クオリティゲートが閉じる前に ☑ を設定したり、明確な権限なしに ◐→✗ を設定したりすることである。

## ゴール

- 4 つのグリフ遷移 (☐→◐、◐→☑、◐→✗、☑/◐→✗) それぞれのオーナーシップを名前付きロールと名前付き Development Workflow 手順に割り当てる。
- 形式化されたオーナーシップがマイルストーン #03、#05、#06 によってすでに実践された暫定慣行を成文化することを確認する ── ドキュメント/オーナーシップの形式化であり、動作変更ではない。
- 各遷移が有効である前に満たされなければならないゲート条件を記述する (例: ◐→☑ 前にクオリティゲートが通過していること)。
- ADR-014 の既存の行/リンク書き込みオーナーシップとのインタラクションを特定する (グリフ遷移ルールは互換性があり矛盾しないこと)。
- ADR-016 の `specs/NN-progress.md` 削除トリガーとのインタラクションを特定する (「◐→☑ または ◐→✗ 変更」として定義されている ── #07 はその変更のオーナーを統治し、2 つのルールを合成可能にする)。
- 関連するワークフロー手順を実行するエージェントが遭遇できる場所に形式化されたルールが存在するよう記述する (正確な配置 ── CLAUDE.md Roadmap Rules ブロック、Development Workflow セクション、またはエージェントプロンプト ── は architect に委ねる)。

## ゴール対象外

- *誰が* グリフを変更したかを検証する CI 強制ディテクターの構築。#07 はオーナーシップ *割り当て* であり; その割り当ての自動強制は別個の将来のマイルストーンである (存在する場合)。(注: マイルストーン #05 のステータスグリフ整形性チェックはグリフ *値* が 4 つの認可された文字のいずれかであることを検証する ── 補完的であるが変更のオーナーシップとは別個である。)
- 4 つの認可されたグリフ値 (☐ / ◐ / ☑ / ✗) の変更。ADR-014 がそれらを所有する; 本マイルストーンはそれらを変更しない。
- 既存のグリフ遷移動作の変更。形式化は慣行を成文化するものであり、新しいポリシーではない。
- 一般的なワークフロー状態機械エンジンの設計や新しいワークフロー手順の追加。
- エージェントプロンプトの直接変更。エージェントプロンプトを更新するかどうかは architect の判断に委ねる。
- 新しい CI ワークフローファイルの追加。#07 はドキュメント/オーナーシップ割り当てであり、CI 追加ではない。

## 対象ユーザー

| ペルソナ | 説明 | 主なニーズ |
|---------|-------------|--------------|
| product-manager (エージェント) | マイルストーン着手時に Spec を作成する | ☐→◐ が Spec 作成手順での責任であることを知る、それとは別の後の行動ではない |
| クオリティゲートのクローズアウト担当者 (エージェント) | code-reviewer / linter / security-reviewer / performance-engineer がすべて通過した後にクオリティゲートをクローズする | その瞬間に ◐→☑ を変更する権限がある ── かつ義務がある ── ことを知る、それより前ではない |
| orchestrator (エージェント) | Analyze 手順で Roadmap を読む | ◐ 行が適切に in-progress として授権されていると信頼する; ☑ 行がクオリティゲートを通過していると信頼する |
| architect (エージェント) | `adr:` リンクを追加する; マイルストーンを削除する可能性がある | ◐→✗ 対 ☑→✗ の手順と誰が開始するかを知る |
| テンプレートメンテナー (人間) | テンプレートをフォークして管理する | コードレビューで慣行ではなくルールを指し示すことで強制できる、ステータス遷移に対する単一の宣言されたルールを持つ |

## ユーザーストーリー

| 〜として | 〜したい | 〜ために |
|---------|--------------|------------|
| product-manager | マイルストーン着手時に Spec を作成した直後に ☐→◐ に変更しなければならないことを知る | Roadmap が人間による手動更新を待たずに進行中の作業を正確に反映する |
| クオリティゲートのクローズアウト担当者 | すべてのクオリティゲートエージェントが通過したら ◐→☑ に変更する権限と義務があることを知る | ☑ グリフが「クオリティゲートが閉じた」を確実に示す、「誰かが完了と思った」ではなく |
| orchestrator | Analyze 手順で ◐ 行を読み、Spec がディスク上に存在すると信頼する | Roadmap ポインター経由で Spec を解決でき、ファイルが実体化されたかどうかを確認しなくてよい |
| テンプレートメンテナー | 常時読まれる成果物内の各グリフ遷移に対する単一の名前付きルールを見つける | 慣行ではなくルールを指し示すことでコードレビューでグリフ規律を強制できる |
| architect | 削除手順 (◐→✗ または ☑→✗) と誰が開始するかを知る | 時代遅れまたは実現不可能になったマイルストーンが、誰が授権されているかについての曖昧さなしにきれいにマークされる |

## 受け入れ基準

- **Given** ☐ todo の Roadmap 行が新しいセッションで着手される **when** `product-manager` が Spec ファイル (`specs/NN-slug.md`) を作成する **then** `product-manager` は同一の論理的行動でステータスグリフを ◐ in-progress に変更する (Spec 作成と ◐ への変更はワークフロー観点から原子的である ── Spec がディスク上にありマイルストーンが進行中の後も、グリフが ☐ のままであってはならない)。
- **Given** Roadmap 行が ◐ in-progress にある **when** そのマイルストーンのすべてのクオリティゲートエージェント (code-reviewer、linter、security-reviewer、performance-engineer) が通過した **then** クオリティゲートのクローズアウト担当者がグリフを ☑ done に変更する; 他のアクターは ◐→☑ を変更できない。
- **Given** Roadmap 行が ◐ in-progress にありマイルストーンが削除または実現不可能と宣言される **when** 削除決定が行われる **then** マイルストーンを保持しているアクター (product-manager または architect の forthcoming decision による orchestrator; R-01 参照) <!-- ref-allow: forthcoming architect decision for #07; authored when #07 moves to implementation --> がグリフを ✗ dropped に変更する; 行はテーブルに残る (ADR-014: 履歴は書き換えない)。
- **Given** Roadmap 行が ☑ done にありマイルストーンが後に実現不可能または差し戻しと発見される **when** 差し戻し決定が行われる **then** 同じ削除権限 (上記 R-01 参照) <!-- ref-allow: forthcoming architect decision for #07; authored when #07 moves to implementation --> が ☑→✗ dropped に変更できる; 行は残る。
- **Given** 形式化されたグリフ遷移オーナーシップルール **when** ADR-014 の既存の行/リンク書き込みオーナーシップ割り当て (`product-manager` が行 + `spec:` リンクを所有; `architect` が `adr:` リンクを所有; `orchestrator` は読むだけ) と比較する **then** グリフ遷移ルールはそれらの割り当てと整合しており矛盾しない (`product-manager` による ☐→◐ 変更はその Spec 作成オーナーシップと整合し; クオリティゲートのクローズアウト担当者による ◐→☑ 変更は ADR-014 が行作成外の書き込みを product-manager/architect のみに制限していないため ADR-014 と互換性がある)。
- **Given** ADR-016 の `specs/NN-progress.md` 削除トリガー (「◐→☑ または ◐→✗ 変更」として定義) **when** 形式化されたグリフ遷移オーナーシップが適用される **then** 2 つのルールは合成可能である: #07 によって ◐→☑ または ◐→✗ を実行するよう授権されたアクターは、その瞬間に `specs/NN-progress.md` が削除されることを (ADR-016 に従って) 確保する責任も持つ; 変更と削除の間にオーナーシップギャップは存在しない。
- **Given** マイルストーン #03、#05、#06 によって実践された暫定慣行 (product-manager が Spec 作成時に ◐ を設定; クオリティゲートのクローズアウトがゲート後に ☑ を設定) **when** 形式化されたルールがそれらの歴史的マイルストーンに適用される **then** すべての歴史的変更がルールの下で遡及的に有効である ── これがドキュメント/オーナーシップの形式化であり動作変更ではないことを確認する。
- **Given** 形式化されたルール **when** architect の決定によって決定された場所に文書化される **then** 関連するワークフロー手順を実行するエージェントはその手順がすでに必要とするファイル以外のファイルを読まずにルールに出会う (正確な場所は architect に委ねる; R-01 参照)。 <!-- ref-allow: forthcoming architect decision for #07; authored when #07 moves to implementation -->

## 主なインタラクション

1. 本 Spec が形式化する暫定ステータス遷移慣行は 3 回実践された: マイルストーン #03 (product-manager が ADR-016 設計セッションの Spec 作成時に ◐ を設定; implementer がクオリティゲート後に ☑ を設定)、マイルストーン #05 (ADR-017 設計セッションで同じパターン)、マイルストーン #06 (ADR-018 設計セッションで同じパターン)。形式化はパターンを変更しない ── それに名前を付ける。
2. 本 Spec 自身は、Roadmap row #07 を ☐ から ◐ に変更する同じ行動で `product-manager` によって作成されており、まさに形式化されている暫定慣行を実践している。この自己参照的な実行は意図的であり、ルールがその自身の条件下で首尾一貫していることの経験的証拠を構成する。
3. マイルストーン #05 (Roadmap drift-detection CI、ADR-017) とのインタラクション: #05 は各ステータスグリフが 4 つの認可された文字のいずれかであることを検証する ── グリフが *何を* 含むかを確認する。#07 は *誰が* それを変更できるか *いつ* かを割り当てる。2 つのチェックは補完的であり、スコープが重複しない。
4. ADR-016 (クロスセッション進捗永続化、マイルストーン #03) とのインタラクション: ADR-016 は `specs/NN-progress.md` の削除を「◐→☑ または ◐→✗ 変更」によってトリガーされると定義する。#07 はまさにそれらの変更のオーナーシップを統治する。2 つのルールは合成可能である: 授権された変更オーナー (#07 による) は削除トリガー (ADR-016 による) も所有する。オーナーシップギャップは存在しない。
5. 正確なオーナーシップマトリックス (どのロールが削除遷移を所有するか; クオリティゲートのクローズアウト担当者が名前付きロールか複合ロールか; ルールが CLAUDE.md Roadmap Rules、Development Workflow セクション、エージェントプロンプト、またはそれら全てのどこに存在するか; CLAUDE.md 編集に claude-md-authoring Skill チェックリストを従う必要があるか) は明示的に architect の forthcoming decision に委ねる。 <!-- ref-allow: forthcoming architect decision for #07; authored when #07 moves to implementation -->
6. 本マイルストーンでは CI ワークフローファイルは不要。グリフ遷移オーナーシップルールはプロセス/ドキュメント成果物であり、自動強制レイヤーではない。

## メトリクス

- **先行指標:** 本マイルストーン出荷後、すべての新しいマイルストーン着手で Spec 作成と同じセッションに `product-manager` による ☐→◐ 変更が含まれる ── CLAUDE.md の git 履歴を Spec 作成コミットと照合することで検証可能。
- **先行指標:** 本マイルストーン以降のテンプレート自身の Roadmap で「Spec がディスク上にあるのに行が ☐ のまま」インシデントがゼロ。
- **遅行指標:** マイルストーンごとの「どのアクターがグリフを変更するはずだったか?」の再導出コストの削減、エージェントが新しいマイルストーンを開始する際に過去のセッションから推測するのではなくルールを読むことでセッショントランスクリプトで観察可能。

## リスクとオープンクエスチョン

### リスク R-01: architect に委ねられた構造的決定 ── オーナーシップマトリックス、配置、エージェントプロンプトへの影響、Skill の必要性 <!-- ref-allow: forthcoming architect decision for #07; authored when #07 moves to implementation -->

**説明。** 本 Spec は *何を* 割り当てなければならないか (4 つのグリフ遷移、名前付きオーナーロール、ゲート条件、ADR-014 および ADR-016 との互換性) と適合した形式化の受け入れ基準を記述する。構造的な *どのように* を明示的に委ねる: 形式化が ADR-014 amendment か新しい ADR-019 か (architect の forthcoming decision); <!-- ref-allow: forthcoming architect decision for #07; authored when #07 moves to implementation --> 削除遷移 (◐→✗ と ☑→✗) の正確なオーナーシップマトリックスとそれが product-manager、orchestrator、または共有権限のいずれか; エージェントプロンプトを更新するかどうかとどのエージェントが影響を受けるか; および結果として生じる CLAUDE.md 編集に claude-md-authoring Skill の Pre/Post チェックリストを従う必要があるかどうか。これは `specs/05-roadmap-drift-detection-ci.md` (構造的キーイングを ADR-017 に委ねた R-01) と `specs/06-bilingual-parity-detector.md` (ADR-018 に委ねた R-01) のパターンを踏襲する。

**architect に渡す緩和制約。** architect の forthcoming decision は以下を指定しなければならない: (a) ◐→✗ と ☑→✗ 削除遷移を所有するロール、(b) 関連するワークフロー手順で追加ファイル読み取りなしにエージェントが出会えるよう形式化されたルールが文書化される場所、(c) これが ADR-014 amendment か新しい ADR-019 か (architect の forthcoming decision)、(d) エージェントプロンプトの編集が必要かどうかとどのエージェントが影響を受けるか。 <!-- ref-allow: forthcoming architect decision for #07; authored when #07 moves to implementation --> その決定が存在するまで、暫定慣行 (product-manager が Spec 作成時に ◐ を設定; クオリティゲート担当者がゲートクローズ時に ☑ を設定; 削除権限は非公式) が ADR-014 が承認されて以来そうであったように、運用ルールとして残る。

**注意:** リスク R-01 見出し行の `<!-- ref-allow: -->` 抑制は本 Spec ファイル (`specs/07-roadmap-status-transitions.md`) のみに存在し、ADR-017 に対する `specs/05-roadmap-drift-detection-ci.md` と ADR-018 に対する `specs/06-bilingual-parity-detector.md` が設定した先例に従っている。抑制は `CLAUDE.md` に現れない。

### リスク R-02: 作成時の自己参照適用

**説明。** 本 Spec はマイルストーン #07 を着手するセッションで `product-manager` によって作成され、☐→◐ 変更はその同じセッションで実行される。形式化は、形式的なルールがディスク上に存在する前に暫定慣行が正しいことに依存する。暫定慣行が誤っていた場合、本 Spec の作成自体が誤りになる。

**緩和策。** 暫定慣行は ADR-014 の成果物生成者の原則 (「成果物生成者によるオーナーシップが暫定的な唯一の安全策である」) に基づいており、#03、#05、#06 にわたって一貫して実践されてきた。自己参照適用は首尾一貫性の証拠であり、循環論ではない: ルールは作成時に自身の適用を正しく予測する。

### リスク R-03: #05 グリフ整形性チェックとのスコープ重複

**説明。** マイルストーン #05 の `check-roadmap-drift.sh` は各ステータスグリフが 4 つの認可された文字 (☐ / ◐ / ☑ / ✗) のいずれかであることを検証する。#07 はそれらのグリフを誰がいつ設定できるかを割り当てる。概念的な隣接性は狭い: 両方ともグリフ規律に関係する。将来の読者が「グリフ有効性」(#05) と「グリフ変更授権」(#07) を混同する可能性がある。

**緩和策。** MECE 境界はクリーンである: #05 は「グリフ値は合法か?」に答える (CI で自動化可能な文字レベルチェック); #07 は「誰が設定したか、授権されていたか?」に答える (監査ログインフラなしには自動化できないプロセスレベル割り当て)。#07 のルールに関する architect のドキュメントは、将来のマイルストーン作成者が新しい CI 文字チェックを #07 に振り分けたり新しいオーナーシップ割り当てを #05 に振り分けたりしないよう、この境界を明示的に記述すべきである。

## スコープ対象外

- グリフを変更した者の CI 強制 ── 形式化はオーナーシップを割り当てる; 自動検証は別個の将来のマイルストーンである (存在する場合)。
- 4 つの認可されたグリフ値の変更 (ADR-014 がそれらを所有する)。
- 新しい Roadmap 列の追加やテーブル形式の変更 (ADR-014 が列コントラクトを所有する)。
- すべての ADR が Roadmap バックリンクを持つことの強制 (それは #05 のドメイン)。
- 形式化されたルールの派生リポジトリ CLAUDE.md ファイルへの翻訳 (フォーク時に派生リポジトリで technical-writer が行うタスク)。
