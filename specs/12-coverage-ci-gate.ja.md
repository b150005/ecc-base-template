# CI カバレッジゲート (80% ハードチェック)

## ステータス

Approved

**オーナー:** product-manager / implementer
**対象リリース:** template v3.13.0

## 問題

テンプレートの `.claude/CLAUDE.md` `## Testing Requirements` セクションは「最低 80% のテストカバレッジ」を文書化されたルールとして定めている。これを強制する CI ジョブは存在しない。既存の再利用可能ワークフロー `.github/workflows/ci-base.yml` は、派生リポジトリから `test-command` 入力を受け取ってテストを実行するが、しきい値を課さず、カバレッジメトリクスを出力せず、カバレッジが 80% を下回っても ビルドを失敗させない。今日、派生リポジトリは 10% のカバレッジでも CI を通過できる。

このギャップはテンプレートの構造的な立場によって複雑化する: テンプレートリポジトリ自体にはアプリケーションコードが存在しない。実行可能なアーティファクトは bash ディテクタースクリプト (`.claude/meta/scripts/check-*.sh`) とそのコンパニオンテストスイート (`.claude/meta/scripts/test-check-*.sh`) のみである。マイルストーン #12 向けに作成される CI カバレッジチェックはテンプレート自身の bash スクリプトに対して実行するチェックではなく、派生リポジトリが独自のテストスイートとカバレッジツールチェーンに接続する **フォーク可能なスキャフォールド** である。これは `.github/workflows/ci-base.yml` (パラメーター化された `workflow_call`) と `.github/workflows/workaround-check.yml` (デフォルトオフ単一スイッチスキャフォールド) の構造的なポスチャーをミラーしている。

マイルストーン #12 はこのギャップを閉じる: 派生リポジトリが接続した場合に、テストカバレッジが 80% を下回るとビルドを失敗させる CI スキャフォールドを提供し、`## Testing Requirements` に記述されたルールを提案ではなく強制可能な契約にする。

## ゴール

- 派生リポジトリにとって 80% カバレッジしきい値をビルド失敗チェックとして強制する CI スキャフォールド (GitHub Actions ワークフローファイルまたは既存のものへの拡張) を提供する。
- 80% しきい値が単一の情報源にトレースされるようにする: `.claude/CLAUDE.md` の `## Testing Requirements` セクション。CI スキャフォールドはそのしきい値の競合する第 2 の数値定義を導入してはならない。
- 派生リポジトリがテンプレート所有のロジックを変更せずに独自の言語固有カバレッジツールと出力フォーマットを提供できるようにする — `ci-base.yml` のパラメーター化された `workflow_call` アプローチに合わせる。
- アクティベーションポスチャーを明示的かつ単一制御点とする: フォークメンテナーがワークフローファイル自体を編集せずに 1 か所でゲートを有効/無効にできる (正確なポスチャー — 常時オン、デフォルトオフ単一スイッチ、またはリポジトリ変数ゲート — は architect に委ねる; リスク R-01 参照)。
- テンプレートリポジトリ自体でゲートが CI ジョブを失敗させないようにする (アプリケーションカバレッジを測定するものがないため)。
- このマイルストーンが所有する問い (「プロジェクトのテストカバレッジは CI 時に 80% を満たすか?」) と 4 つの既存ディテクター間の MECE 境界を確立する (既存ディテクターはカバレッジしきい値チェックを所有しない)。

## ゴール対象外

- パス解決、ADR テキスト参照、または `.claude/`-ルートのパス言及の確認 — それはマイルストーン #04 (`check-dangling-refs.sh`、ADR-015) が所有する。
- Roadmap 双方向リンク契約またはステータスグリフの適合性の確認 — それはマイルストーン #05 (`check-roadmap-drift.sh`、ADR-017) が所有する。
- EN/JA 見出しツリーパリティの確認 — それはマイルストーン #06 (`check-bilingual-parity.sh`、ADR-018) が所有する。
- 検証ドメインのオプトインガイダンスの提供 — それはマイルストーン #11 (ADR-014:1800 に従ったドキュメント/規約レイヤー) が所有する。マイルストーン #12 はドキュメント/規約マイルストーンではなく、ADR-014 の §(d) MECE テーブル (#04、#05、#09、#10、#11 を名指しするが #12 を含まない) の事前予約スロットを占有しない。これは architect が ADR-018 Alternative-B 判別子を適用する際に考慮すべき実質的な区別である (リスク R-01 参照)。
- テンプレート自身の bash ディテクタースクリプトまたはそのテストスイートに対するカバレッジゲートの実行 — それらのスクリプトにはカバレッジ計装がなく、追加することは本マイルストーンのスコープ外である。
- カバレッジギャップの自動修復 — ゲートは報告して失敗させる; 人間とエージェントが修正する。
- 正確な CI 構造形式 (パラメーター化ワークフロー、`ci-base.yml` 拡張、スタンドアロンファイル) の指定。それは architect の構造的決定である (リスク R-01 参照)。
- GitHub Actions 以外の CI プロバイダーへのスキャフォールドの変換。
- 4 つの既存ディテクタースクリプト (`.claude/meta/scripts/check-dangling-refs.sh`、`check-roadmap-drift.sh`、`check-skill-invariants.sh`、`check-bilingual-parity.sh`) またはその 3 つのテストスイート (`test-check-dangling-refs.sh`、`test-check-roadmap-drift.sh`、`test-check-bilingual-parity.sh`) の変更。マイルストーン #12 はそれらのアーティファクトに変更を加えない。

## 受け入れ基準

- **Given** 派生リポジトリがカバレッジゲートスキャフォールドをアクティブにした状態で (architect が選択するアクティベーションメカニズムにより) **when** テストスイートが実行されて測定されたカバレッジが 80% を下回る **then** スキャフォールドが命名した CI ジョブが非ゼロ終了コードと、測定されたカバレッジと 80% しきい値の両方を名指しする人間が読めるメッセージで失敗する — ゲートを忠告警告ではなくハードなビルド失敗チェックにする。

- **Given** CI スキャフォールドが強制するしきい値 **when** レビュアーが宣言された情報源にトレースバックする **then** しきい値を単一の場所に解決できる: `## Testing Requirements` に「最低 80% のテストカバレッジ」と記述している `.claude/CLAUDE.md` の `## Testing Requirements` セクション。スキャフォールドは漂流しうる第 2 のハードコードされた数値しきい値を導入してはならない。

- **Given** 言語固有カバレッジツール (例: Go `go test -coverprofile` レポート、Python `coverage.py` XML 出力、JavaScript `lcov.info` ファイル、JVM JaCoCo レポート) を使用する派生リポジトリ **when** フォークメンテナーがスキャフォールドを接続する **then** テンプレート所有のワークフローファイルを変更せずに入力またはコンフィグパラメーターを通じてカバレッジコマンドとレポートフォーマットを提供できる。`ci-base.yml` の `workflow_call` `test-command` 入力パターンをミラーする。

- **Given** architect が選択したアクティベーションポスチャー (常時オン、`workaround-check.yml` スタイルのデフォルトオフ単一スイッチ、または `.github/workflows/security.yml` と CodeQL マイルストーン #02 スタイルのリポジトリ変数ゲート) **when** フォークメンテナーがスキャフォールドファイルとそのコンパニオン設定ドキュメントを読む **then** アクティベーションメカニズムが厳密に 1 か所に文書化されており、厳密に 1 つの変更でトグルできる — 第 2 の `if: false` ガード、第 2 の設定キー、`workaround-check.yml` と ADR-002 の「単一スイッチ」規律に一致。

- **Given** テンプレートリポジトリ自身の CI がスキャフォールドを実行する **when** ゲートが評価する **then** 新たな失敗ジョブが導入されない。ゲートはテンプレート自体に対してグリーン by construction または正しく不活性でなければならない — アクティベーションスイッチがデフォルトでオフ (オプトインポスチャー)、またはスキャフォールドがアプリケーションカバレッジアーティファクトの不在を検出してゼロで明示的に終了することによる。テンプレートリポジトリはカバレッジ免除例外または `ref-allow` スタイルの抑制を必要とせずにグリーンのままでなければならない。

- **Given** 4 つの既存ディテクタースクリプト (`.claude/meta/scripts/check-dangling-refs.sh`、`check-roadmap-drift.sh`、`check-skill-invariants.sh`、`check-bilingual-parity.sh`) とその 3 つのテストスイート (`test-check-dangling-refs.sh`、`test-check-roadmap-drift.sh`、`test-check-bilingual-parity.sh`) **when** マイルストーン #12 が出荷する **then** それら 7 つのファイルはいずれも変更されていない — #12 が既存のディテクターレイヤーにスコープ漏れを導入しないことを確認する。

- **Given** カバレッジしきい値の懸念をルーティングする場所を評価している将来のマイルストーン作成者 **when** マイルストーン #12 が確立した MECE 境界を読む **then** 所有する問いが明確である:「プロジェクトのテストカバレッジは CI 時に 80% 最低限を満たすか?」この問いは、#04 の (「散文パス参照は実際のファイルに解決するか?」)、#05 の (「Roadmap の adr:/Roadmap 行のバックリンクは双方向で一貫しておりグリフは適切か?」)、#06 の (「EN と JA のスペック見出しツリーは一致するか?」)、および #11 の (「どのようなプロジェクト特性の下でフォークは実装または設計検証ドメインを有効にすべきか?」) とは異なる。

- **Given** マイルストーン #12 出荷後の `.claude/CLAUDE.md` `## Testing Requirements` セクション **when** レビュアーがそれを読む **then** 正規の記述「最低 80% のテストカバレッジ」を依然として含んでおり、CI スキャフォールド内だけで定義されるしきい値に複製または置き換えられていない。CLAUDE.md セクションが権威ある定義; スキャフォールドがそれを強制する。両者は一致していなければならない: 1 つの正規の宣言、1 つの強制アーティファクト。

## 主なインタラクション

1. **`.github/workflows/ci-base.yml` とのインタラクション。** 既存の `ci-base.yml` 再利用可能ワークフローは `test-command` 入力を受け取りしきい値なしで実行する。マイルストーン #12 のスキャフォールドは `coverage-threshold` 入力 (またはコンパニオンステップ) で `ci-base.yml` を拡張するか、スタンドアロン `workflow_call` ファイルとして出荷するか、別の構造形式を取るか — すべて architect に委ねる。重要な制約は、オプトインしていない派生リポジトリに対して既存の `test-command` 入力とその動作が変更されないままでなければならないことである。

2. **`.github/workflows/workaround-check.yml` とのインタラクション。** workaround-check ワークフローは単一スイッチ (`.github/workaround-tracker.yml` 内の `enabled: true`) によってデフォルトオフで出荷される。architect が #12 にデフォルトオフ単一スイッチポスチャーを選択した場合、これが最も近い構造的先例である。アクティベーションメカニズム (CI ランタイムで読まれる YAML 設定ファイル、リポジトリ変数、またはワークフロー入力) は architect の構造的決定である。

3. **CodeQL アクティベーションパターン (マイルストーン #02) とのインタラクション。** マイルストーン #02 はリポジトリ変数 `CODEQL_ENABLED=true` の背後に CodeQL ジョブをゲートする。architect が #12 にリポジトリ変数ポスチャーを選択した場合、これが先例である。本 Spec はどちらのポスチャーも規定しない; AC-4 は選択されたポスチャーが文書化され単一制御点であることのみを主張する。

4. **`.claude/CLAUDE.md` `## Testing Requirements` とのインタラクション。** スキャフォールドは第 2 の数値しきい値を導入してはならない。単一情報源制約 (AC-2、AC-8) は実装への拘束要件である: スキャフォールドは正規の場所から 80% の数値を読み取るか参照する、または明示的な相互参照で同じしきい値を強制するよう文書化されていなければならない。将来のしきい値変更が厳密に 1 つのファイルの編集を必要とするようにする。

5. **既存ディテクタースクリプトとのインタラクション。** 4 つの既存ディテクター (`.claude/meta/scripts/check-dangling-refs.sh`、`check-roadmap-drift.sh`、`check-skill-invariants.sh`、`check-bilingual-parity.sh`) は本マイルストーンによって変更されない。カバレッジゲートとそれらのディテクター間の MECE 境界は非ゴールセクションと AC-6 および AC-7 に記述されている。

6. **architect に委ねた構造的 HOW。** #12 が (a) `ci-base.yml` を `coverage-threshold` 入力で拡張する新しいパラメーター化再利用可能 `workflow_call` ファイル、(b) `workaround-check.yml` に類似したスタンドアロンデフォルトオフ単一スイッチワークフロー、(c) #02 の CodeQL パターンに類似したリポジトリ変数ゲートワークフロー、またはその組み合わせとして出荷するかどうか — すべて architect の forthcoming decision に委ねる。architect は ADR-018 Alternative-B 判別子を適用する: マイルストーン #12 は新しい CI ハードチェックを導入し、カバレッジしきい値 (新しいキーイング: 80% の数値; 新しい MECE 境界:「CI 時にテストカバレッジはしきい値を満たすか?」という既存のディテクターが所有しない問い) を強制する。#04/#05/#06 の先例 — それぞれが新しいディテクター、新しい MECE 境界、新しい構造的キーイングを導入し、それぞれが新しい ADR を受け取った — は ADR-019 が適切であることを指し示す。ADR-019 は次の未使用 ADR 番号 (016/017/018 は消費済み; #07–#11 の 5 つの ADR-014 修正は新しい番号を消費しない)。architect が決定する; 本 Spec は決定しない。 <!-- ref-allow: ADR-019 is a forthcoming reserved number cited as a possible outcome of the architect's decision; it does not yet exist by design -->

## メトリクス

- **先行指標:** マイルストーン #12 出荷後、フォークメンテナーが単一の設定変更でカバレッジゲートをアクティブにできる (アクティベーションドキュメントを読むことで検証可能)。
- **先行指標:** テンプレート自身の `main` ブランチの CI ジョブがマイルストーン出荷直後に通過する — 新たな失敗ジョブが導入されない (AC-5)。
- **先行指標:** 既存ディテクタースクリプトまたはそのテストスイートファイルへのゼロ変更 (AC-6)、`git diff` で 4 つのスクリプトと 3 つのテストスイートファイルに対して検証可能。
- **遅行指標:** スキャフォールドが採用されると時間の経過によるフォーク監査を通じて観察可能な、テストカバレッジが 80% を下回った状態で通過する派生リポジトリ CI パイプラインの削減。

## リスクとオープンクエスチョン

### リスク R-01: architect に委ねた構造的決定 — CI 形式、アクティベーションポスチャー、ADR 戦略

**説明。** 本 Spec はカバレッジゲートが保証しなければならない *こと* (80% がビルド失敗チェックとして強制される、しきい値が単一の正規情報源にトレースされる、派生リポジトリがテンプレートロジックを変更せずに独自の言語/カバレッジツールを接続できる、アクティベーションポスチャーが単一制御点である、テンプレート自身の CI がグリーンのままである) を述べる。構造的な *どのように* を明示的に委ねる: スキャフォールドが新しいスタンドアロンワークフロー、`ci-base.yml` の拡張、または別の形式かどうか; アクティベーションポスチャーとその単一制御点メカニズム; そして受け入れられた AC が新しい ADR または既存 ADR の修正を必要とするかどうか。

**architect に明示的に渡された ADR-018 Alternative-B 判別子。** architect は ADR-018 Alternative-B 判別子を適用しなければならない。マイルストーン #12 は新しい CI ハードチェック — 新しいキーイング (80% の数値)、新しい MECE 境界 (「CI 時にカバレッジはしきい値を満たすか?」)、既存のディテクターが所有しない新しい構造的アーティファクト — を導入する。このパターンは #04/#05/#06 の先例に一致する: それぞれが新しいディテクター、新しい MECE 境界、新しい構造的キーイングを導入し、それぞれが新しい ADR を正当化した。さらに、#12 は ADR-014 の §(d) MECE テーブル (#04、#05、#09、#10、#11 を名指しするが #12 は含まない) 内の事前予約「ドキュメント/規約」スロットを占有しない。この区別は ADR-014 修正ではなく新しい ADR-019 を指し示すが、architect が決定する。ADR-019 は次の未使用番号 (ADR 016、017、018 は消費済み; マイルストーン #07–#11 は ADR-014 修正を生成し、新しい ADR 番号を消費しない)。 <!-- ref-allow: ADR-019 is a forthcoming reserved number cited as a possible outcome of the architect's decision; it does not yet exist by design -->

### リスク R-02: 単一情報源ドリフト

**説明。** CI スキャフォールドが (例: `if [ "$coverage" -lt 80 ]`) のように `CLAUDE.md` への参照とは独立して「80」を数値リテラルとしてハードコードする場合、将来のしきい値変更 (例えば 85% への引き上げ) は CLAUDE.md ルールと CI スクリプトの両方の編集を必要とし、2 つが乖離しうる。

**緩和策。** AC-2 と AC-8 は implementer をしきい値を 1 か所に保つように拘束する。implementer はこれを次のいずれかで満たす: (a) スキャフォールドが CLAUDE.md をその強制アーティファクトとして扱う設定ファイルからしきい値を動的に読み取る; (b) ワークフローのコメントブロックに CLAUDE.md 相互参照を持つ単一の設定パラメーターにしきい値をエンコードする; または (c) architect が指定する別のメカニズム。architect の構造的決定 (R-01) はこの制約を明示的に考慮しなければならない。

### リスク R-03: テンプレートリポジトリグリーン保証

**説明。** テンプレートリポジトリにはアプリケーションコードがない。カバレッジゲートがテンプレート自体に対して実行してカバレッジアーティファクトが見つからない場合、「カバレッジレポートが見つからない」で失敗するのではなくゼロで終了しなければならない。カバレッジレポートがない場合に失敗するナイーブな実装はテンプレート自身の CI をすぐに壊す。

**緩和策。** AC-5 は拘束受け入れ基準である。architect の構造的決定はテンプレート自体がグリーンのままである明示的なメカニズムを含まなければならない: アクティベーションスイッチがデフォルトでオフ (オプトインポスチャー)、スキャフォールドがカバレッジアーティファクトの不在を検出してログメッセージとともにゼロで終了、またはゲートが派生リポジトリのみにスコープされる。implementer はマイルストーンを完了とマークする前にこれをテンプレートリポジトリに対してテストで確認しなければならない。

### リスク R-04: 言語非依存性

**説明。** カバレッジ出力フォーマットは言語とツールチェーンによって異なる: `coverage.py` XML、Go `coverprofile`、JavaScript `lcov.info`、JVM JaCoCo XML、Rust `llvm-cov`、Swift カバレッジ JSON など。一つのフォーマットしか扱えないスキャフォールドは、派生リポジトリにネイティブ出力の変換を強いることになり、フォーク可能性のゴールを無効にする。

**緩和策。** AC-3 は派生リポジトリがテンプレート所有のロジックを編集せずに独自の言語とフォーマットを接続できることを要求する。`ci-base.yml` の `test-command` 入力をミラーする。architect の構造的決定は、スキャフォールドが派生リポジトリのカバレッジパーセンテージを既に計算済みの入力として受け取る方法 (テンプレートが複数のフォーマットを解析する必要がない)、または出力が最小限の言語非依存エクストラクターによって解析されるカバレッジコマンドを受け取る方法を指定しなければならない。

## スコープ対象外

- カバレッジギャップの自動修復 — ゲートは報告して失敗させる; 人間とエージェントが修正する。
- テンプレート自身の bash ディテクタースクリプトまたはそのテストスイートに対するカバレッジの強制。
- GitHub Actions 以外の CI プロバイダーへのスキャフォールドの変換。
- 4 つの既存ディテクタースクリプトまたはその 3 つのテストスイートの変更。
- ファイルごとまたはパッケージごとのカバレッジ内訳の追加 — ゲートは単一のプロジェクトレベルのしきい値チェックである。
- CI アーティファクトの正確なファイル名、ジョブ名、または構造形式の指定 — それらは R-01 に従った architect の決定である。
