# auth→T2 誤分類に対するリサーチ Tier 検証

## ステータス

Approved

**オーナー:** product-manager / implementer
**対象リリース:** template v3.15.0

## コンテキスト注記: このマイルストーンにおける検証レイヤの適用可否

このマイルストーンは**内部構造マイルストーン** (テンプレートのメタインフラ、構築に必要な外部 API やライブラリのリサーチは不要) です。したがって、検証レイヤのリサーチドメインは #14 の構築には**適用されません** — 外部ソースから検証すべき事実はありません: ライブラリ選定なし、API 使用なし、バージョン固定なし、破壊的変更の評価なし。これは #11、#12、#13 で示された N/A のスタンスと同じです。

ただし、#14 の**主題**はリサーチドメインの Tier モデル (T1/T2/T3) と `.claude/verification.yml` の `default_tier: T2` 設定です。本 Spec はそのモデルを主題コンテンツとして参照する必要があります。Tier モデルを主題コンテンツとして参照することは、このマイルストーンの構築に必要なリサーチのために検証レイヤを起動することとは異なります。この 2 つの読み方は MECE であり、混同してはなりません。

## 問題

リサーチドメインの Tier 表 (`.claude/skills/verification-layer/research/protocol.md`) は **T1** を「破壊的変更、auth、セキュリティ機微な API、暗号プリミティブ」に対する強制 Tier として定義しています。リサーチドメインの設定 (`.claude/verification.yml`) は `default_tier: T2` を設定しています — これは Critic が 1 回実行され、CRITICAL または HIGH の指摘が残らない限りそれ以上繰り返さない、より弱い強制レベルです。

Tier は**成果物ごとに Generator 宣言型**です: `docs-researcher` エージェントが Critic がレビューする前にリサーチ結果ごとに Tier を宣言します。orchestrator は上方向へのエスカレーション (T3→T2、T2→T1) はできますが、下方向には決してできません。

失敗モード: `docs-researcher` が auth 関連の外部事実 (認証ライブラリの動作、authn/authz API の形状、トークン処理のデフォルト、セッション管理フラグ) をリサーチしているにもかかわらず、その成果物に T1 を明示的に宣言しない場合、その事実は静かに `default_tier: T2` に落ちます。orchestrator の「Tier 確認ガードレール」(`orchestrator.md` 104–109 行目) は散文によるバックストップを提供しています: `auth`、`authn`、`authz`、`crypto`、`breaking change`、`migration`、`CVE`、`security`、`permission`、`token` をルーティング時に宣言された Tier を受け入れる前に Tier 確認をトリガーするキーワードとして列挙しています。このガードレールはルーティング時に発火し、orchestrator がリサーチトピック内のキーワードを認識することに依存しています。

ギャップ: ガードレールは orchestrator への散文的な指示です。CI 時に検証可能ではなく、Tier 表に対して監査可能な書面契約として表面化されていません。auth キーワードを省いたトピック記述を持つ Generator 成果物 — しかし内容が認証ロジックに関わる — は、orchestrator のガードレールが発火することなく T2 でレビューに到達する可能性があります。`protocol.md` も `verification.yml` も auth→T1 要件を、orchestrator のランタイム判断とは別個に独立にチェック可能な書面契約の形で述べていません。

マイルストーン #14 はこのギャップを閉じます。検証メカニズムの形態は architect に委ねられており、auth-touches-T1 要件が検証可能で発見可能な契約として表現され、orchestrator への散文的な指示としてのみではなくなります。

## ゴール

- auth→T1 要件を独立に検証可能な書面契約として述べる: `protocol.md` 内の T1 のスコープ (破壊的変更、auth、セキュリティ機微な API、暗号) は Tier 表の記述であるだけでなく、検証をトリガーするルールです。
- 宣言された Tier が T2 または T3 であるが内容が auth/authn/authz/crypto/セキュリティ機微なトピックに関わる Generator 成果物を、T2 で Critic に到達する前に潜在的な誤分類として検出可能にする — orchestrator のガードレールのみがトピック記述の省略に対して開けたままにしているギャップを閉じます。
- メカニズム (architect が選択した形態に関わらず) が orchestrator を唯一の強制点とすることを要求しないようにする; auth→T1 ルールの第二の、独立にチェック可能な表現が存在しなければなりません。
- #14 が所有する問い (「auth 関連内容を持つリサーチ成果物は検証可能な契約として T1 に正しく分類されているか?」) と既存の 5 つのディテクタとの MECE 境界を確立し、将来のマイルストーン作成者がスコープを明確にルーティングできるようにします。
- `default_tier: T2`、Tier 表の構造、および orchestrator のガードレール散文を**無変更のまま**にする。#14 は既存の機構の上に検証レイヤを追加します; Tier 表、デフォルト、または orchestrator のランタイムロジックを変更しません。

## 受け入れ基準

- **AC-1.** #14 が検証契約を配置するアーティファクト (正確なアーティファクトとセクションは architect が決定) があるとき、`docs-researcher` の成果物が auth、authn、authz、crypto、セキュリティ機微な API 使用、またはトークン処理に関わる場合、契約は要求される Tier が T1 であることを明確に述べています — この要件は強制ルールとして表現されており、ガイダンスやベストプラクティスの提案ではなく、`orchestrator.md` を先に参照することなく独立に読めます。

- **AC-2.** #14 が確立した検証契約があるとき、レビュアーが orchestrator の Tier 確認ガードレール (`orchestrator.md` 104–109 行目) と比較した場合、両者が補完的で非重複であることが明確です: orchestrator ガードレールは*ランタイムルーティング*チェック (orchestrator がトピック記述内の特定キーワードを見たときに発火) であり、#14 の契約は同じルールの*書面の、独立にチェック可能な*言明です — ガードレールのキーワードスキャンの失敗 (トピック記述が「auth」を省略) が書面の義務として契約を強制不能のままにしないように。

- **AC-3.** #14 が確立した検証契約があるとき、レビュアーが `.claude/verification.yml` の `default_tier: T2` への変更を検査した場合、値は無変更です — #14 が T2 が適用される*とき*を (auth 関連成果物には適用しない) 絞り込むのであり、非 auth の大多数のデフォルトを変更しないことを確認します。

- **AC-4.** #14 が確立した検証契約があるとき、レビュアーが `research/protocol.md` の Tier 表定義への変更 (T1 スコープ行: 「Breaking changes, auth, security-sensitive APIs, crypto primitives」) を検査した場合、Tier 表は無変更です — #14 が既存の T1 スコープをテスト可能な契約にするのであり、スコープの再定義ではないことを確認します。

- **AC-5.** #14 が確立した検証契約があるとき、レビュアーが orchestrator の Tier 確認ガードレール散文 (`orchestrator.md` 104–109 行目) への変更を検査した場合、その散文は無変更です — #14 が補完的な書面契約を追加し orchestrator のランタイムロジックを変更しなかったことを確認します。

- **AC-6.** 既存の 5 つのディテクタスクリプト (`check-dangling-refs.sh`、`check-roadmap-drift.sh`、`check-skill-invariants.sh`、`check-bilingual-parity.sh`、`check-ecc-delegation-consistency.sh`) とそのテストスイートがあるとき、マイルストーン #14 が出荷された場合、それらのファイルはいずれも変更されていません — #14 が既存のディテクタレイヤにスコープ漏出を導入しないことを確認します。

- **AC-7.** auth-Tier の懸念をルーティングする場所を評価する将来のマイルストーン作成者が #14 が確立した MECE 境界を読む場合、所有される問いは明確です: 「auth 関連内容を持つリサーチ成果物は、独立にチェック可能な書面契約として T1 に検証されているか?」この問いは #04 の (パス解決)、#05 の (Roadmap 構造)、#06 の (EN/JA パリティ)、#12 の (カバレッジしきい値)、#13 の (ECC 不在レビューポスチャー) とは異なります。既存のディテクタや契約が auth-Tier の誤分類の問いを所有していません; auth-Tier の懸念は #14 またはその後継にルーティングされなければなりません。

- **AC-8.** #14 が確立した検証契約があるとき、オペレータ環境のファイルシステムイントロスペクションまたは外部ソース参照について検査した場合、それは一切行いません — 契約がリポジトリ内のアーティファクト (`protocol.md` の Tier 表、`verification.yml` の `default_tier`、`orchestrator.md` の auth キーワードリスト) から完全に導出可能であり、外部サービスのライブプローブを行わないことを確認します。

## 主なインタラクション

1. **`research/protocol.md` Tier 表とのインタラクション。** Tier 表は T1 のスコープに既に「auth」を挙げています: 「Breaking changes, auth, security-sensitive APIs, crypto primitives。」表は T1 をいつ使うかの記述です; 現在は検証可能な契約として機能していません。#14 の検証メカニズムは auth→T1 要件を第二の表現に対してチェック可能にします — 表を変更することなく。architect の配置決定 (R-01) は、第二の表現が Generator の事前リサーチチェックリストの新しい制約なのか、Tier 表自体への修正なのか、新しい機械可読ルールなのか、別の形態なのかを決定します。

2. **`.claude/verification.yml` `default_tier: T2` とのインタラクション。** デフォルトは非 auth の大多数には正しく、T2 のままでなければなりません。#14 のメカニズムは例外を定義します — auth 関連成果物は Generator のトピック記述の文言とは無関係に T2 に静かに落ちることができない — を Generator のトピック記述の文言から独立した書面制約として。AC-3 は無変更デフォルト要件について具体的に検証可能です。

3. **`orchestrator.md` Tier 確認ガードレール (104–109 行目) とのインタラクション。** ガードレールはリサーチトピック内のキーワード `auth`、`authn`、`authz`、`crypto`、`breaking change`、`migration`、`CVE`、`security`、`permission`、`token` を orchestrator が認識するときにルーティング時に発火します。失敗ケース: トピック記述がそれらのキーワードなしに「login flow」または「session management」を使用するリサーチ成果物。#14 の第二の表現はガードレールのスキャンが失敗するときでも強制可能でなければなりません。両者は補完的です; いずれも他方を置換しません (AC-2)。

4. **既存の 5 つのディテクタ (#04/#05/#06/#12/#13) とのインタラクション。** architect の選択メカニズムが新しいディテクタであれば、#04 が確立し #05/#06/#13 がミラーした `check-*.sh` ファミリーに加わります。それが正しい形態なのか — あるいは #11 の ADR-014:1800 「文書/規約」分類に類似したドキュメント/規約配置がより適切なのか — は architect の構造的決定です。#14 の Non-goals は、メカニズムに関わらず #14 が既存の 5 つのディテクタやそのスイートを変更しないことを固定します。

5. **ADR-020 (#13 — ECC 不在シグナル) とのインタラクション。** ADR-020 は最も最近消費された ADR 番号です。architect の #14 の構造的決定が新しい ADR を正当化する場合、ADR-021 が次の未使用番号です。新しい ADR-021 が正当かそれとも修正で足りるかは architect の判断であり、ADR-018 Alternative-B 判別子を適用します (リスク R-01 参照)。

6. **ADR-014 §(d) MECE 表とのインタラクション。** ADR-014 の §(d) MECE 表は #04、#05、#09、#10、#11 を挙げています (ADR-019 の推論により #12 について修正済み、ADR-020 経由で #13 について修正済み)。#14 のスロットを事前予約**していません**。#14 は事前予約された文書/規約スロットを占有しません — architect が ADR-018 Alternative-B 判別子を適用する際に考慮すべき実質的な区別。これは `specs/12-coverage-ci-gate.md` R-01 と `specs/13-ecc-absent-signal.md` R-01 による観察をミラーします。

7. **構造的 HOW は architect に委ねる。** #14 が (a) T1 スコープ行を強制的な事前分類ルールに格上げする `research/protocol.md` への修正、(b) Tier 宣言が受け入れられる前に発火する `docs-researcher.md` の新しいエージェントプロンプト制約、(c) auth→T1 要件を独立にチェック可能な義務として命名する新しいスタンドアロン契約文書または SKILL.md セクション、(d) セッションや CI でリサーチ成果物を T2/T3 宣言について auth キーワード一致トピックに対して監査するディテクタスタイルスクリプト、または (e) その組み合わせとして出荷するかどうか — すべて architect の forthcoming decision に委ねます。architect は ADR-018 Alternative-B 判別子を逐語的に適用します。ADR-021 は次の未使用番号 (ADR 016–020 は消費済み) です。architect が決定します; 本 Spec は決定しません。

## メトリクス

- **先行指標:** #14 出荷後、auth→T1 要件が `orchestrator.md` 以外の少なくとも 1 つのアーティファクトに書面の独立にチェック可能な契約として表現されている — architect がそれを配置するアーティファクトを読むことで検証可能。
- **先行指標:** 既存の 5 つのディテクタスクリプトやそのテストスイートファイルへのゼロ変更 (AC-6)、それらのアーティファクトに対する `git diff` で検証可能。
- **先行指標:** #14 出荷後に `.claude/verification.yml` の `default_tier: T2` が無変更 (AC-3)、ファイルを読むことで検証可能。
- **遅行指標:** 契約が整備された後に、derived repositories 全体で auth 関連リサーチ成果物がサイレントに T2 で Critic に到達する回数の削減、Generator の Tier 宣言の時間経過による監査を通じて観察可能。

## リスクとオープンクエスチョン

### リスク R-01: architect に委ねた構造的決定 — 検証メカニズム、配置、ADR 戦略

**説明。** 本 Spec は検証契約が達成しなければならない*こと* (auth 関連成果物は T2 に静かに落ちることができない; ルールは独立にチェック可能; default_tier、Tier 表、orchestrator ガードレールは無変更; 既存ディテクタへのスコープ漏出なし; 外部イントロスペクションなし) と適合した検証契約の受け入れ基準 (AC-1 から AC-8) を述べます。構造的な*どのように*を明示的に委ねます: メカニズムがプロトコル修正、エージェントプロンプト制約、文書/規約配置、新しいディテクタ、またはその組み合わせかどうか; 契約が着地する正確なアーティファクトとセクション; および解決策が新しい ADR-021 か既存 ADR への修正 (ADR-008、ADR-010、その他) を必要とするかどうか (ADR-018 Alternative-B 判別子を適用: NEW ディテクター + NEW MECE 契約境界 + NEW キーイング/メカニズム ⇒ 新しい ADR-021; ADR-008 の既に述べられているが未形式化の T1-for-auth ルールの帰結明確化/拡張 ⇒ ADR-008 修正; ADR-020 は最後に消費された ADR 番号、ADR-021 は次の未使用)。これは `specs/12-coverage-ci-gate.md` R-01 と `specs/13-ecc-absent-signal.md` R-01 の明示的な引き継ぎをミラーします。

**architect に明示的に渡された緩和制約。** architect の forthcoming decision は以下を指定しなければなりません: (a) auth→T1 検証契約が着地する正確なアーティファクトとセクション、`orchestrator.md` を参照することなく独立に読めるように; (b) 契約がガードレールのキーワードスキャンが見逃せるトピック記述省略失敗 (「auth」キーワードなしの auth 内容) をカバーする方法; (c) 解決策が新しい ADR-021 か既存 ADR への修正かどうか (Alternative-B 判別子、句ごとの推論を記録); (d) #14 が #04/#05/#06/#12/#13 およびドメインごとの Tier 機構に対する MECE 境界のどこに位置するかの明示的な言明、および新しい契約パーティションを追加するかどうか。その決定が存在するまで、本 Spec で特定されたギャップ (auth→T1 ルールが orchestrator 散文としてのみ表現されている; トピック記述省略が T2 へのサイレントなルーティングを可能にする) が運用状態のままです。

**注記:** `<!-- ref-allow: -->` 抑制は、architect の forthcoming decision (ADR-021) と JA 兄弟 (`specs/14-research-tier-validation.ja.md`) を参照する行に本 Spec ファイルの作成時点で存在し、`specs/13-ecc-absent-signal.md`、`specs/12-coverage-ci-gate.md`、`specs/11-verification-domain-opt-in-guidance.md` が設定した先例に従い、本 Spec ファイルにのみ存在していました。それらは `.claude/CLAUDE.md` には存在しません。それらの抑制は ADR-021 と JA 兄弟が実現された時点で除去されました (#11/#12/#13 の過剰抑制除去先例)。

### リスク R-02: Tier 表または default_tier の変更へのスコープクリープ

**説明。** 将来の作成者またはレビュアーが「検証契約を追加する」と「T1 のスコープを再定義する」または「すべてのリサーチで default_tier を T1 に引き上げる」を混同するかもしれません。前者は #14 より広い; 後者は非 auth の大多数に対して T2 Tier の有用性を排除します。

**緩和策。** AC-3 と AC-4 はデフォルト無変更と Tier 表無変更要件について具体的に検証可能です。Non-goals は両者を成文化します。将来の作成者が T1 スコープの再定義または `default_tier` の変更を提案した場合、正しい対応はそれを新しいマイルストーンまたは ADR-008 への意図的な修正としてルーティングすることであり、#14 に折り込むことではありません。

### リスク R-03: すべてのセキュリティトピック誤分類の処理へのスコープクリープ

**説明。** Tier 表の T1 スコープは「auth、セキュリティ機微な API、暗号プリミティブ」を挙げています — 「auth」のみではありません。#14 が auth に対して指定するメカニズムは原則として crypto とセキュリティ機微な API にも適用されます。すべての T1 スコープトピックに拡張することはより大きなサーフェスです。

**緩和策。** auth→T2 誤分類は orchestrator の Analyze スコープスケッチからの命名された特定の失敗モードです。architect の実装は、選択されたメカニズムが auth のみではなく T1 スコープ全体 (auth + crypto + セキュリティ機微な API) で動作する場合、完全な T1 スコープを自然にカバーする可能性があります — そして、それは受け入れられます。受け入れられないのは T1 の既に定義されたスコープ外のトピックへのスコープ拡張です (例: 新しい T1 カテゴリを発明する)。Non-goals と AC-1 はこれを境界付けます: 契約は `protocol.md` に既に存在するままの T1 スコープをカバーし、強制ルールとして適用します。#14 によって新しい T1 カテゴリを導入することはできません。

### リスク R-04: protocol.md が後で修正された場合に検証契約が陳腐化する

**説明。** `protocol.md` の Tier 表の T1 スコープ行が後で修正された場合 (例: 「OAuth flows」を明示的に追加する)、別のアーティファクトの検証契約が更新されないと、2 つの表現が乖離します。これは ADR-012 が `code-reviewer` 委譲テーブルに対して命名した「行がサイレントに陳腐化する」失敗と同じです。

**緩和策。** architect の構造的決定 (R-01) は検証契約と `protocol.md` がどのように同期を保つかを指定しなければなりません。1 つのアプローチ: 契約はスコープを複製するのではなく `protocol.md` の T1 スコープ行を直接参照するので、スコープの単一の真実の源は依然 Tier 表です。別のアプローチ: 両者が同じアーティファクトに居住する。実装者は将来の `protocol.md` T1 スコープ修正が契約も更新することを必要とし、サイレントな乖離を許さないことを検証しなければなりません。
