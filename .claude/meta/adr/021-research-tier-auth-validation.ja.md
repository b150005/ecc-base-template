## コンテキスト

ADR-008 は **Generator 宣言型 Tier モデル** とともにリサーチ検証レイヤを導入した: `docs-researcher` が外部リサーチ成果物ごとに T1/T2/T3 を宣言し、`research-critic` がレビューし、orchestrator は上方向へのエスカレーション (T3→T2、T2→T1) はできるが下方向には決してできない。ADR-008 §「Tier 定義」は T1 スコープを **「破壊的変更、認証/認可、セキュリティ機微な API、暗号プリミティブ」** と固定する; `.claude/skills/verification-layer/research/protocol.md` (Tier 表、49–53 行目) は同じ行を **「Breaking changes, auth, security-sensitive APIs, crypto primitives」** として保持する; `.claude/verification.yml` (34–38 行目) は `default_tier: T2` と、T1 の説明に同じく「auth」を挙げるコメントブロックを設定する。

ADR-008 §「Tier 確認ガードレール」はバックストップを追加した: orchestrator は閉じたキーワード許可リスト (`auth`、`authn`、`authz`、`crypto`、`breaking change`、`migration`、`CVE`、`security`、`permission`、`token`) を適用し、**リサーチトピック** がそのいずれかを含むとき宣言された Tier を確認する。そのガードレールは `.claude/agents/orchestrator.md` 内に散文として符号化されている — `**Tier-confirmation guardrail**:` ブロックである。

> **行範囲の訂正 (事実、実装者のために記録)。** Spec (`specs/14-research-tier-validation.md`) はこのガードレールを繰り返し「`orchestrator.md` 104–109 行目」と引用する。本設計セッションで `grep -n` と `sed -n` により独立に再検証した: 文字列 `**Tier-confirmation guardrail**:` は **103 行目から始まり** ("never downward. **Tier-confirmation guardrail**: when the")、ブロックは **109 行目で終わる** ("path (ADR-008 §Consequences).")。Spec の「104–109」は **開始** が 1 だけずれている。実装者は **検証済み範囲である 103–109 行目** を使用しなければならない — あるいは、行番号は壊れやすいため、より堅牢には、ガードレールを **内容/アンカーで** 引用する: `.claude/agents/orchestrator.md` §「Research domain routing」配下の `**Tier-confirmation guardrail**:` ブロックである。本 ADR は Spec の「104–109」を伝播させない; 以下のすべての参照は訂正済み範囲または内容アンカーを使う。Spec の Non-goals/Out-of-scope の行で「orchestrator.md lines 104–109」と述べるものは、その同一性が太字文字列アンカーにより一意なブロックに対する *無変更* 義務を記述している; この 1 ずれは義務を変えず引用のみを変える。訂正済み引用を将来の読者が誤導されないようここに記録する。

`specs/14-research-tier-validation.md` が権威あるスコープである — AC-1 から AC-8、Non-goals、R-01 から R-04、7 つの Key interactions。本 ADR は Spec が `architect` に明示的に委ねた **構造的** 決定を記録する (Spec Risk R-01 (a)–(d)、Key-interaction 7): 検証メカニズムとその形態、auth→T1 契約が着地する正確な成果物とセクション、トピック記述欠落のカバレッジ、ADR-018 Alternative-B ディスクリミネータによる新規 ADR か修正かの決定、MECE 境界、R-04 の陳腐化同期の取り扱い。Spec はこの決定を ADR-021 と命名し、ディスクリミネータを architect に逐語的に委ねる; 本 ADR がそれを閉じる。

#14 が閉じるギャップ (Spec §Problem): auth→T1 要件は今日 **のみ** (a) `protocol.md` 内の *記述的* な Tier 表の行 (「いつ T1 を使うか」の記述であり、チェック可能な義務ではない) と (b) orchestrator の *ランタイム* キーワードスキャン (orchestrator が **トピック記述内に** auth キーワードを認識したときのみ発火する) として存在する。トピック記述が「login flow」や「session management」と言う Generator 成果物 — auth 内容だが「auth」キーワードなし — は T2 を宣言し、orchestrator スキャンは発火せず、その成果物は静かに T2 で Critic に到達する。`protocol.md` も `verification.yml` も auth→T1 ルールを、orchestrator のランタイム判断とは別個に、成果物に対し独立にチェック可能な書面契約として述べていない。

6 つのハード制約が設計を縛り、交渉不可である (Spec Non-goals、Out of scope、AC-3/AC-4/AC-5/AC-6/AC-8):

1. **`.claude/verification.yml` の `default_tier: T2` は無変更 (AC-3)。** デフォルトは非 auth の多数派にとって正しい; #14 は T2 が安全な *とき* を狭めるのであり、デフォルトを変えない。
2. **`protocol.md` の Tier 表 T1 スコープ行は無変更 (AC-4)。** その行は既に「auth」を挙げている; #14 はそのスコープをテスト可能な契約にするのであり、T1 を再定義しない。新規 T1 カテゴリなし (Spec R-03)。
3. **orchestrator の Tier 確認ガードレール散文は無変更 (AC-5)。** それは #14 の契約を *補完する* ランタイムバックストップである; いずれも他方を置換しない (AC-2)。
4. **既存 5 ディテクタへのスコープ漏出なし (AC-6)。** `check-dangling-refs.sh`、`check-roadmap-drift.sh`、`check-skill-invariants.sh`、`check-bilingual-parity.sh`、`check-ecc-delegation-consistency.sh` とそのテストスイートは **変更されない**。
5. **オペレータ環境のイントロスペクション/外部ソース参照なし (AC-8)。** 契約はリポジトリ内成果物のみから導出可能である; 外部サービスへのライブプローブなし。
6. **メカニズムは orchestrator を唯一の強制点にすることを要求しない (Spec Goals)。** auth→T1 ルールの第二の、独立にチェック可能な表現が存在しなければならない。

第七の力は **ADR-018 Alternative-B ディスクリミネータそのもの** であり、Spec R-01 と Key-interaction 7 が architect に委ね、以下の Decision 1 で逐条適用される — #12 と #13 のために ADR-019 §5 と ADR-020 §1 が適用したのと同じ道具である。

第八の力は **#04 ダングリング参照ディテクタ** であり、現在アクティブな CI である。本 ADR ファイルは #04 ディテクタの Check-1 スコープにある; まだ書かれていない `.claude/meta/scripts/check-research-tier-auth.sh`、`.github/workflows/research-tier-auth-check.yml`、アクティベーション設定への言及は Check 2 配下に入り、そこから ADR ファイルは #04 ディテクタ自身の文書化されたスコープ決定により除外される (ADR ファイルは歴史的記録である; その `.claude/` 始まりの前方パスは Check-2 検証されない)。本 ADR 内の同じ前方参照行は実装セッションウィンドウのために `<!-- ref-allow: -->` アンカーを携える、#19/#20 の設計時先例; それらは成果物が実体化した時点で除去される (#11 の過剰抑制先例 — `technical-writer` の判断であり、ここでは実行しない)。

## 決定

#14 を **新規 ADR-021** として解決し (ADR-008 修正でも ADR-010 修正でもない)、後続の実装セッションで、T2/T3 で宣言された auth 関連内容について **検証レビュー成果物** を検証する **新規デフォルト無効ディテクタスクリプトとフォーク可能なデフォルト無効ワークフロー** を出荷する。auth→T1 書面契約は **`protocol.md` 内の Tier 表の直下に併設** され (既存 T1 スコープ行を *参照し、決して複製しない* 新規散文サブセクション)、**オペレータ環境イントロスペクションゼロ** で、テンプレートは **構成上グリーン** である。これは後続の実装セッションで出荷された。具体的には:

### 1. 新規 ADR か修正か — ADR-018 Alternative-B ディスクリミネータを逐条適用

Spec の R-01 (c) は `architect` に明示的選択「新規 ADR-021 か既存 ADR (ADR-008、ADR-010、その他) への修正か」を委ね、ADR-018 の Alternative-B ディスクリミネータを逐語的に適用するよう指示する: *#14 は既存ディテクタのいずれも所有しない **新規契約境界** + **新規キーイング/メカニズム** + **新規構造的成果物** を導入するか (⇒ 新規 ADR)、それとも ADR-008 の既に述べられているが未形式化の T1-for-auth スコープ行の **帰結明確化/拡張** か (⇒ ADR-008 修正)?* 誠実に、逐条適用する:

- **新規契約境界か? Yes — ADR-014 §(d) が事前予約しないパーティション。** #14 は次の問いを所有する: *「内容が auth/authn/authz/crypto/セキュリティ機微 API に関わる research-verification 成果物は、orchestrator のランタイムキーワードスキャンとは独立に、独立チェック可能な書面契約として T1 に分類されているか?」* 以下の §3 は既存所有者がこれを保持しないことを示す。ADR-014 §(d) の MECE 表は #04/#05/#07/#08 を挙げる (そして §(d) の系譜は #09/#10/#11 に及び、ADR-019 §5 経由で #12、ADR-020 §2 経由で #13 のため修正済み); それは #14 のスロットを **事前予約しない**。Spec Key-interaction 6 がこれを明示する。これは ADR-019 §5 が #12 のため、ADR-020 §1/§2 が #13 のため記録したのと同じ事前未予約スロットの観察である — #07–#11 (各々が ADR-014 §(d) が既に予約したスロットを *埋め*、よって正しく番号を消費しない ADR-014 修正を取った) との決定的区別。
- **新規キーイング/メカニズムか? Yes。** キーイングは *「検証レビュー成果物の内容 (そのトピック行ではない) における auth キーワードの存在 対 その同一成果物に宣言された Tier」* である。これは次のいずれでもない: ADR-015 のパス解決キーイング、ADR-017 の主張不在キーイング、ADR-018 の規約存在キーイング、ADR-019 のカバレッジ百分率キーイング、ADR-020 のプロンプト内表整合性キーイング。決定的な新規メカニズムは *orchestrator のトピック行スキャンが見逃すトピック記述欠落を捕捉するためにまさに成果物本文をスキャンする内容キー型 Tier 監査* である (Spec Goals、Key-interaction 3、R-01 (b))。
- **新規構造的成果物か? Yes。** 新規 `check-*.sh` ファミリーメンバ (`check-research-tier-auth.sh`) + 新規フォーク可能ワークフロー + 新規アクティベーション設定 + 新規 `test-check-*.sh` スイート、加えて `protocol.md` 内の新規散文契約サブセクション。既存 5 ディテクタのいずれもこれらのどれも所有しない。

3 つのディスクリミネータ条項すべてが満たされる — トライアド **3/3**。構造的半分が支配する、ADR-015 (自己分類)、ADR-017 (Alternative B)、ADR-018 (Alternative B)、ADR-019 §5、ADR-020 §1 がそうしたのと完全に同じく。**ADR-008 修正は却下される**: ADR-008 の決定 (Tier モデル、Generator 宣言型スコープ、ガードレール) は #14 により *無変更* である (Spec Non-goals AC-3/AC-4/AC-5 がこれを固定する)。#14 は ADR-008 のガードレールがトピックレベルで *命名したがキーワードなし内容について構造的に未強制のまま残した* ギャップを閉じる — それは ADR-017/ADR-018/ADR-019/ADR-020 が各々新規 ADR と自己分類した「新規ディテクタ + 新規境界 + 継承可能ルール」の形であり、ADR-008 の決定の帰結明確化ではない。同じ理由で **ADR-010 修正も却下される**: ADR-010 はレイヤのクロスドメイン構造とオプトインスイッチを一般化した; #14 はその構造を変えずドメインも追加しない — それは既存リサーチドメイン機構の上に内容キー型検証パーティションを追加する。

### 2. 検証メカニズムとその形態 — 内容キー型ディテクタ + 併設書面契約

Spec Key-interaction 7 は 5 つの候補形態 (a–e) を挙げる。選択された設計は **(c) + (d) の組合せ** であり、意図的に (a) でも (b) でもない:

- **(c) — 書面契約: `protocol.md` 内の Tier 表の直下の新規散文サブセクション。** タイトル (正確な文言は実装者のもの) は、**強制ルール** として (ガイダンスでも、ベストプラクティスでもなく) 次を述べる: *内容が Tier 表の既存 T1 スコープ行のいずれかの項目 — auth、authn、authz、crypto、セキュリティ機微 API — に関わる検証レビュー成果物は T1 を宣言しなければならない; トピック行がどう書かれていようと、そのような内容に T2/T3 は非適合である; この義務はまず `orchestrator.md` を参照せずここで独立に読める。* サブセクションは **既存 T1 スコープ行をポインタで参照し (「上記の Tier 表 T1 スコープ行」)、決して複製しない** — T1 が *何を* カバーするかの単一の真実の源は Tier 表のままである (R-04 解決、Decision 5 参照; ADR-019 §3 が 80% 値に使ったのと同じ「参照せよ、再宣言するな」の規律)。この追加は **表の下に追記される新規サブセクション** である; Tier 表の行テキストを編集しない (AC-4 維持 — 実装者が Tier 表行に対する `git diff` で検証) し、`verification.yml` (AC-3) も `orchestrator.md` (AC-5) も編集しない。
- **(d) — ディテクタ: 新規デフォルト無効 `check-*.sh` スクリプト** で、**検証レビュー成果物** (リサーチドメインが生む `.claude/templates/verification-review-template.md` 形の成果物 — Generator の宣言した Tier とリサーチ内容を携える成果物) を次の失敗モードについて監査する: **内容が auth スコープキーワード集合に一致しつつ宣言された Tier が T2 か T3 である**。それはトピック行のみではなく成果物 *本文* をスキャンする — それが orchestrator スキャン見逃しケースを捕捉する正確なメカニズムである (Key-interaction 3、R-01 (b))。一致時、それは成果物、一致した auth 用語、宣言された Tier 対 要求される T1 を命名する人間可読メッセージとともに FAIL する。

形態 (a) と (b) は **明示的に選ばれず**、理由を記録する: (a)「Tier 表の行そのものを機械可読な強制ルールに格上げ」は *Tier 表を編集する* ことになり AC-4 に違反する (Spec Non-goals: 「Tier 表定義を変更すること … #14 はそのスコープをテスト可能な契約にするのであり、T1 が何を意味するかを再定義しない」)。(b)「`docs-researcher.md` 内の新規エージェントプロンプト制約」はルールをエージェントプロンプト内に戻す — まさに #14 が破るために存在する「散文のみ、ランタイムのみ、単一強制点」性質である (Spec Goals: 「orchestrator を唯一の強制点とすることを要求しない」; 単一点を orchestrator から docs-researcher へ移すことにも同じ反論が適用される)。書面契約は **独立にチェック可能でエージェント指示ではない** ものでなければならない (AC-1、AC-2); ディテクタがそれを *チェック可能* にし、`protocol.md` サブセクションがそれを *`orchestrator.md` なしで読める* ようにする。

### 3. MECE 境界 — ADR-014 §(d) が事前予約しない新規パーティション

#14/ADR-021 は次の問いを所有する: **「内容が Tier 表の既存 T1 スコープ (auth/authn/authz/crypto/セキュリティ機微 API) に関わる research-verification 成果物は、orchestrator のランタイムトピックキーワードスキャンとは独立に、独立チェック可能な書面契約として T1 に宣言されているか?」** これは **新規パーティション** であり、既存のすべての所有された問いと異なる:

| 所有者 | 所有する問い | スキャンする入力 |
|---|---|---|
| #04 `check-dangling-refs.sh` (ADR-015) | 散文/パス参照は実ファイル/ADR に **解決** するか? | リポジトリの Markdown 成果物 |
| #05 `check-roadmap-drift.sh` (ADR-017) | **双方向 Roadmap インデックス契約** が成立し、すべての Status グリフは整形式か? | `.claude/CLAUDE.md` + ADR 群 |
| #06 `check-bilingual-parity.sh` (ADR-018) | **EN↔JA ペアが構造的に一致する** か (見出し木、全角括弧、存在)? | ペアの `.md`/`.ja.md` 成果物 |
| #11 (検証ドメインオプトインガイダンス、ADR-014 §(d)) | どのプロジェクト特性下でフォークは implementation/design 検証ドメインを **有効化** すべきか? | 文書/規約 (ディテクタなし) |
| #12 `coverage-gate.yml` (ADR-019) | プロジェクトの **テストカバレッジ** は CI 時に強制される 80% 最低を満たすか? | 派生リポジトリの算出済みカバレッジ百分率 |
| #13 `check-ecc-delegation-consistency.sh` (ADR-020) | `code-reviewer.md` の ECC 委譲表は内部整合的で、常在の劣化レビュー姿勢は発見可能か? | `code-reviewer.md` の委譲表 — リポジトリ内部のみ |
| **#14 `check-research-tier-auth.sh` (ADR-021)** | **auth 関連の research-verification 成果物は、独立チェック可能な書面契約として T1 に宣言されているか?** | **検証レビュー成果物の内容 対 その宣言された Tier — リポジトリ内部のみ、外部プローブなし** |

欠陥はちょうど一人の所有者にマップする: *壊れたポインタ* は #04 の; *Roadmap インデックス不整合* は #05 の; *構造的に乖離した EN/JA ペア* は #06 の; *検証ドメイン有効化ガイダンスの問い* は #11 の文書関心事; *閾値未満のカバレッジ* は #12 の; *委譲表内部不整合* は #13 の; *auth 関連内容が T1 未満で宣言された誤分類* は #14 の、そして **#14 のみ** の。境界は明瞭である: #14 は任意のポインタを決して解決せず、Roadmap に決して触れず、EN/JA パリティに決して触れず、カバレッジを決してチェックせず、委譲表を決して検証せず、そして — 決定的に — **オペレータ環境や任意の外部ソースを決してプローブしない** (AC-8; ADR-020 §3 が引いたのと同じ構成的不可能性境界を、ここでは ECC 存在ではなくリサーチ内容監査に適用)。Spec AC-7 がこれをルーティング解として固定する: auth-Tier 誤分類関心事は #14 か後継にルートし、#04/#05/#06/#12/#13 へは決してルートしない。

### 4. オペレータ環境イントロスペクションなし/外部参照なし — AC-8 制約

ディテクタはリポジトリ成果物のみを読む (検証レビュー成果物と、キーワードスコープのための `protocol.md` の Tier 表行)。`~/.claude/` を決して読まず、ネットワーク呼び出しを決してせず、外部サービスを決してプローブしない。ディテクタが一致させる auth スコープキーワード集合は **`protocol.md` の Tier 表の既存 T1 スコープ行から導出される** (Decision 5)、独立リストとしてハードコードされない — よってディテクタの「auth 関連」の概念はちょうどリポジトリが既に宣言した T1 スコープであり、外部権威はない。これが AC-8 を構成上満たし、テンプレート自身の CI を決定論的に保つものである。

### 5. R-04 陳腐化同期 — 単一の真実の源は Tier 表; 契約とディテクタは双方それを参照

Spec R-04 (および Key-interaction 1) は、書面契約と `protocol.md` の T1 スコープ行が静かに乖離できないことを要求する — ADR-012 の Negative が命名した「行が静かに陳腐化する」失敗と同じ。ここで固定される解決:

- **`protocol.md` サブセクション (Decision 2c) は Tier 表と同じファイルに居住し**、T1 スコープ行をポインタで参照する (「上記の Tier 表 T1 スコープ行」)、スコープの語を決して複製しない。T1 スコープ行への将来の修正 (例: 「OAuth flows」追加) は単一の源を変える; サブセクションのポインタは **第二の編集ゼロ** で修正された行に解決し続ける。併設 + 参照 (複製ではない) が構造的反陳腐化保証である — ADR-019 §3 が 80% 閾値を単一の正準行に束縛したのと同じ規律。
- **ディテクタ (Decision 2d) は自身の auth スコープキーワード集合を、実行時に `protocol.md` から Tier 表 T1 スコープ行を読むことで導出する**、スクリプト内に埋め込まれた独立リテラルからではない。抽出が正準 T1 スコープ行を見つけられない場合 (例: フォークが Tier 表を再構成した)、ディテクタは明示メッセージとともに **クローズで失敗** する (「protocol.md Tier 表内に正準 T1 スコープ行が見つからない」)、決して静かに通過しない — ADR-019 §3 が `## Testing Requirements` 欠落ケースに固定したのと同じクローズ失敗方向であり、よって除去された契約は不可視ではなく大声になる。これは抽出器を Tier 表行の形に結合させる; その結合は Consequences → Negative 配下に記録され、単一の正準行に狭められる、ADR-015/ADR-017/ADR-018/ADR-019 が各々その最も狭い面の結合を記録したのと完全に同じく。

実装者は (テストフィクスチャで) 将来の `protocol.md` T1 スコープ修正が契約ポインタとディテクタのランタイム導出キーワード集合の双方により第二の編集なしに自動追跡されることを検証 **しなければならない** — R-04 を構成上閉じる。

### 6. 各受入基準がどう満たされるか

- **AC-1** (auth 内容 ⇒ T1 を強制ルールとして述べ、`orchestrator.md` なしで独立に読める): `protocol.md` サブセクション (Decision 2c)、強制ルールとして文言化、Tier 表に併設、単独で読める。
- **AC-2** (orchestrator ガードレールと補完的、非重複): サブセクションは自身が *書面の、独立チェック可能な* 表現であり、orchestrator ブロック (内容アンカー/訂正済み 103–109 行目で引用) が *ランタイムルーティング* チェックであることを明示する; ディテクタはガードレールのトピックスキャンが見逃すときでも書面ルールを強制する (Decision 2d)。
- **AC-3** (`default_tier: T2` 無変更): Decision 2 は `verification.yml` もデフォルトも編集しない; 実装者は `git diff .claude/verification.yml` (空) で検証する。
- **AC-4** (Tier 表 T1 スコープ行無変更): Decision 2c は表の **下にサブセクションを追記** する; 実装者は Tier 表行そのものが Tier 表行に絞った `git diff` でバイト無変更であることを検証する。
- **AC-5** (orchestrator ガードレール散文無変更): Decision 2 はエージェントプロンプトを編集しない; 実装者は `git diff .claude/agents/orchestrator.md` (空) で検証する。§コンテキストの行範囲訂正は本 ADR の *引用* のみを変え、`orchestrator.md` を決して変えない。
- **AC-6** (既存 5 ディテクタ + スイート無変更): Decision 2 は *新規* スクリプト/ワークフロー/スイートを追加する; 実装者は 5 つの `check-*.sh`、`check-ecc-delegation-consistency.sh`、その `test-check-*.sh` に対する `git diff` が空であることを検証する。
- **AC-7** (MECE 境界、別個の所有された問い): Decision 3 の表とルーティング言明。
- **AC-8** (オペレータ環境イントロスペクション/外部参照なし): Decision 4; ディテクタはリポジトリ内成果物のみを読む。

### 7. 実装セッション契約 (繰延 — 二セッション分割)

実装セッションは、Spec の受入基準と本 ADR の決定に従い、次を行った: `check-*.sh` ファミリースケルトン (`set -euo pipefail`、`git rev-parse` ルート解決、`pass`/`warn`/`fail_check` ヘルパ、`fail=0` アキュムレータ、`exit "$fail"`、行レベル `<!-- ref-allow: -->` エスケープハッチを無修正で再利用、auth→T1 契約・外部イントロスペクションなし制約・R-04 単一源束縛・本 ADR へのポインタ付き七方向 MECE-by-contract 境界を文書化する目立つヘッダ) に従う新規デフォルト無効ディテクタスクリプト `check-research-tier-auth.sh` を作成した; `ecc-delegation-consistency-check.yml` のデフォルト無効単一スイッチ先例に従う 1 つのフォーク可能ワークフロー `research-tier-auth-check.yml` (スタンドアロン、`ci-base.yml` の修正としてではなく **併設して** 作成; `ci-base.yml` バイト無変更; `permissions: contents: read` 最小権限; `timeout-minutes: 5`; `${{ inputs.* }}` を `run:` ブロックに決して挿入しない — すべての動的値は `env:` 経由; 1 つの in-repository アクティベーション設定内の単一 `enabled: true` スイッチ、第二の `if: false` ガードなし、第二の設定キーなし、リポジトリ変数なし); ちょうど 1 つの `enabled` 型ブール値を携えるアクティベーション設定成果物; `protocol.md` Tier 表の下に追記される新規散文サブセクション (Decision 2c、5); 専用 `test-check-research-tier-auth.sh` スイート (フィクスチャ: T2 の auth 内容は用語 + Tier を命名して FAIL; T3 の auth 内容は FAIL; T1 の auth 内容は通過; T2 の非 auth 内容は通過; スイッチオフはジョブを不活性化/テンプレート構成上グリーン; `protocol.md` の正準 T1 スコープ行欠落はクローズで失敗; `protocol.md` T1 スコープ修正は第二の編集なしに追跡され R-04 を閉じる; そして `verification.yml`、`orchestrator.md`、`protocol.md` Tier 表行、既存 5 ディテクタ + スイートがバイト無変更、AC-3/AC-4/AC-5/AC-6)。それは既存 5 ディテクタスクリプトまたはそのスイートへの変更を **ゼロ** 導入した。実装完了時、architect は本 ADR を Proposed → Accepted へ移行し、いまや偽となった現在形「繰延/will」自己叙述を過去形へ調停した (ADR-019/ADR-020 二セッション調停先例)、Alternatives/Counter-proposal の設計時論拠は歴史的記録として無変更で残す。

本 ADR は決定と下流の含意を記録する。それ自身はスクリプト、ワークフロー、アクティベーション設定、`protocol.md` サブセクション、テストを含まず、いかなるエージェントプロンプト、Spec、テンプレート、他の ADR、CHANGELOG、CI/スクリプトファイルも設計セッションでは変更しなかった — 実装は後続の実装セッションへ繰延され、そこで実施され、トレーサビリティのため Consequences → Neutral に列挙される、ADR-014/ADR-015/ADR-016/ADR-017/ADR-018/ADR-019/ADR-020 がそうするのと完全に同じく。これは #03/ADR-016・#05/ADR-017・#06/ADR-018・#12/ADR-019・#13/ADR-020 の二セッション決定後実装分割先例を継続し、単一セッション集約の意図的な **対極** であった。

## 帰結

### ポジティブ

- auth→T1 要件は `protocol.md` 内の **独立チェック可能な書面契約** (`orchestrator.md` なしで読める) **かつ** 決定論的ディテクタになる — Spec の見出しギャップを閉じる: orchestrator のトピックキーワードスキャンが見逃すトピック記述欠落 (「login flow」、「session management」) も依然捕捉される、ディテクタが成果物 *内容* をスキャンするため。
- **orchestrator が唯一の強制点であることをやめる。** auth→T1 ルールの第二の、独立にチェック可能な表現が今や存在する (Spec Goals)、ランタイムガードレールと補完的 (非重複) (AC-2)。
- **単一の真実の源が維持される (R-04 を構成上閉じる)。** 契約サブセクションとディテクタの双方が Tier 表の既存 T1 スコープ行を参照/ランタイム導出する; 将来のスコープ修正は第二の編集ゼロで追跡する — ADR-019 §3 の「成果物からルールを読め、再宣言するな」規律を T1 スコープに適用。
- **`default_tier: T2`、Tier 表、orchestrator ガードレールはバイト無変更** (AC-3/AC-4/AC-5) — #14 は既存機構の上に検証レイヤを追加する、Spec Goals が要求するのと完全に同じく。
- **テンプレートは構成上グリーン** で特例なし: デフォルト無効 (Decision 7) はジョブがテンプレートに対し全く走らないことを意味し、テンプレート自身の検証レビュー成果物 (もしあれば) は構成上適合的である; AC-8 はいかなる外部プローブも禁じるため不活性検出分岐はない。
- **MECE パーティションは明瞭で素である。** #14 は検証レビュー成果物内の *内容 対 宣言 Tier* 関係をスキャンする — 他のディテクタが触れない入力; 七方向境界 (Decision 3) には推論すべき重複ゾーンがない。
- **ディテクタファミリーのレバレッジが新規パターンなしで拡張する。** #14 は #04 が確立し #05/#06/#13 がミラーした `check-*.sh` + `test-check-*.sh` + デフォルト無効ワークフローの形をミラーする — 「1 パターン、N マイルストーン」(ADR-015 §Decision point 3) がもう一度拡張する。

### ネガティブ

- **七番目のディテクタがファミリーの概念的負荷に加わる。** メンテナはもう 1 つパーティションを保持しなければならない。緩和: パーティション (Decision 3) は各所有者がちょうど 1 つの問いに答えるよう引かれる; 免除面は増え **ない** (ディテクタにパス許可リストはない — そのスコープは検証レビュー成果物集合、そのキーワード集合は Tier 表からランタイム導出、列挙されない)。
- **ディテクタは内容キーワードの存在を検証し、意味的意図を検証しない。** Tier 表のスコープ語の外の同義語のみで auth に関わるリサーチ成果物は依然すり抜け得る — ディテクタの再現率はちょうど Tier 表の宣言スコープであり、それ以上広くない (Spec R-03 は新規 T1 カテゴリの発明を禁じる; AC-8 は外部分類器を禁じる)。これは意図的で Spec 境界づけられた限界である: 契約は T1 スコープを *既に存在するまま* カバーし、強制ルールとして適用される、より広い意味的 auth ディテクタではない。常在書面契約 (Decision 2c) が、ディテクタのキーワード再現率を超えて人間/エージェント読者のために義務を担うものである。
- **ディテクタと契約は Tier 表 T1 スコープ行の形に結合する。** Decision 5 はその行を実行時に読む。Tier 表が再構成されると抽出器はそれとともに変わらねばならない; 何も両者を自動相互チェックしない。緩和: 正準行が欠落するとディテクタは **大声でクローズ失敗** する (Decision 5) — ADR-015/ADR-017/ADR-018/ADR-019 が各々受容したのと同じ、許容可能で狭められたクローズ失敗結合、単一の最も狭い面 (1 つの正準行) にキーされる。
- **デフォルト無効はアンコンフィグなフォークが何も強制しないことを意味する。** スイッチを決して反転しない派生リポジトリはディテクタ不活性で出荷する — 受容された `workaround-check.yml`/`coverage-gate.yml`/`ecc-delegation-consistency-check.yml` 性質。コスト非対称は意図方向に走る: アンオプトインなフォークはメンテナの明示的選択である; `protocol.md` 内の書面契約 (常在) はディテクタがオフでも任意の読者にルールを依然述べる。
- **二セッション分割は ADR 番号 1 つとセッション間ハンドオフ 1 つを追加する。** 緩和: ADR-016/017/018/019/020 ライフサイクル先例がハンドオフを既知の低リスクパターンにする; Status ブロックと Decision 7 が実装セッション契約を曖昧さなく記録する。

### ニュートラル

- これは ADR-015/ADR-017/ADR-018/ADR-019/ADR-020 の鋳型の **CI レイヤ + 文書追加** である: エージェントは追加も除去もされない; エージェントプロンプトは変更されない (Spec AC-5 / Key-interaction 3 — orchestrator ガードレール散文は明示的に無変更)。エージェント数無変更。
- これは ADR 自身に述べられた ADR-014 §(d) 事前未予約 MECE パーティションを記録する **三番目** のテンプレートマイルストーンである (#12/ADR-019 と #13/ADR-020 に続く); ADR-014 §(d) 修正としてではなくパターンは今や三度適用され安定である。
- Roadmap 行 #14 の `Design source` セルは本 ADR への `adr:` リンクを得る (本設計セッションが ADR-014 ライト所有権に従い実行: `architect` が `adr:` リンクを追加、既存の予約済み `spec:` リンクの後に `<br>` 結合、行 #03/#04/#05/#06/#12/#13 が示すのと完全に同じく)。行 Status グリフは設計時 `◐ in-progress` である — これは二セッション分割; グリフは実装完了時、ステップ 6 品質ゲートが通過するとき `☑` へ反転する (`product-manager` の反転であり、architect の反転ではない)。他の行は触れられない; Roadmap フォーマット変更なし; 変更はインデックスのみ (単一セル編集)。
- `protocol.md` 内の正確なサブセクション文言、ディテクタの成果物探索グロブ、auth スコープキーワード抽出 awk/grep 形、アクティベーション設定ファイル名と YAML キー名、ワークフロージョブ名、パススコープは `implementer` の詳細である; 本 ADR は *新規 ADR 分類*、*メカニズム形態* ((c)+(d)、(a)/(b) ではない)、*契約配置* (Tier 表の下に併設、複製ではなく参照)、*姿勢* (デフォルト無効単一スイッチ)、*MECE パーティション*、*R-04 単一源束縛* を固定する — bash ではない。ADR-015/016/017/018/019/020 が使った同じニュートラルセクション「制約であって bash ではない」規律。
- 本 ADR の日本語版 (`021-research-tier-auth-validation.ja.md`) は **本同一セッションで** `architect` により作成される (新規 ADR の JA ミラーは architect のものであり、`technical-writer` へ繰延されない)、ADR-019 と ADR-020 の JA 兄弟がその EN 原本とともに生成されたのと完全に同じく; 見出し木パリティ (レベル + 位置) は必須で本セッションで検証される。
- 下流 `implementer` タスクはトレーサビリティのため Decision 7 に記録される; それらは **後続の実装セッションで実行される**、同一セッション実装の意図的な対極。

## カウンタープロポーザル

真剣な対抗ポジションは **代替案 E — ディテクタを追加しない; #14 を文書/規約言明のみ (`protocol.md` サブセクションのみ、スクリプト/ワークフローなし) にし、#11 の散文のみ ADR-014 修正と単一セッション集約をミラーする** である。これは ADR-012 / ADR-014 / ADR-015 / ADR-016 / ADR-017 / ADR-018 / ADR-019 / ADR-020 の、却下された代替案を藁人形ではなく真剣に記録する先例に従いここに記録される。最強の形での論証:

1. **Spec は「文書/規約配置」を明示的 R-01 オプションとして挙げる**、#11 の ADR-014:1800 文書/規約分類に類似 (Spec Key-interaction 4 がまさにこの類推を提起)。auth→T1 義務を命名する `protocol.md` サブセクションは、スクリプトなしで、既に AC-1 (独立に読める)、AC-2 (ガードレールと補完的)、AC-3/AC-4/AC-5 (他は何も変えない) を満たす。それはギャップの *書面契約* 半分を閉じる最小変更である — 七番目のディテクタなし、新規ワークフローなし、アクティベーション設定なし、追加ディテクタファミリー概念的負荷ゼロ (ADR-018 の Negative がまさにその負荷を警告した)。
2. **テンプレートの主要ユーザは学習者である。** Tier 表自身のファイル内の散文義務 (「auth 内容は T1、常に、トピックがどう書かれていようと」) は、学習者がまずその意味論を理解せねばならないグリーン/レッドのディテクタ終了コードよりも、レッスンをより直接的に教え得る。#11 は類似の「ルールを発見可能にする」マイルストーンで意図的に散文のみと単一セッション集約を選び、そこではそれが正しい判断だった。
3. **単一セッション集約 + ADR-014 修正、新規 ADR 番号なし、が保守的デフォルト** であり、最近の #07–#11 ランが確立した。新規 ADR 番号は恒久的な概念的重みを担う; サブセクションで足りるとき鋳造しないのが慎重な選択である。

**なぜ対抗が採用されなかったか:**

- **#11 への類推は決定的点で破れる — 検出可能失敗モード、まさに ADR-020 §Counter-proposal が記録した論理。** #11 は **検出可能失敗モードを持たなかった** (「どの特性下でフォークはドメインを有効化すべきか?」はディテクタがなし得ない判断)、よって散文が唯一の整合的形式だった **かつ** #11 は *ADR-014 §(d) が既に予約したスロットを埋めた*。#14 は **具体的で検出可能な失敗モード** を持つ: 内容が auth に関わりつつ宣言された Tier が T2/T3 である検証レビュー成果物 — まさに Spec §Problem が命名する静かな誤分類。散文サブセクションはそのドリフトを捕捉できない; 静的チェックのみができる。そして #14 は ADR-014 §(d) で **事前予約されない** (Spec Key-interaction 6) — よって #11 類推の修正ビークル半分すら破れる。ディスクリミネータトライアドは 3/3; 構造的半分が ADR-017/018/019/020 が各々記録したのと完全に同じく支配する。
- **散文のみは既に半ば存在するルールを再陳述する; それは *検出* ギャップを閉じない。** Tier 表は *既に* T1 スコープに「auth」を記述的に命名する; 「そしてこれは強制である」と言うサブセクションを追加することは *可読性* を改善する (契約半分、AC-1) が、読者/エージェントは依然 T2 で宣言された成果物を捕捉する決定論的チェックポイントを持たない。Spec §Problem は、ギャップがまさに *orchestrator ランタイム判断とは別個の独立チェック可能な強制の不在* であると明示する — 散文のみは #14 が破るために存在する「散文のみ」状態を再生する。これは ADR-020 が自身の代替案 C に対し到達した「第二の散文言明は検出ギャップを閉じない」結論と同じ。
- **対抗の論点 2 と 3 はファミリーが既に受容した実コストである。** 七番目のディテクタの概念的負荷ともう 1 つの ADR 番号は、ADR-015/017/018/019/020 が *検出可能失敗モードを持つマイルストーンのためにディテクタファミリーパターンが拡張されるたびに* 各々受容したコストである。#14 はそのようなマイルストーンである; #11 はそうでなかった。対抗が正しく評価する発見可能性/学習者半分 **は** 尊重される — 選択された設計は `protocol.md` サブセクションを *含む* (Decision 2c); 対抗は散文が解の中に属すると正しく、散文が解の *全体* だと誤っている。これはまさに ADR-020 §Counter-proposal が取ったポジションである (「散文は解の中に属する; それは解の全体ではない」)。
- **単一セッション集約は実装重量について誤っている。** 選択された設計は新規ディテクタスクリプト、フォーク可能なデフォルト無効ワークフロー、アクティベーション設定、新規 `test-check-*.sh` スイート、**かつ** `protocol.md` サブセクションを出荷する — #12/#13 の重実装プロファイルであり、#11 の散文のみプロファイルではない。二セッション分割 (設計 ADR を今 Proposed; 実装 + Accepted を後) はまさにこの重量のための ADR-016/017/018/019/020 ライフサイクルであり、対抗が提案する #11 集約の意図的な対極である。

**このカウンタープロポーザル再評価のトリガ条件:**

- ADR-014 の §(d) MECE 表が **リサーチ Tier 検証スロットを事前予約** するよう再構成される。その時点で #14 は *事前予約スロットを埋める* ことになり、ADR-014 修正 + 単一セッション集約 — スタンドアロン ADR-021 ではなく — が本 ADR が適用するまさにそのディスクリミネータの下で正しくなる (まさに ADR-019 §Counter-proposal の再評価トリガを、ここで適用)。
- 検証レビュー成果物フォーマットが除去されるかリサーチドメインが完全に退役する (例: レイヤが Generator 宣言型 Tier を落とす)。ディテクタの主題はその時消え、主題存在ルールがディテクタを退役または再分類する — その時点でこの ADR 全体が再評価され、対抗だけではない。
- `check-research-tier-auth.sh` と既存 `check-*.sh` ディテクタが、共有パーシングライブラリ — マージされたスクリプトではなく — をそれら全てがソースするのが正しいリファクタになるほど多くのパーシングコード (Tier 表ウォーキング、フェンス追跡、エスケープハッチ処理) を共有することが判明する、七方向契約パーティションを保ちつつ重複を除去 (ADR-017/ADR-018/ADR-019 がディテクタファミリーに記録したのと同じ共有ライブラリ再評価トリガ)。

カウンタープロポーザルは、ADR-012 / ADR-014 / ADR-015 / ADR-016 / ADR-017 / ADR-018 / ADR-019 / ADR-020 の慣習に従い、決定の最も真剣な異議の歴史的記録として本 ADR に残る。代替 ADR ファイルは作成されない — 却下された対抗の正しい状態は非存在である; この ADR-021 ファイルがその唯一の引用可能な居場所である。
