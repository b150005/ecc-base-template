# ADR-017: Roadmap ドリフト検出 CI — 双方向リンク契約、ステータスグリフ整形式、#04 に対する MECE 境界

## ステータス

Accepted — 2026-05-16

## 背景

Roadmap (`.claude/CLAUDE.md`、ADR-014) はマイルストーンをその権威的な
設計ソースにマッピングする常時読まれる唯一のインデックスである。ADR-014 は
`adr:` ↔ `Roadmap row: #NN` リンクを **双方向** 契約にする: 行の `adr:` セルが
ADR を指名し、その ADR の `## References` が行番号に逆参照する。
ADR-014 §Consequences → Negative はこのギャップを逐語的に指名する ──
「Index↔reality のドリフト … 本 ADR に自動化された強制手段はない。
緩和策は将来の可能な … CI チェックに *委ねられている*」
── そして `specs/05-roadmap-drift-detection-ci.md` がその委ねられた
緩和策である。`specs/05-roadmap-drift-detection-ci.md` が権威的なスコープであり、
本 ADR は Spec が `architect` に明示的に委ねる **構造的** 決定を記録する
(Spec リスク R-01、Key-interaction 4): ディテクターがキーとするドリフトクラス、
#04 ディテクターに対する MECE スコープ境界、そして逆参照のない ADR を
本物にドリフトした ADR と区別する免除キーイングルール。
Spec はこの決定を ADR-017 と指名する。

設計を制約する 3 つのハード制約は交渉不可能である:

1. **CI ポスチャーは継承であり、再決定ではない (Spec R-02)。** ADR-015
   §Decision point 3 は subject-matter-presence ルールによって #05/#06 の
   always-on ポスチャーを固定し、「再議論するのではなく継承する」と述べた。
   本 ADR はポスチャーを **継承** として記録し、再開しない。
   Roadmap 一貫性のドリフトはすべてのフォークに初日から存在する構造的契約であり、
   subject-matter-presence ルールがそれを always-on に置く。
   ここでの追加推論は不要である。
2. **#04 に対する MECE (Spec R-03)。** #04 ディテクター
   (`check-dangling-refs.sh`、ADR-015) は参照の *解決* を所有する。
   本ディテクターは Roadmap *インデックス一貫性* を所有する。
   分割は単一の欠陥がちょうど 1 つのチェックと 1 人のオーナーにマッピングされるように
   引かれなければならない — ADR-015 の Check-4 境界が防止しようとする
   同じドリフトモードである。
3. **ADR-014 インデックスのみおよび予約ルール一貫性。** 本ディテクターは
   #04 の予約カーブアウト (`spec: specs/NN-slug.md` はファイルが存在する前でも
   設計上有効) を複製してはならず、Roadmap テーブルに何も追加してはならず、
   ADR-014 の双方向リンク契約と一貫したまま (ADR-014 を緩和させることなく)
   でなければならない。

4 番目の力は **#04 dangling-reference detector** 自体であり、現在アクティブな
CI である。本 ADR ファイルは #04 ディテクターの Check-1 スコープ内にある。
まだ書かれていない `.claude/meta/scripts/check-roadmap-drift.sh` への
前方参照は Check 2 に該当するが、ADR ファイルは #04 ディテクター自身の文書化された
スコープ決定 (ADR ファイルは歴史的記録であり、`.claude/` ルートのパスは
Check-2 で検証されない) によって除外される。これは明示的な設計インプットとして
扱われ、ADR-015 と ADR-016 がディテクターの相互作用を列挙した方法を踏襲する。

非自明な決定は **免除キーイング** である — 「すべての ADR が Roadmap 行を
持たなければならない」という偽陽性クラスを防ぐルール。これは ADR-015 の
カーブアウトが使う同じ規律で推論する: 免除をパス許可リストではなく、
参照と共存する構造的シグナルにキーイングする。

## 決定

Roadmap ドリフトディテクターは **`.claude/meta/scripts/check-dangling-refs.sh`
(#04) を構造的にモデルとした、`.claude/meta/scripts/check-roadmap-drift.sh`
という単一のリポジトリローカルスクリプト** であり、フォークごとの設定なしに
`main` へのすべての push と pull request で `.github/workflows/roadmap-drift-check.yml`
によって **always-on** で実行される。ディテクターはちょうど 3 つのドリフトクラスに
キーイングし、*契約分割* (解決 vs. 一貫性) によって #04 ディテクターと
MECE 境界を持ち、ADR が **`Roadmap row:` 行を一切持たない場合にのみ**
双方向契約から免除する — 主張の不在はドリフトではなく、
存在する主張が不整合である場合のみがドリフトである。

### 1. スコープ内のドリフトクラス (ディテクターキー可能、正確)

ディテクターは以下のクラスのみで FAIL する:

- **双方向契約の順方向。** `Design source` セルに **ディスク上に存在する**
  ファイルへの `adr:` リンクを持つ Roadmap 行で、その `## References` セクションに
  その行番号に一致する `Roadmap row: #NN` エントリが **ない** もの。
- **双方向契約の逆方向。** `.claude/meta/adr/` 配下の ADR で、`## References`
  セクションに `Roadmap row: #NN` 行を持ちながら Roadmap 行 `#NN` の
  `Design source` セルがその ADR ファイルへの `adr:` リンクを **列挙しない** もの。
- **ステータスグリフ整形式。** Status セルに ADR-014 公認の 4 グリフ
  (`☐` todo / `◐` in-progress / `☑` done / `✗` dropped) 以外の文字を
  含む Roadmap 行。

いかなるカーブアウトもカバーしないため、1 つの狭い一貫性ケースも **FAIL** である:
ディスク上に **存在しない** パスへの Roadmap `adr:` リンク。`spec:` 予約済みリンク
(不在でも設計上有効、#04 の予約カーブアウト) とは異なり、`adr:` リンクは
ADR-014 の書き込みオーナーシップに従い ADR が書かれた瞬間にのみ `architect`
によって追加されるため、存在しない `adr:` ターゲットは設計上有効であることがなく、
常にドリフトである。これは意図的に #04 ディテクターと重複する
(「決定 2」参照)。重複は強いシグナルであり境界違反ではない。
2 つのチェックが同じ症状について異なる問い (「解決するか?」vs.「契約は満たされているか?」)
に答えるからである。

**除外 — 正確な免除ルールで境界付けられた偽陽性生成者:**
「すべての ADR が Roadmap 逆参照を持たなければならない」は **チェックしない**。
ADR 001–013 は Roadmap ドッグフード化より前のものであり、ADR-014 自体が
単一マイルストーンではなく Roadmap *機構のため* の設計決定を記録している。
将来の ADR も単一マイルストーンのない横断的決定を正当に記録するかもしれない。
免除は 1 つの構造的シグナルにキーイングされる: **ADR が `## References`
セクションに `Roadmap row:` 行を一切持たない場合にのみ双方向契約から免除される。**
主張の不在が設計上有効な状態であり、ディテクターは *主張が存在する場合の一貫性*
をキーとし、*主張の普遍性* は決してキーとしない。これは ADR-015 の予約カーブアウト
(「文書化された設計上有効な集合と同じ広さであり、それ以上に広くない」) と
その Reference-intent ルールと同じ絞り込み規律であり、新しいシグナル、
つまりパス形状やファイル不在ではなく主張の存在に適用される。

### 2. #04 の `check-dangling-refs.sh` に対する MECE スコープ境界

分割はファイルタイプではなく **契約** で引かれる (#04↔Check-4 境界は
ファイルタイプ/リンクタイプを使ったが、ここでは両方のチェックが同じファイルを
スキャンするため契約で引く):

| チェック | 問いの所有 | 動詞 |
|---|---|---|
| #04 `check-dangling-refs.sh` | ポインターは実際のファイル/ADR に **解決** するか? | 解決 |
| #05 `check-roadmap-drift.sh` | **双方向インデックス契約** が両方向で保たれているか、すべての Status グリフは整形式か? | 一貫性 |

欠陥はこのルールによってちょうど 1 人のオーナーにマッピングされる: *壊れたポインター*
(ターゲットが存在しない) は #04 のもの。*一貫したポインターだが不整合な契約*
の欠陥 (両方のファイルが存在するが逆参照が欠けているかグリフが非公認) は #05 のもの。
意図的な唯一の重複 — ターゲットファイルが不在の Roadmap `adr:` リンク — は
解決について **#04 が主として所有**し、#05 も FAIL とする。
不在の `adr:` ターゲットは定義上壊れた双方向契約であるからである
(ファイルが存在しなければ逆参照も存在できない)。これは Spec の R-03 緩和策が
述べる「重複は強いシグナル」という推論と同じであり、MECE-by-contract に違反しない:
2 つの失敗が 1 つの症状について 2 つの異なる問い (「解決するか?」vs.
「契約は満たされているか?」) に 2 つの異なる概念オーナーで答えており、
ADR-015 の Check-4 境界が許容するのと同じ方法である。境界は構造的選択であり、
実装詳細ではない — ADR-015 §Decision point 1 が Check-4 分割に適用した
同じ基準である。

この境界は **両方のスクリプトのヘッダーコメントに再記述しなければならない**
(下流タスク) — ADR-015 が Check-4 境界に要求したのと同じ規律であり
(`check-skill-invariants.sh` が相互的なワンライン注記を持つ)、
分割がどちらの側からも発見可能になる。

### 3. CI ポスチャー — ADR-015 から継承、明示的に再議論しない

ディテクターは always-on であり、フォークごとの設定変数や設定ファイルなしに
`.github/workflows/dangling-ref-check.yml` (#04) をモデルとする。
このポスチャーは ADR-015 の subject-matter-presence ルール (§Decision point 3、
#05 を明示的に指名) から **継承** されたものであり、**本 ADR での新しい決定ではない**。
Roadmap インデックス一貫性は Roadmap を保持するすべてのフォークに存在する
構造的契約であり、always-on (`skill-invariants`) カテゴリに属し、
default-off (`workaround-check`) カテゴリには属さない。
ここで新しいポスチャー推論は行わない。ADR-015 自身の「継承、再議論しない」
指示によって再開はスコープ外である。

### 4. パース戦略制約 (構造的要件であり、bash ではない)

Spec の R-01 は制約を `architect` に渡す。
2 つの構造的要件が固定されており、正確な awk/sed/grep の形式は
`implementer` の詳細である (ADR-015/016 が使った中立セクション規律):

- **複数行の `Design source` セル。** Roadmap 行は複数の設計ソースリンクを
  単一の Markdown テーブルセル内で `<br>` で結合する (行 #03/#04 は
  `spec: …<br>adr: …` を持つ)。パーサーは `Design source` セルを
  `<br>` 結合された単位として扱い、その中の *すべての* `adr:` リンクを抽出しなければならず、
  最初または最後の行だけを抽出してはならない。最初の `adr:` トークンで止まる
  行greedy 単一マッチパーサーは 2 つの ADR を持つ将来の行
  (ADR-014 は 1:N を許容) をミスキーし、禁止される。
- **主張の不在にキーイングされた免除、パス許可リストへのキーイング禁止。**
  pre-Roadmap / Roadmap-mechanism 免除 (決定 1) は構造的シグナル
  「この ADR の `## References` に `Roadmap row:` 行がない」から
  スキャン時に ADR ごとに導出されなければならない。
  スクリプト内に免除 ADR ファイル名を列挙することは **禁止** である —
  ADR-015 の amendment が明示的に却下したアドホック許可リスト
  アンチパターンであるからだ (ADR が追加されるにつれてサイレントに open に失敗する。
  ADR ごとのメンテナンスコスト)。免除は成果物のプロパティであり、
  成果物から読み取られる。

本 ADR は決定とエージェント契約/ダウンストリームへの示唆を記録する。
スクリプト、ワークフロー、テストを **自ら書くことはなく**、エージェントプロンプトも
変更しない — 実装は `implementer` に委ねられ、
トレーサビリティのために帰結 → 中立に列挙する。これは ADR-014、ADR-015、
ADR-016 が行うのとまったく同じである。

## 帰結

### ポジティブ

- ADR-014 の双方向リンク契約がゼロオプトインですべての push/PR で
  **両方向** 検証される: 逆参照のない ADR を指名する行、
  それを列挙しない行を逆参照する ADR、どちらも
  エージェントが片側の参照を辿る前に検出される。Spec の主要なギャップが閉じる。
- ステータスグリフ整形式が強制され、ADR-014 が認めた「フォークが手動でテーブルを
  編集すると静かに乖離する。グリフ列を検証するものが何もない」というネガティブな
  帰結がグリフ列について具体的に閉じる。
- MECE-by-contract 境界によりオーナーシップが明確になる: 壊れたポインターは
  #04 のもの。一貫したポインターだが壊れた契約の欠陥は #05 のもの。
  意図的な唯一の重複は強いシグナルであり、2 オーナーの曖昧さではない —
  ADR-015 の Check-4 境界が提供するのと同じプロパティ。
- 免除は **パターンキーの構造的ルール** (逆参照主張の不在) であり、
  保持された許可リストではないため、ADR が追加されても open に失敗せず、
  ADR ごとのメンテナンスコストがない — ADR-015 の amendment が列挙された許可リストより
  選んだのと同じプロパティ。
- インフラストラクチャレバレッジが実現する: #04 が再利用可能なディテクター形状を構築し、
  #05 はパターンなしにそれをミラーする。ADR-015 §Decision point 3 が予測した
  (「1 つのパターン、3 つのマイルストーン」) とおりである。
- ポスチャーはすでに決定済みの監査可能なルールから継承されるため、
  テンプレートは新しいアドホックなポスチャー概念を得ない — ADR-015 と ADR-016 と一致し、
  ポスチャーを再導出するのではなく subject-matter-presence ルールを適用する。

### ネガティブ

- **不在 `adr:` ターゲットケースでの意図的な #04 重複。** 1 つの症状
  (存在しないファイルへの Roadmap `adr:` リンク) が 2 つのチェックから
  2 つの CI 失敗を生じる。これは強いシグナルとして受け入れられる (Spec R-03) が、
  メンテナーは 1 つの症状に対してなぜ 2 つのチェックが発火するかを理解するために
  契約分割を知る必要がある。緩和策: 境界は両方のスクリプトヘッダーに文書化され
  (下流タスク) どちらの側からも発見可能になる。
- **ディテクターが ADR-014 のテーブル形式と逆参照文字列に結合する。**
  パーサーは `<br>` 結合の `Design source` セル形状とリテラルの `Roadmap row: #NN`
  逆参照トークンに依存する。ADR-014 のテーブル形式や逆参照規約が変更された場合、
  パーサーも変更しなければならず、2 つを自動的に相互チェックするものはない。
  これは ADR-015 の予約カーブアウト (ADR-014 の `specs/NN-slug.md` 形状にキーイング)
  と ADR-016 のパスキー (行番号にキーイング) が引き受けた同じ許容可能な結合であり、
  最も狭いサーフェス (Roadmap テーブルと逆参照行のみ) に絞られた
  既知のメンテナンスエッジとして記録する。
- **4 番目の原則的カーブアウトがディテクターファミリーの概念的負荷に加わる。**
  テンプレートは今や #04 の予約カーブアウト、#04 の Reference-intent (オプトイン設定 WARN)
  ルール、Class-A プレースホルダースキップ、そして #05 の主張不在免除を持つ。
  メンテナーは 2 つのディテクターにわたって 4 つの免除概念を保持しなければならない。
  それぞれは 1 つの反証可能な文、パターンキー、ヘッダー文書化 (下流タスク) であるため、
  サーフェスは発見可能だが、負荷が 1 ルール増加した。緩和策: 免除はここに
  1 文で述べられているため、#06 が (もし類似のルールが必要であれば) 規律
  (co-located な構造的シグナルにキーイングし、許可リストにしない) を継承し、
  再導出しない。
- **Always-on はリポジトリ全体の CI を偽陽性でブロックすることを意味する。**
  ADR-015 のポスチャーとその受け入れられた緩和策から継承: 行レベルの
  `<!-- ref-allow: -->` エスケープハッチ (本ディテクターが変更なしに再利用、
  Spec 受け入れ基準) が前方参照を行ごとに吸収する。スコープは Roadmap と
  ADR ツリーにパス制限される。コスト非対称性は ADR-015 が受け入れたものと同じ —
  見逃されたドリフトはすべてのセッションで Roadmap を読むすべてのエージェントを誤解させ、
  偽陽性は 1 つの抑制コメントのコストを払う。

### 中立

- これは ADR-015 モールドの **CI レイヤー追加** である: エージェントは
  追加も削除もされない。Spec はエージェントプロンプトの変更が
  本マイルストーンで不要と述べている。エージェント数は変わらない。
- Roadmap 行 #05 の `Design source` セルは本 ADR への `adr:` リンクを得る
  (ADR-014 の書き込みオーナーシップに従い本変更が実施: `architect` が
  `adr:` リンクを追加し、行 #03/#04 が示すとおり既存の予約済み `spec:` リンクの後に
  `<br>` で結合する)。他の行には触れない。Roadmap フォーマットの変更なし。
- 正確な awk/sed/grep パース形式、`<br>` 分割メカニクス、ゼロパディング/`#NN` 正規化、
  ヘッダーコメントの文言は `implementer` の詳細である。本 ADR は
  *カテゴリ化、キーイング、境界制約* を固定し、bash は固定しない —
  ADR-015 と ADR-016 が使った同じ中立セクション規律。
- 下流の `implementer` タスク (トレーサビリティのために記録。
  **本 ADR では実施しない** — 実装は将来のセッション):
  - `.claude/meta/scripts/check-roadmap-drift.sh` — `check-dangling-refs.sh`
    の構造に従い作成する (`set -euo pipefail`、`git rev-parse` ルート解決、
    `pass`/`warn`/`fail_check` ヘルパー、`fail=0` アキュムレーター、`exit "$fail"`、
    行レベルの `<!-- ref-allow: -->` エスケープハッチを変更なしに再利用)。
    (a) 3 つのドリフトクラス、(b) 「`Roadmap row:` 行なし」にキーイングされた
    主張不在免除、(c) `check-dangling-refs.sh` に対する MECE-by-contract 境界、
    本 ADR へのワンラインポインターを文書化する目立つヘッダーブロックを含める。
  - `.github/workflows/roadmap-drift-check.yml` — `dangling-ref-check.yml` の
    構造に従い作成する: always-on、`.claude/CLAUDE.md`、`.claude/meta/adr/`、
    スクリプトとワークフロー自体にパス指定した `main` への
    `on: push/pull_request`、`bash .claude/meta/scripts/check-roadmap-drift.sh`
    を実行する単一 `check` ジョブ、`permissions: contents: read`、
    `timeout-minutes: 5`、ジョブ名 `roadmap-drift-check`。

## 反対提案

深刻な反対立場は **代替案 A ── 別個のディテクターを追加しない。
`check-dangling-refs.sh` (#04) を拡張して Roadmap 双方向一貫性と
ステータスグリフ整形式も検証し、1 スクリプト 1 ワークフローにする** である。
ADR-012 / ADR-014 / ADR-015 / ADR-016 の先例 ── strawman としてではなく
却下された代替案を真剣に扱う ── に従いここに記録する。
これは ADR-015 の Alternative C (新しいディテクターを既存のものに折り込む)
の直接類似である。論点:

1. 1 つのスクリプト、1 つのワークフロー、1 人のオーナーが最も単純な構造である。
   #04 ディテクターはすでに CLAUDE.md と ADR ファイルをパースし、
   `<!-- ref-allow: -->` エスケープハッチを持ち、Roadmap の `adr:`/`spec:` セルを
   解決する — 「逆参照が相互的かも検証する」を追加するのは同じファイルを
   既に走る数個の関数にすぎない。
2. 本 ADR が受け入れる意図的な唯一の重複 (欠けているファイルへの Roadmap `adr:`
   リンクが #04 と #05 の両方で FAIL) が 1 つのスクリプトの下で **消える**:
   1 つの症状、1 つの失敗、「なぜ 2 つのチェックが発火したか?」混乱なし。
   マージすることで本 ADR が積極的に守る唯一のネガティブを取り除く。
3. Spec の R-03 はすでに重複が「狭く」「許容可能」と認める。
   重複が許容可能であれば、それを完全に除去するより単純な構造が
   より複雑な構造より好ましいと言える。

**反対提案が採用されなかった理由:**

- 決定的な問題は **2 つの契約、2 つのファイルセットではない** ことである。
  ADR-015 の Check-4 境界はファイルタイプ/リンクタイプで分割した。
  なぜなら契約が異なるファイルにあったからである。ここでは両方のチェックが
  同じファイル (CLAUDE.md、ADR) をスキャンするため、分割は *契約* で行わなければならない:
  参照の *解決* (ポインターが解決するか) vs. インデックスの *一貫性*
  (双方向契約が保たれているか、すべてのグリフが公認か)。
  折り込むことで解決の失敗と一貫性の失敗がジョブレベルで区別不能になる —
  ADR-015 §Decision point 1 が Check-4 ケースで却下した「どの契約が失敗したか?」
  の曖昧さをまさに同じ成果物で再現する。2 つのチェックは異なる概念オーナーを持つ
  (#04 ディテクターは「ポインターが実在する」を所有し、本ディテクターは
  「インデックスが自己整合する」を所有する)。1 つのジョブが両方を報告すると
  そのオーナーシップが消える。
- Spec は #05 を **別個のディテクター** としてスコープする (Key-interaction 1–2:
  #04 ファイルに従うのではなく、それを拡張するのでもなく、`check-roadmap-drift.sh`
  と `roadmap-drift-check.yml` を作成する) そして Non-goals が #04 の
  散文パス/ADR 参照解決は *本ディテクターのスコープではない* と明示する。
  マージすることで Spec が分離したものをまさに再混在させることになる。
- 反対提案が取り除く重複は **意図的で安価**: 1 つの不在 `adr:` ターゲット症状が
  2 つの失敗を生じることは強いシグナル (Spec R-03) であり欠陥ではない。
  コストは 2 つのスクリプトヘッダーの 1 文書化された文のみ。
  2 契約の過負荷なスクリプト (その後 #06 も折り込まれることになる) という
  はるかに大きなコストを払って安価でシグナルポジティブな重複を取り除くのは
  間違った trade-off である — ADR-012 が dispatcher に適用し
  ADR-015 が Alternative C に適用したのと同じ locality-of-behavior の価値。

**この反対提案を再評価するトリガー条件:**

- #04 と #05 ディテクターが同じ Roadmap テーブルのパーサーを多く共有し、
  複製コスト (同じテーブルの 2 つのパーサー) が契約分離の利益を超えることが
  判明した場合 — この時点では両方のスクリプトがソースする *共有パースライブラリ*
  (マージされたスクリプトではない) が正しいリファクタリングとなり、
  複製を取り除きながら契約分割を保持する。
- ADR-014 のテーブル形式が変化し、解決と一貫性が Roadmap 上で意味的に
  分離できなくなった場合 (例: 「解決する」と「一貫している」が同じ述語になる形に
  インデックスが崩壊する)、2 契約の前提が取り除かれる。
- #06 (bilingual パリティ) が設計され、同じ *契約* (双方向マッピングの一貫性) を
  #05 と十分に共有することが判明し、3 つのサブチェックを持つ 1 つの一貫性
  ディテクターが 3 つのスクリプトより凝集性が高い場合 — デフォルトではなく
  意図的な再評価ポイント。

反対提案は ADR-012 / ADR-014 / ADR-015 / ADR-016 の規約に従い、
決定の最も深刻な異議の歴史的記録として本 ADR に残る。
