# ADR-020: ECC 不在時の劣化レビューシグナル — `code-reviewer.md` の ECC 委譲テーブル内部整合性を検証する新規 default-off ディテクター、オペレーター環境イントロスペクションなし、ADR-014 §(d) が事前予約しない新しい MECE 分割

## ステータス

Proposed — 2026-05-18

## 背景

ADR-012 は `.claude/agents/code-reviewer.md` を、9 行の `manifest → ECC reviewer` 委譲テーブルを介して言語固有の深さを ECC の `*-reviewer` エージェントに委譲するメタレビュアーにした。ADR-012 の Negative セクションは、未対処として残した 2 つのコストを明示的に記録している。(1)「ECC を決してインストールしないフォークは恒久的に低いレビュー品質で運用される」、(2)「ECC レビュアーとの契約は **バージョン管理されていない**。ECC が `typescript-reviewer` をリネームしたりプロンプト契約を大幅に変更したりすると、ディスパッチャーの委譲行はサイレントに陳腐化する。**ターゲットエージェントの存在を確認する CI チェックは存在しない**」。

現在、唯一の ECC 不在 / 劣化レビューシグナルは、`code-reviewer.md` 内のレビューごとの verdict 行ノート(3 ケース委譲ルール、66〜87 行、レビューが実際に実行されたときのみ発火)と、`README.md` の `## Prerequisites` 内の 1 つの静的散文段落(README を閲覧する人間が読むのみで、いかなるエージェント/CI チェックポイントにも表出しない)である。委譲テーブルの *standing*(常在)劣化レビューポスチャーと *内部整合性* は、いかなる決定論的かつ非レビュー時のチェックポイントでも観測できない。

`specs/13-ecc-absent-signal.md` が信頼できるスコープであり、その 8 つの受け入れ基準、3 つのリスク、Non-goals がそれである。この ADR は、Spec が `architect` に明示的に委ねた **構造的** 決定(Spec Risk R-01 (a)〜(d)、Key-interaction 6)を記録する。すなわち、シグナル機構、その配置、オペレーター環境イントロスペクションなし契約、期待される不在に対するテンプレート CI グリーン契約、MECE 境界、新規 ADR か ADR-012 amendment かの決定である。Spec はこの決定を ADR-020 と命名し、ADR-018 Alternative-B ディスクリミネーターを architect に逐語的に委ねている。この ADR がそれを締結する。

このマイルストーンは未分化のディテクター集積の 6 番目の構成員 **ではない**。#04 (`check-dangling-refs.sh`、ADR-015) はクロスリファレンス *解決* を所有する。#05 (`check-roadmap-drift.sh`、ADR-017) は Roadmap *インデックス整合性* を所有する。#06 (`check-bilingual-parity.sh`、ADR-018) は EN↔JA 構造的パリティを所有する。#12 (`coverage-gate.yml`、ADR-019) は *カバレッジしきい値* の問いを所有する。それらのいずれも「`code-reviewer.md` の ECC 委譲テーブルは内部的に整合しているか、そして常在の劣化レビューポスチャーはレビューを先に実行せずとも発見可能か」という問いを所有しない。ADR-014 §(d) の MECE テーブルは #04/#05/#09/#10/#11 を名指し(ADR-019 の論証により #12 向けに修正済み)、#13 のスロットを事前予約 **していない** — ADR-019 §5 が #12 に対して引いたのと同じ実質的区別である。

これは **2 セッション分割** である(重実装マイルストーンに対する ADR-016/017/018/019 ライフサイクル先例)。本セッションは設計(ADR-020 Proposed、Spec Approved)を `docs(adr-020):` コミットとして出荷する。実装(ディテクタースクリプト、そのワークフロー、そのテストスイート)は後続セッションに `feat(roadmap):` コミットとして繰り越される。実装は実施されていない。ステータスは Proposed である。対照的な先例は #11(ADR-014 amendment、散文のみ、単一セッション collapse)であり、#13 の構造的重量は #11 ではなく #12 に一致する。

## 決定

#13 を **新規 ADR-020**(ADR-012 amendment ではない)として解決し、実装セッションにおいて、`code-reviewer.md` の ECC 委譲テーブル内部整合性を検証する **新規 default-off ディテクタースクリプトとフォーク可能ワークフロー** を、**オペレーター環境イントロスペクションをゼロ** とし、**関連チェックポイントが既に参照するアーティファクトに併置された常在ポスチャーステートメント** とともに出荷する。具体的には:

### 1. 新規 ADR か ADR-012 amendment か — ADR-018 Alternative-B ディスクリミネーター、句ごとの適用

Spec の R-01 (b) は `architect` に「新規 ADR-020 か ADR-012 amendment か」の明示的選択を委ね、ADR-018 の Alternative-B ディスクリミネーターを逐語的に適用するよう指示する。すなわち、*#13 は新規ディテクター + 新規 MECE 契約境界 + 新規キーイング/機構を導入するか(⇒ 新規 ADR)、それとも既存 ADR の既に承認された決定の帰結明確化/拡張か(⇒ amendment)か?* 誠実に句ごとに適用すると:

- **新規ディテクターか? Yes。** #13 の最も価値の高い実現形は、決定論的な非レビュー時チェックポイントで委譲テーブルの内部整合性をチェックする新規静的解析スクリプト + フォーク可能ワークフローである。ADR-017 と ADR-018 はそれぞれ、新規スクリプト + 新規ワークフロー(`check-roadmap-drift.sh` / `check-bilingual-parity.sh`)を導入した *がゆえに* 新規 ADR 相当と自己分類した。ADR-019 は `coverage-gate.yml` に対して同じことを行った。#13 は新規スクリプト 1 つと新規ワークフロー 1 つを導入する。ADR-017/ADR-018/ADR-019 で支配的だった構造的半分がここに存在する。
- **新規 MECE 契約境界か? Yes — ADR-014 §(d) が事前予約しない新しい分割。** #13 は「`code-reviewer.md` の ECC 委譲テーブルは内部的に整合しているか、そして常在の劣化レビューポスチャーは発見可能か」という問いを所有する。§2 が示すとおり既存のいかなる所有者もこれを保持しない。ADR-014 §(d) のテーブルは #04/#05/#09/#10/#11 を名指す(#12 向けに修正済み)。それは #13 を事前予約しない。これは ADR-019 §5 が #12 に対して記録した同じ非事前予約スロットの観察であり、形式ではなく実質的区別である。新しい分割は ADR-017/ADR-018/ADR-019 のトリガーである。
- **新規キーイング/機構か? Yes。** キーイングは「*エージェントプロンプト内部の* クロスリファレンス整合性 — 委譲テーブル行の ECC エージェント名と `code-reviewer.md` 自身のディスパッチャー契約との照合 — をリポジトリ外の何も読まずに検証する」である。これは ADR-015 のパス解決キーイング、ADR-017 の主張不在キーイング、ADR-018 の規約存在キーイング、ADR-019 のカバレッジパーセンテージキーイングのいずれでもない。オペレーター環境イントロスペクションなし制約(Spec AC-5、`code-reviewer.md` 84〜87 行はナイーブな読みが要求する信頼できないランタイムイントロスペクションを禁止する)が定義的な新機構である。#13 は *内部整合性と常在ポスチャー* をチェックし、決して *ライブ ECC 存在* をチェックしない。

3 つの句すべてが充足される。ADR-017/ADR-018/ADR-019 とまったく同様に構造的半分が支配する。ADR-012 amendment は **却下** される。ADR-012 の決定(ディスパッチャーリファクタ + 3 ケースルール)は #13 によって *不変* である(Spec Non-goals がこれを固定する)。#13 は ADR-012 が *記録したが意図的に未対処として残した* コストを締結する — これは ADR-017/ADR-018 が「新規ディテクター + 新規境界 + 継承可能ルール」として新規 ADR と自己分類した形態であり、既存決定の帰結明確化ではない。

### 2. MECE 境界 — ADR-014 §(d) が事前予約しない新しい分割

#13/ADR-020 は **「`code-reviewer.md` の ECC 委譲テーブルは内部的に整合しているか、そして常在の劣化レビューポスチャーはレビューを先に実行せずとも発見可能か」** という問いを所有する。これは **新しい分割** であり、既存のすべての所有される問いと区別される。

| 所有者 | 所有する問い | スキャン対象入力 |
|---|---|---|
| #04 `check-dangling-refs.sh` (ADR-015) | 散文/パス参照は実在ファイル/ADR に **解決** するか? | リポジトリの Markdown アーティファクト |
| #05 `check-roadmap-drift.sh` (ADR-017) | **双方向 Roadmap インデックス契約** は成立し、すべてのステータスグリフは整形式か? | `.claude/CLAUDE.md` + ADR |
| #06 `check-bilingual-parity.sh` (ADR-018) | **EN↔JA ペアは構造的に一致** するか(見出しツリー、全角括弧、存在)? | ペアの `.md`/`.ja.md` アーティファクト |
| #11 (検証ドメインオプトインガイダンス、ADR-014 §(d)) | どのプロジェクト特性下でフォークは implementation/design 検証ドメインを **有効化** すべきか? | ドキュメント/規約(ディテクターなし) |
| #12 `coverage-gate.yml` (ADR-019) | プロジェクトの **テストカバレッジ** は CI 時に強制される 80% 最小値を満たすか? | 派生リポの既に計算済みのカバレッジパーセンテージ |
| **#13 `<#13 ディテクター>` (ADR-020)** | **`code-reviewer.md` の ECC 委譲テーブルは内部的に整合しているか、そして常在の劣化レビューポスチャーは発見可能か?** | **`code-reviewer.md` の委譲テーブル — リポジトリ内部のみ、オペレーター環境プローブなし** |

欠陥はちょうど 1 つの所有者にマップされる。*壊れたポインター* は #04 のもの。*Roadmap インデックス不整合* は #05 のもの。*構造的に乖離した EN/JA ペア* は #06 のもの。*検証ドメイン有効化ガイダンスの問い* は #11 のドキュメント上の関心事。*CI 時のしきい値未満カバレッジ* は #12 のもの。*委譲テーブル内部不整合または発見不能な劣化レビューポスチャー* は #13 の、そして **#13 のみ** のものである。境界はクリーンである。#13 はカバレッジを決してスキャンせず、任意のポインターを決して解決せず(特定の 1 テーブルの内部整合性を検証する)、EN/JA パリティに決して触れず、そして — 決定的に — ECC 存在についてオペレーター環境を決してプローブしない(それはリポジトリ/CI から構成的に不可能であり、`code-reviewer.md` 66〜87 行が既に所有するレビューごとのランタイムシグナルに対する境界である)。

### 3. オペレーター環境イントロスペクションなし — 定義的制約

シグナルは *内部整合性* を検証し *常在ポスチャー* を述べる。それは決して ECC がオペレーターの `~/.claude/` にインストールされているかを検出しようとしてはならない — その検出はリポジトリおよび CI から構成的に信頼できる形で不可能であり、`code-reviewer.md` 84〜87 行はそれが要求する信頼できないランタイムイントロスペクションを明示的に禁止する(「エージェントはファイルシステムをイントロスペクトしない … 疑わしいときはデフォルトでケース 3 を選ぶ」)。ディテクターはリポジトリアーティファクト(主に `code-reviewer.md`)のみを読む。これがテンプレート自身の CI を期待される通常の ECC 不在リポジトリ内条件に対してグリーンに保つもの(Spec AC-3)である。ディテクターは「ECC はここにあるか?」(リポ内では常に「いいえ」)を問うのではなく、「委譲テーブルは自己整合しているか?」(リポジトリローカルで安定した答えを持つ問い)を問う。

### 4. 期待される ECC 不在ケースに対するテンプレート CI グリーン

§3 がディテクターをリポジトリ内部整合性チェックにするため、それは特別扱いなしにテンプレート自身の `main` でパスする。委譲テーブルはテンプレート内で整合しているのでディテクターはグリーンであり、ECC のリポ内不在はディテクターが測定するものに無関係である。これは #12/ADR-019 先例(期待される条件に対してテンプレート自身の CI を失敗させないゲート)を、カバレッジゲートではなく整合性ディテクターに適用したものである。

### 5. 常在ポスチャー配置 — 併置、新規 always-read ファイルなし

常在劣化レビューポスチャーステートメントは、関連チェックポイントが既に参照するアーティファクト(ディテクター自身の出力および/または `code-reviewer.md` / `README.md` `## Prerequisites`、正確な文言は実装詳細)に併置されるので、フォーク保守者またはエージェントは、そのチェックポイントが既に義務付けるものを超える新規 always-read ファイルや 3 つ目のルックアップなしにそれに遭遇する(Spec AC-7)。それはレビューごとの 3 ケースルールを補完する — 再陳述しない(Spec AC-2、Key-interaction 1)。

### 6. 実装セッション契約(繰り越し)

実装セッションは、Spec の受け入れ基準とこの ADR の決定に従い、次を行わねばならない。新規 default-off ディテクタースクリプト 1 つ(#04 が確立し #05/#06 がミラーした `check-*.sh` ファミリー形態)+ フォーク可能ワークフロー 1 つを作成する。`test-check-*.sh` 先例をミラーする専用テストスイートを追加する(分離実行スイート数を 5 にする)。4 つの既存ディテクタースクリプトまたはそのテストスイートへの変更を **ゼロ** 導入する(Spec Non-goals)。`code-reviewer.md` の 3 ケースルールと「疑わしいときはデフォルトでケース 3」ポスチャーをバイト不変に保つ(Spec AC-6)。ディテクターの機構をリポジトリ外の読み取りから一切自由に保つ(Spec AC-5、上記 §3)。実装完了時、architect はこの ADR を Proposed → Accepted に遷移し、now-false な現在形「未実装」自己叙述を過去形に reconcile する(ADR-017/ADR-019 の 2 セッション reconciliation 先例)。代替案/反対提案の設計時論拠は履歴記録として不変のまま残す。

## 帰結

### ポジティブ

- ADR-012 が記録したが未対処の「ターゲットエージェントの存在を確認する CI チェックは存在しない」/「委譲行はサイレントに陳腐化する」コストが、決定論的かつ非レビュー時のシグナルによって締結される — ADR-012 の Negative が名指し、未対処で残した正確なギャップである。
- 劣化レビューポスチャーが、それがアクション可能なチェックポイント(採用 / CI)で発見可能になる。レビュー後 verdict 行やどのエージェントも読まない README 段落に埋もれるのみではなくなる。
- ディテクターファミリーの「1 パターン、N マイルストーン」レバレッジ(ADR-015 §Decision point 3、#06 まで完了、#12 で再利用)が新パターンなしにもう一度拡張される。#13 は `check-*.sh` + `test-check-*.sh` 形態をミラーする。
- MECE 分割がクリーンかつ曖昧でないまま保たれる。スコープをルーティングする将来のマイルストーン作者は、マップすべき 6 番目の鋭く境界付けられた所有者を持つ。

### ネガティブ

- 6 番目のディテクターがファミリーの概念的負荷に加わる。緩和策: 分割(§2)は各所有者がちょうど 1 つの問いに答えるよう引かれる。免除サーフェスは増大しない(ディテクターには allowlist がない — 1 テーブルの内部整合性をチェックする)。
- ディテクターは *ライブ ECC 存在* ではなく *内部整合性* を検証する。完全に整合した委譲テーブルを持つが ECC がインストールされていないフォークは依然グリーンディテクターを得る — そのフォークに劣化していると伝えるのは、ディテクターの終了コードではなく常在ポスチャーステートメント(§5)である。これは意図的な境界(§3)である。ライブ存在は構成的に検出不能であり、両者を混同すると `code-reviewer.md` が禁止する信頼できないイントロスペクションを再現する。
- 2 セッション分割は ADR 番号 1 つとクロスセッションハンドオフ 1 つを加える。緩和策: ADR-016/017/018/019 ライフサイクル先例がハンドオフを既知の低リスクパターンにする。ステータスブロックと §6 が実装セッションの契約を曖昧でなく記録する。

### 中立

- `code-reviewer.md` の 3 ケースルールと ADR-012 の決定は手付かずである。能力はそれらの傍らに加わり、何も再編成されない。
- これは ADR-014 §(d) が事前予約しない MECE 分割をその ADR が記録する 2 番目のテンプレートマイルストーン(#12/ADR-019 に続く)である。分割を ADR 自身に述べる(ADR-014 §(d) を修正するのではなく)パターンは今や 2 回適用され安定している。
- 実装は繰り越される。スクリプト、ワークフロー、テストスイートはまだ存在しない。ステータスは Proposed であり、実装セッションで Accepted に移行する。

## 反対提案

真剣な反対ポジションは **代替案 C — ディテクターを追加しない。#13 を #11 の散文のみ ADR-014 amendment をミラーしてドキュメント/規約ステートメントのみにする** である。これは ADR-012 / ADR-014 / ADR-015 / ADR-016 / ADR-017 / ADR-018 / ADR-019 の、却下された代替案をストローマンとしてではなく真剣に扱う先例に従いここに記録される。論証:

1. #13 自身の Spec は R-01 で「ドキュメント/規約ステートメント」を明示的オプションとして列挙する。ADR-012 は既に劣化ポスチャーを `README.md` `## Prerequisites` に述べる。#13 の最も安価な読みは「そのステートメントをより発見可能にする」 — 純粋な散文、新規スクリプトなし、新規ワークフローなし、保守すべき 6 番目のディテクターなし。これはまさに #11 が取った形態(ADR-014 amendment、新規 ADR 番号なし)であり、#11 は採用ガイダンスにとって正しい判断だった。
2. ディテクターファミリーの概念的負荷は実在する。ADR-018 自身の Negative は「保守者はディテクター横断で N 個の免除概念を保持せねばならない」と警告した。6 番目のディテクターはその負荷に加わる。散文ステートメントはディテクターをゼロ加える。
3. テンプレートの主要ユーザーは学習者である。「ECC なしであなたのレビューは劣化する。理由とすべきことはこうだ」と述べる散文ステートメントは、セマンティクス(「内部整合性、ライブ存在ではない」)を学習者が先に理解せねばならない緑/赤ディテクター終了コードよりも、レッスンをより直接的に教えるかもしれない。

この反対提案は **不採用** である。なぜなら #11 への類推が 1 つの決定的点で破綻するからである。#11 は **検出可能な失敗モードがなかった** — 「どの特性下でフォークはドメインを有効化すべきか?」はディテクターが下せない判断であり、散文が唯一のコヒーレントな形態だった。#13 は **具体的に検出可能な失敗モード** を持つ。委譲テーブル行のうち ECC エージェント名が `code-reviewer.md` 自身の契約と不整合に乖離したもの — まさに ADR-012 の Negative が名指した「行はサイレントに陳腐化する」失敗である。散文段落は乖離した行を捕捉できない。静的チェックのみがそれを行える。ADR-012 は *既に* 散文ステートメント(README `## Prerequisites`)を持つ。2 番目の散文ステートメントを追加しても *検出* ギャップを締結しない — それは既に述べられたものを再陳述する。反対提案の点 2 と 3 は実在するコストだが、それらは ADR-015/ADR-017/ADR-018/ADR-019 が検出可能な失敗モードを持つマイルストーンのためにディテクターファミリーパターンを拡張するたびに既に受け入れたコストである。#13 はそのようなマイルストーンであり #11 はそうでなかった。#13 のポスチャー半分(発見可能性)*は* 併置ステートメント(§5)によって扱われる — 反対提案は散文が解決策に属する点で正しい。散文が解決策の *全体* である点で誤っている。
