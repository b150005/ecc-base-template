# ADR-016: セッション間マイルストーン進捗永続化 — リポジトリローカル、行キー、境界トリガー

## ステータス

Accepted — 2026-05-16

## 背景

Roadmap (`.claude/CLAUDE.md`、ADR-014) はマイルストーンの
*実装状態* を 4 つのグリフ (☐ / ◐ / ☑ / ✗) のいずれかで記録する。
`◐ in-progress` の行が示すのは「作業が開始された」という事実のみであり、
開発ワークフローの 9 ステップのうちどこまで完了しているか、
どの成果物がディスク上に存在するか、次の具体的なアクションは何か、
あるいはなぜ作業が止まったかは示さない。
非自明な長さのマイルストーンがセッションまたはコンパクション境界をまたぐと、
再開するオペレーターやエージェントは `git log`、`specs/` スキャン、
ワークフローの再トレースからこれらをすべて再導出しなければならない
── コンテキスト予算が再発見に消費され、再導出エラーのリスク
(「次のステップ」の誤認、完了済みアクションの重複実行) が生じる。
`specs/03-cross-session-progress-persistence.md`
が権威的なスコープであり、本 ADR は Spec が `architect` に委ねた 4 つの
**構造的** 決定を記録する: ストレージ場所とパス規約、トリガーモデル、
陳腐化認識、完了時のリタイアメント ── さらに既存のセッション機構との
関係 (Spec US-004) を記録する。

設計を制約する 3 つのハード制約は交渉不可能である:

1. **ADR-014 インデックスのみ (Spec R-02)。** 進捗詳細を
   Roadmap テーブル、Roadmap 列、またはテーブル形式への追加として
   入れてはならない。グリフが Roadmap が持つ唯一の実装状態トークンであり続ける。
   進捗レコードは Roadmap の *外側* に置く。
2. **Invariant 2 コンパクション耐久性 (Spec R-01)。** Claude の
   コンテキストのみに保持された進捗レコード ── またはコンパクションが
   要約してしまうサブディレクトリの `CLAUDE.md`
   (`.claude/skills/claude-md-authoring/invariants.md` §2) ──
   はコンパクション境界を越えると失われる。ディスク上の *ファイル*
   はコンパクションの影響を受けない (コンパクションは Claude の
   ワーキングメモリを破棄するのであり、ファイルシステムではない)。
   レコードはディスク上に存在し、かつファイルシステム検索なしに
   発見できる決定論的パスに置かれなければならない。
3. **既存のセッション機構との組み合わせ可能性 (Spec R-05 /
   US-004)。** グローバルな `/save-session` ↔ `/resume-session`
   コマンドはすでに存在する (ユーザーホーム `~/.claude/session-data/`、
   プロジェクト非依存、セッション単位)。新しいマイルストーン単位の
   機構はこれを補完しなければならず、競合する並列規約を導入してはならない。
   リポジトリ grep により **リポジトリ内に `ECC:SUMMARY` ブロックが存在しない**
   ことが確認されている: 既存のセッションサマリーサーフェスはユーザーホームの
   ものだけである。2 つのスコープはクリーンに非重複でなければならない。

4 番目の力は **#04 dangling-reference ディテクター** であり、
現在アクティブな CI である (`check-dangling-refs.sh`、ADR-015)。
このディテクターは `CLAUDE.md`、`.claude/meta/adr/*.md`、`specs/*.md`、
`.claude/agents/*.md` をスキャンする。本 ADR が導入するストレージパスは、
一貫してすでにスコープされたツリーの内側に収まるか、
新たな dangling-reference の偽陽性を生み出してはならない。
これは事後の考慮ではなく明示的な設計インプットとして扱う
(ADR-015 がディテクターの相互作用を列挙した方法を踏襲)。

トリガーモデルの決定は非自明であり、ADR-015 の
**主題存在性ルール** を通じて推論する: ある機構はその主題が
初日からすべてのフォークに存在する場合は常時有効であり、
その主題が特定の状況が生じるまで存在しないか無関係である場合は
必要時トリガー / オプトインである。そのルールは CI ポスチャーのために
確立されたが、ここでも直接適用される。

## 決定

マイルストーン単位の in-progress レコードは、**`specs/NN-progress.md`
という決定論的パスに置かれる単一のリポジトリローカル Markdown ファイル**
であり、`NN` は安定していて再利用されない Roadmap 行番号
(ADR-014 の予約ルールが `specs/NN-slug.md` に使う同じイミュータブルキー)
である。これは **マイルストーンが `◐ in-progress` の間にセッションまたは
コンパクション境界が発生した場合にのみ作成/更新され**
(Spec の製品優先オプション b)、☐→◐ のステータス遷移時には作成されず、
オペレーターコマンドによっても作成されない。行を **☑ done** にフリップする
エージェントが完了を記録する同じ変更の中で **削除する**。
精密に引かれたスコープ境界を持ちつつ `/save-session` と
**並行して動作する**。

### 1. ストレージ場所とパス規約

`specs/NN-progress.md`、`NN` = 2 桁の Roadmap 行番号。
具体的には、マイルストーン #03 のレコードは `specs/03-progress.md` である。

すべての制約を満たす理由:

- **ディスク上にあり、コンパクション耐久性あり (Invariant 2 / R-01)。**
  `specs/` 内のファイルはファイルシステム上のファイルであり、
  コンパクションはそれに触れない。サブディレクトリの `CLAUDE.md`
  (要約されてしまう) でもコンテキストのみでもない。
- **決定論的で、ファイルシステム検索不要 (R-01)。** パスは
  読者がすでに Roadmap から持っている行番号の純粋関数である。
  再開者は Roadmap 行 #03 を読み、`specs/03-progress.md` を開く
  ── `ls`、`git log`、スキャンは不要。キーは *安定した行番号* であり、
  ADR-014 はそれが変更または再利用されないことを保証する。
- **Roadmap の外側 (ADR-014 / R-02)。** テーブルには何も追加されない。
  グリフは唯一の実装状態トークンであり続ける。レコードはマイルストーンの
  Spec (`specs/NN-slug.md`) と同じ場所に置かれる兄弟ファイルであり、
  2 つのマイルストーン成果物が一緒に並ぶ。
- **ディテクターと一貫 (#04 の相互作用)。** `specs/` はアクティブな
  ディテクターにとってすでに完全にスコープされたツリーである。
  `specs/NN-progress.md` は ADR-014 の予約カーブアウトと Class-A
  プレースホルダースキップがすでに推論している
  `specs/<NN>-<slug>.md` の形状にマッチする。
  **ディスク上に存在する** 実際の数字の `specs/03-progress.md` は
  正常に解決されて dangling-reference の検出結果を生まない。
  レコードは境界時にのみ作成されるため (決定 2)、
  参照される前にディスク上に実体化し、
  「参照されているが存在しない」ウィンドウは生じない。
  下流タスク (後述) が `implementer` に実際のフィクスチャを使って
  ディテクター互換性を確認するよう求める。これは ADR-015 の
  下流タスク規律を踏襲している。

レコードは **.gitignore されず、git-tracked である**。
根拠: US-002 の耐久性要件はどちらでも満たせるが、
tracked なファイルは (a) 同じフォークの複数オペレーター間で
共有可能であり ── マイルストーン単位の状態はプロジェクト知識であり、
1 人の開発者のスクラッチパッドではない ── そして (b) 誤って削除された
場合に git 履歴から復元可能である。`.gitignore` されたファイルは
別のマシンで同じ `◐` マイルストーンを再開するチームメートには
見えなくなり、Spec が Non-goals に記述するリポジトリ単位
(開発者単位ではない) のスコープを損なう。

**スキーマ (最小限、CI ではなく規約で強制 ── Spec の
対象外リストは存在/鮮度 CI チェックを禁じている):** YAML
フロントマターに続く短い本文。

```
---
roadmap_row: 3
milestone: "Cross-session milestone progress persistence"
status_glyph: "◐"            # MUST mirror the Roadmap glyph; mismatch ⇒ stale
workflow_step: 4             # 1–9 per ## Development Workflow; current step
last_updated: 2026-05-16     # YYYY-MM-DD, date the record was last written
head_sha: 7cee30f            # git HEAD short SHA at write time (staleness pin)
spec_exists: true            # mirrors specs/NN-slug.md presence (US-001 (c))
adr_links: [".claude/meta/adr/016-cross-session-progress-persistence.md"]
---

## Done
- Step 2 (Spec) — specs/03-...md authored
- Step 4 (Architecture) — ADR-016 written

## Next concrete action
[the single next action a resumer takes]

## Notes / why work stopped
[free text; e.g. "compaction boundary at step 4"]
```

`workflow_step` は `## Development Workflow` の手順の整数
(1 イシュー分析 … 9 コミット) であり、再開者は既知の
9 ステップパイプラインに直接マッピングできる (US-001 (a))。
本文セクションの形状は意図的に `/save-session` の
「What WORKED / Next Step」と同じ語彙にして、
一方を知るオペレーターがもう一方をゼロの新しいメンタルモデルで
読めるようにしている (US-004 / R-05)。正確なフィールドセットは
`implementer` に委ねる。本 ADR は *必須シグナル*
(行キー、グリフミラー、ステップ、タイムスタンプ、SHA、
spec-exists) を固定するのであり、最終的な bash/YAML 形式は固定しない
── ADR-015 が採用した中立セクション規律と同じである。

### 2. トリガーモデル — 境界トリガー (オプション b)

レコードは `◐` マイルストーン中に **セッションまたはコンパクション境界が
発生した場合にのみ書かれ**、☐→◐ 遷移時 (オプション a) でも
明示的なオペレーターコマンド時 (オプション c) でもない。

これは Spec の製品優先の選択であり、主題存在性ルール (ADR-015) が
それを *確認* する (上書きするのではなく)。進捗レコードの主題 ──
「*将来の* コンテキストが回復しなければならない進行中の状態」 ──
は **境界が現在のコンテキストを次のコンテキストから切り離そうとする
瞬間まで存在しない**。1 回の中断なしのセッションで出荷されるマイルストーンは
その主題を持たない: 手渡しすべき将来のコンテキストが存在しないため、
オプション a (常に ◐ で作成する) はその主題がまだ存在しないレコードを
製造することになり、Spec R-04 / US-003 が S-effort の散文行 (#16–#21)
に対して禁じる手間を正確に課すことになる。オプション c
(オペレーターコマンド `/save-session` 等) はエージェントの場合に
under-trigger する: コンパクション境界をまたいでいるエージェントは、
人間がコマンドを事前に実行していることに依存できない
(US-002 のアクターは「コンパクション境界をまたぐあらゆるエージェント」)。
境界トリガーは、その起動条件が主題が存在してくる瞬間と
一致する唯一のオプションである ── ADR-015 が主題の存在によって
always-on と default-off を置いたのと同じ論理である。

**書き込みオーナーシップ (ADR-014 のプロデューサー所有インデックスモデルを
踏襲したエージェント契約用語):**

- `product-manager` または `implementer` が、マイルストーンが `◐` の間に
  最初のセッション/コンパクション境界に遭遇した時点でレコードを
  **作成する** (Spec Key-interaction 2)。境界に当たったとき
  作業を持っているエージェントが作成を担う。
- `implementer` は境界が予期されるときに、ワークフロー手順が完了するたびに
  レコードを **更新する** (Spec Key-interaction 3) ──
  毎手順無条件に更新するのではない (それは手順単位の手間を再導入することになる)。
- `orchestrator` は Analyze 手順の開始時に、Roadmap 行を読んだ直後、
  サブエージェントをディスパッチする前に、レコードを **読む**。
  マイルストーンが `◐` でレコードが存在しない場合は
  git-log 再導出にフォールバックしてその旨を明示する
  (Spec Key-interaction 1; US-002 AC-3 ──
  不在は明示的でなければならず、暗黙に想定してはならない)。
  `orchestrator` は書かない。ADR-014 で Roadmap 行を決して書かないのと
  まったく同じである。

これにより、プロデューサー/リーダーの分割は ADR-014 と形状が同一になる:
作業を行うエージェントが書き込みを所有し、`orchestrator` は読むだけ。

### 3. 陳腐化認識

再開者はレコードを盲目的に信頼することなく、
現在のレコードと陳腐化したレコードを区別しなければならない。
3 つの具体的で安価な相互チェック (順序順):

1. **グリフミラー。** レコードの `status_glyph` は Roadmap 行の
   グリフと一致しなければならない。Roadmap が ☑ または ✗ を示しているが
   レコードが ◐ を示している場合 (またはレコードが存在する場合)、
   レコードは **定義上陳腐化している** ──
   マイルストーンはレコードが廃棄されないまま進んだ。
   Roadmap グリフが権威的である (ADR-014)。レコードはそれを上書きしない。
2. **`head_sha` ピン。** レコードは書き込み時の `git HEAD` ショート SHA を
   記録する。再開者はそれを現在の `HEAD` と比較する:
   一致 ⇒ スナップショット以降にコミットなし (最高鮮度);
   乖離 ⇒ レコードは N コミット前のものであり
   `Done`/`Next` が遅れている可能性がある ── 再開者は
   *進捗の下限* として読み、`git log <head_sha>..HEAD` で差分を照合する。
   これは有界で安価であり、全履歴の再導出ではない。
3. **`last_updated` 日付。** 人間向けの粗い鮮度シグナルであり、
   SHA ピンへの副次的指標
   (日付は「作業なし」と「作業あり、レコード未更新」を区別できないが、
   SHA は区別できる)。

再開者が適用する契約: **Roadmap グリフが *実装状態* で勝る。
レコードは *進行中の詳細* (どのステップ、次に何をするか) のみに権威があり、
そのグリフが Roadmap を映しており、かつ SHA が HEAD の祖先である間のみ。**
陳腐化したレコードはレコードなしより悪くはない (US-002 のフレーミング:
「ゼロ情報よりも古くない」) ── SHA ピンが陳腐化を *見えない* ものではなく
*測定可能な* ものにするからである。

### 4. ◐ → ☑ のリタイアメント

マイルストーンが `◐ in-progress` → `☑ done` に遷移するとき、
Roadmap グリフをフリップするエージェントが完了を記録する **同じ変更の中で
`specs/NN-progress.md` を削除する**。アーカイブではなく削除:

- レコードの存在意義は「このマイルストーンは ◐ である。その進行中の状態は何か?」
  に答えることである。☑ のマイルストーンには進行中の状態がない。
  残されたレコードは将来の読者を誤導するだけである
  (Spec R-03: 「マイルストーン完了後に更新されないレコードは
  将来のオペレーターを誤導する」)。削除することで誤導する成果物を
  完全に取り除く。
- これは **ADR-014 の「ドロップした行は残す / 履歴は書き換えない」という
  哲学と一致している**。正しく読めば: ADR-014 は *インデックス*
  (Roadmap 行とそのグリフ履歴) の書き換えを防ぐ ──
  ☑/✗ の行は永遠に残る。進捗レコードは *インデックスではなく*、
  インデックスの外側に明示的に置かれた一時的な作業状態である (決定 1)。
  削除しても履歴を書き換えない ── 完了は Roadmap グリフと
  マイルストーンの Spec/ADR (すべて永続する) に記録されている。
  もしフォレンジックな復元が必要になった場合は git 履歴にファイルが残る。
- ◐ → ✗ (ドロップ) の場合: 同じルール ── グリフフリップ時に削除する。
  ドロップされたマイルストーンには保持する価値のある再開可能な
  進行中の状態がない。✗ の行と Spec/ADR が ADR-014 に従い
  「なぜドロップしたか」を記録する。

リタイアメントは **グリフフリップに縛られたエージェントアクション** であり、
個別の CI ジョブでも (Spec の対象外リストがこれを禁じる)、
忘れられかねない手動オペレーターの作業でもない。削除をステータスフリップと
同じ変更に縛ることで、読者の視点からは「レコードが廃棄された」と
「行が done とマークされた」が原子的になる。グリフミラー (陳腐化チェック 1) が
縛りが破られた場合のバックストップとなる ──
☑ の行に残存するレコードは *検出可能に* 陳腐化している。

### 5. `/save-session` ↔ `/resume-session` および ECC:SUMMARY との関係

マイルストーン単位のレコードはグローバルなセッションコマンドと
**並行して動作し**、それを拡張したり包んだりしない。境界は
機構ではなく **スコープ** に基づいて引かれる:

| 次元 | `/save-session` ↔ `/resume-session` | `specs/NN-progress.md` |
|---|---|---|
| スコープ | 1 回の *作業セッション* (オペレーターが行ったすべて) | 1 つの *マイルストーン* のワークフロー状態 |
| 場所 | ユーザーホーム `~/.claude/session-data/` (リポジトリ外) | リポジトリローカル `specs/` (リポジトリ内、git-tracked) |
| 粒度 | セッション単位、プロジェクト非依存 | Roadmap 行単位、プロジェクト固有 |
| ライフタイム | オペレーター管理、ユーザーホームに残る | ◐ ウィンドウに紐付く、☑ で削除 |
| コンパクション耐久性 | 明示的な `/resume-session` でのみ生き残る | 暗黙的に生き残る (ディスク上、決定論的パス) |
| トリガー | オペレーターコマンド | ◐ 中のセッション/コンパクション境界 |

これらは **組み合わせ可能で競合しない**: オペレーターは
広範なセッション継続性のために `/save-session` を実行しながら、
「マイルストーン #NN はどこか」という狭い問いに `specs/NN-progress.md`
を使うことができる ──
US-004 の「オペレーターはどちらを独立して使うこともできる。
2 つの機構は組み合わせ可能で競合しない」という要件。
意図的な設計選択は **スコープによる非重複**: グローバルコマンドは
「このセッションで何をしていたか」に答え、マイルストーンレコードは
「この特定のマイルストーンの進行中の状態は何か」に答える。
再開者は Roadmap → マイルストーンレコードでマイルストーンスコープの状態を読む。
`/resume-session` はホールセッション状態のためのオペレーターツールであり続ける。
どちらも他方の使用を必要としない。

**ECC:SUMMARY について**: リポジトリ grep により本テンプレートに
リポジトリ内 `ECC:SUMMARY` ブロックや規約が存在しないことが確認されている。
したがってリポジトリ内で拡張または整合させるものはなく、
既存のセッションサマリーサーフェスはユーザーホームの `save-session`
ファイル形式だけである。`specs/NN-progress.md` の本文セクション形状
(Done / Next concrete action / Notes) は *意図的に*
`save-session` のセクション語彙を踏襲しており、
一方を知るオペレーターがもう一方をゼロの新しいメンタルモデルで
読めるようにしている ── 新しい共有ブロック形式ではなく、
親しみある形状による組み合わせ。既存の機構が
カバーしないギャップ (マイルストーン単位、リポジトリローカル、
明示的な resume コマンドなしのコンパクション耐久性) に
正確にスコープして、再利用より再発明しないという原則
(開発ワークフロー手順 3) を尊重している。

本 ADR は決定とエージェント契約/ダウンストリームへの示唆を記録する。
進捗ファイルの作成、スクリプトの作成、エージェントプロンプトの変更は
**行わない** ── 実装は将来のセッションに委ねられており、
トレーサビリティのために帰結 → 中立に列挙する。
これは ADR-014 と ADR-015 が行うのとまったく同じである。

## 帰結

### ポジティブ

- 再開するオペレーターやエージェントは「どのワークフロー手順が現在か、
  ディスク上に何が存在するか、次のアクションは何か」を
  Roadmap 行番号をキーとした **1 回の決定論的なファイル読み込み** で
  答えられる ── `git log` なし、`specs/` スキャンなし、
  ワークフローの再トレースなし
  (US-001、Spec メトリック: 再オリエンテーション < 60s、
  再導出トークンほぼゼロ)。
- コンパクション耐久性は手続き的ではなく構造的: レコードは
  安定した行番号の純粋関数であるパスに置かれたディスク上のファイルであり、
  再開コンテキストはオペレーターアクションなしに回復できる (US-002)。
  `/save-session` は明示的な `/resume-session` が必要であるのに対し。
- 単一セッションのマイルストーンにはゼロの手間 (US-003):
  境界トリガーは 1 セッションで ☐→☑ まで出荷されるマイルストーンが
  レコードを作成しないことを意味し、不在に対して CI が失敗することもない
  (Spec がこの CI チェックを禁じている)。S-effort の散文行 (#16–#21)
  は進捗追跡の負担を一切払わない。
- ADR-014 インデックスのみ契約は維持される: Roadmap グリフが
  唯一の実装状態トークンであり続け、進捗詳細は兄弟ファイルに置かれ、
  テーブルには入らない。
- 陳腐化は *測定可能* (グリフミラー + `head_sha` ピン) であり、
  陳腐化したレコードは「進捗の下限、有界なデルタを照合する」に
  優雅にデグレードし、暗黙に誤導することがない ──
  Spec の R-03 緩和要件が具体的に満たされる。
- トリガーモデルは ADR-015 が確立した *同じ* 主題存在性ルールによって
  決定されるため、テンプレートは新しいアドホックなポスチャー概念を得ない ──
  ルールは CI ポスチャーと進捗レコードのトリガーの両方を
  監査可能かつ一貫した形で統治する。
- スコープパーティションによって既存のセッション機構と組み合わせられるため、
  オペレーターは 1 つのメンタルモデルを持ち続ける (US-004 / R-05)。
  並列規約は発明されない (開発ワークフロー手順 3 の再利用原則)。

### ネガティブ

- **更新規律はエージェントプロンプトのコンプライアンスに依存する。**
  ADR-014 のインデックス↔実態のドリフトと同様に、
  境界が実際に書き込みをトリガーすることを強制するものはない
  (Spec が存在/鮮度 CI チェックを禁じている)。書き込みのない境界は
  次の再開者にレコードなしの状態を残す ──
  現在のベースラインである git-log 再導出にデグレードし、
  退行ではないが、そのマイルストーンの利益は未実現となる。
  緩和策は明示的な不在フォールバック
  (orchestrator が「レコードなし、再導出中」と明示する) と
  書かれたレコードの陳腐化を SHA ピンで測定可能にすることである。
- **2 つのセッション継続性サーフェスが残る**
  (グローバル `/save-session`、マイルストーン単位レコード)。
  スコープテーブルが境界を明示するが、メンテナーは両方の概念を
  保持しなければならない。リスクはオペレーターが `/save-session` を使って
  それが持たないマイルストーンステップ粒度を期待したり、
  その逆をしたりすることである。意図的に非重複なスコープと
  共有の本文セクション語彙によって緩和される。
- **レコードパスが ADR-014 の行番号キーに結合する。**
  ADR-014 の行番号規約が変更された場合 (「再利用しない」それ自体が
  ADR-014 の不変条件であるため変更されない)、`specs/NN-progress.md`
  のキーも変更される。これは ADR-015 の予約カーブアウトがすでに
  引き受けた同じ同じイミュータブルな番号をキーとした受け入れ可能な結合である。
- **☑ での削除により進行中のナラティブが失われる。**
  完了したマイルストーンがどのように進んだかに興味のある読者は
  (削除された) レコードを読めない。意図的に受け入れる:
  そのナラティブはインデックスコンテンツではなく、Spec は
  レコードをアクティブな ◐ 行にのみスコープし、
  git 履歴がフォレンジックな復元のためにファイルを保持しており、
  残されたレコードは積極的に誤導する (R-03) ──
  保持するコストが失うコストを超える。

### 中立

- これは ADR-014 / ADR-015 の型の **CLAUDE.md プラスエージェントプロンプト**
  変更である: エージェントの追加も削除もない。既存のエージェント
  (`product-manager`、`implementer`、`orchestrator`) がそれぞれ 1 つの
  責任を得る。エージェント数は変わらない。
- Roadmap 行 #03 の `Design source` セルは本 ADR への `adr:` リンクを得る
  (ADR-014 の書き込みオーナーシップに従い本変更が実施: `architect` が
  `adr:` リンクを追加する)。他の行には触れない。Roadmap フォーマットの変更なし。
- 下流の `implementer` タスク (トレーサビリティのために記録。
  本 ADR では実施しない ── 実装は将来のセッション):
  - `.claude/templates/` — `progress-template.md` ペーストイン
    スケルトン (YAML フロントマター + Done / Next / Notes 本文)
    を決定 1 のスキーマにマッチする形で追加する。
    `.ja.md` 対訳は `technical-writer` のタスクであり、本タスクではない。
  - `.claude/agents/product-manager.md` — 追加:
    「マイルストーンが `◐` の間に最初のセッション/コンパクション境界で、
    不在の場合はテンプレートから `specs/NN-progress.md` を作成する。」
  - `.claude/agents/implementer.md` — 追加:
    「マイルストーン途中で境界が予期されるとき、
    `specs/NN-progress.md` を更新する
    (`workflow_step`、`head_sha`、`last_updated`、Done/Next)。
    ◐→☑ (または ◐→✗) のグリフフリップ時に、
    同じ変更の中で `specs/NN-progress.md` を削除する。」
  - `.claude/agents/orchestrator.md` — Analyze 手順:
    「Roadmap 行を読んだ後、マイルストーンが `◐` であれば
    `specs/NN-progress.md` を読む。不在の場合は、
    レコードが存在しないことを明示して git から再導出する。
    レコードを決して書かない。」
  - `.claude/CLAUDE.md` `## Development Workflow` ──
    `◐` マイルストーンが境界をまたぐとき
    `specs/NN-progress.md` に進行中の状態を永続化する
    (ADR-016 による)、`/save-session` と組み合わせ可能、
    と記す 1 文を追加する。`claude-md-authoring` Skill のもとで
    作成する (構造的な CLAUDE.md 変更であるため)。
    認定されたラインバジェット相互作用は影響を受けない (1 文であり、
    Roadmap ではない)。
  - `implementer` がディテクター互換性を確認する:
    実際の `specs/NN-progress.md` フィクスチャを
    `test-check-dangling-refs.sh` スイートに追加し、
    ディスク上に存在する進捗ファイルが dangling-reference 検出結果を
    生まないこと、および *参照されているが不在* の進捗パスが
    正しく処理されることを証明する (境界トリガーの
    参照前作成の順序付けによりこれは発生しないはずだが、
    テストが不変条件をピンする)。ディテクターコードの変更は
    予期しない ── `specs/` はすでに完全にスコープされており、
    `specs/03-progress.md` は存在する場合に正常に解決する実際の数字のパスである。
  - 本 ADR の日本語版
    (`016-cross-session-progress-persistence.ja.md`) は
    `technical-writer` が所有する (本タスクではない)。
- CI チェックは導入も示唆もされない。Spec の対象外リストが
  進捗の存在や鮮度の CI チェックを禁じている。本 ADR はそれを尊重する ──
  陳腐化はワークフローではなく、再開時に読まれるレコード内の
  グリフミラー + SHA ピンによって処理される。

## 反対提案

深刻な反対立場は **代替案 A ── リポジトリローカルレコードを追加しない。
既存の `/save-session` ↔ `/resume-session` 機構に完全に依存する** である。
ADR-012 / ADR-014 / ADR-015 の先例 ── strawman ではなく却下された
代替案を真剣に扱う ── に従いここに記録する。論点:

1. 機構はすでに存在し、文書化されており、オペレーターが知っている。
   再利用より再発明しない (開発ワークフロー手順 3) は、
   新しいものよりも実証された機構を組み合わせることを明示的に優先する。
   2 番目のセッション継続性成果物を追加することは、
   本 ADR が自らに有利に引用するまさにその原則に違反する可能性がある。
2. `save-session` ファイル形式はすでに
   「What WORKED / Next Step / Decisions Made」セクションを持ち、
   進捗レコードが必要とするほとんどをカバーする。
   マイルストーンスコープのバリアントは、新しいファイルタイプではなく
   既存のファイルの *規約* として成り立てる。
3. 2 つの機構は Spec 自身が指摘する R-05 のリスクである
   (「`/save-session` とマイルストーン進捗レコードのどちらを使うべきか?」)。
   1 つの機構はそのリスクを構造上排除する。

**反対提案が採用されなかった理由:**

- 決定的な失敗は親しみやすさではなく、**Spec の受け入れ基準における
  場所の決定論性** である。US-001 は再開者がマイルストーン #NN の状態を
  *検索なしに* 見つけることを要求する ── 行番号の純粋関数として。
  `~/.claude/session-data/` のファイルは日付とショート ID が付いており、
  プロジェクト非依存で、Roadmap 行にキー付けされていない。
  「行 #03」から「#03 の状態を持つファイル」への決定論的パスが存在しない。
  再利用は再利用された機構が要件を *満たせる* 場合のみ価値がある。
  この機構は構造上、行キー付きの決定論的アドレスを提供できない。
- **ゼロオペレーターアクションのコンパクション耐久性 (US-002)** が
  満たされない: ユーザーホームのセッションファイルは
  明示的な `/resume-session` でのみ回復される。US-002 のアクターは
  「コンパクション境界をまたぐあらゆるエージェント」であり、
  コマンドを呼び出すオペレーターがいない。
- **リポジトリ単位の共有可能性**
  (Spec の Non-goals はリポジトリ単位にスコープし、
  開発者単位ではない / クロスリポジトリではない):
  ユーザーホームファイルは再開する *開発者の* ものであり、
  *フォークの* ものではない。別のマシンで同じ `◐` マイルストーンを
  引き継ぐチームメートはそれを見られない。
- 再利用は *可能なレベル* で尊重される: 新しい成果物の
  本文セクション語彙は意図的に `save-session` のものを踏襲し、
  2 つはクリーンなスコープパーティションで組み合わせられる (決定 5)。
  原則はユーザーホームの行キー付けできない機構に
  それがその表現できないジョブを強制することではなく、
  形状による組み合わせで満たされる。

**この反対提案を再評価するトリガー条件:**

- セッション機構がリポジトリローカルで行アドレス可能な
  ストレージモード (例えば将来の `/save-session --milestone NN` が
  決定論的パスでリポジトリに書き込む) を得た場合、
  決定論性や共有可能性を失わずに新しい機構をそれに折り込める。
- テンプレートのオーディエンスが、リポジトリ単位の共有可能性が
  重要でない単一開発者のフォークにシフトし、3 つの却下根拠の
  1 つを弱める場合 (他の 2 つ ── 決定論性、ゼロアクション耐久性 ──
  は依然として存在する)。

反対提案は ADR-012 / ADR-014 / ADR-015 の規約に従い、
決定の最も深刻な異議の歴史的記録として本 ADR に残る。
