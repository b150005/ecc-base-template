# ADR-015: Dangling-Reference Detector — always-on、subject-matter-keyed CI ポスチャー

## ステータス

Accepted — 2026-05-16

## 背景

本テンプレートは設計成果物 ── `CLAUDE.md`、ADR、Spec、
エージェントファイル ── を密に相互参照している。ADR は
「ADR-007 参照」「ADR-012 に従い」のように兄弟 ADR を
番号で引用し、`CLAUDE.md` はスクリプトパスや Skill ディレクトリを
パスで指定し、Spec は Roadmap 行への逆参照として `spec:` と `adr:` リンクを
持ち、エージェントファイルは ADR 番号とパスをインラインで参照する。
これらの参照は一切検証されていない。リネーム、移動、削除、
または数字の転置が生じても、ダングリング参照が静かに生まれ、
その文書を次に読むエージェントを誤導する ──
orchestrator は `CLAUDE.md` を通じて設計成果物を解決し、
`implementer` は Roadmap 行を通じて Spec を解決し、
`architect` は新しい ADR を作成する前に一貫性のために
先行 ADR を読む。これらの解決パスのいずれも、解決できない
ポインターを追うためにコンテキスト予算を消費する。

既存の `check-skill-invariants.sh` Check 4 は
**`SKILL.md` ファイル内に限り** 相対パスリンクを検証する。
任意のファイルの `ADR-NNN` テキスト参照も、`CLAUDE.md`、ADR、
Spec における `.claude/` ルートのパス言及も検証しない。
これがマイルストーン #04 が埋めるギャップである。
Spec `specs/04-dangling-reference-detector.md` が権威的なスコープであり、
本 ADR は Spec が `architect` に委ねた **構造的** 決定を記録する:
always-on と default-off の CI ポスチャー、`check-skill-invariants.sh`
に対するスコープ境界、ADR-014 予約ルール免除のハード制約、
そしてマイルストーン #05/#06 によるディテクターパターン再利用。

非自明な決定は **CI ポスチャー** である。本テンプレートには
2 つの確立した CI 規約があり、表面上は対立している:

- `skill-invariants.yml` (ADR-007) — **always-on**、パス指定、
  関連パスに触れるすべての push/PR で実行、設定ステップなし。
- `workaround-check.yml` (ADR-006) — **default-off、single-switch**、
  すべてのジョブが `.github/workaround-tracker.yml` を読み込み、
  `enabled: true` になるまで短絡する。

レビュアーは合理的にこう問うことができる: このテンプレートの
設定駆動 CI はすべて default-off である (ADR-006 は「エルゴノミクスと
規約」を理由に default-on の代替案を明示的に却下している)。
なぜこのディテクターは異なるのか? この反対立場は
後述の代替案セクションと「反対提案」セクションで
真剣に扱う。ADR-012 / ADR-014 の先例に従い、却下された選択肢を
真のプロとともに選択されなかった具体的な理由と
ともに監査可能な形で記録する。

これは **新しい構造的決定** ── 新しい CI 機構、そのポスチャー、
既存チェックに対するスコープ境界、#05/#06 が継承するポスチャー
ルール ── であるため、ADR-014 が述べた ECC 先例
(「新しい ADR 番号は新しい構造的決定のために予約する。
帰結の明確化は amendment に折り込む」) に従い、
ADR-014 の amendment ではなく新しい ADR (015) が必要である。

## 決定

dangling-reference detector は `workaround-check.yml` のような
default-off ではなく、`skill-invariants.yml` をモデルとした
**always-on** である。設定変数や設定ファイルを必要とせず、
スキャン対象の文書ツリーおよびスクリプト/ワークフロー自体への
パス指定のもとで `main` へのすべての push と pull request で実行する。

ポスチャーはここに記述する単一の明示的なルールで決定する。
#05 と #06 が再議論することなく継承できるようにするためである:

> **Subject-matter-presence rule (主題存在性ルール)。**
> テンプレート CI チェックは、その主題が *すべての* フォークに
> 初日から存在する構造的契約である場合は **always-on** である。
> その主題が新鮮なフォークにおいて機能を有効化するまで
> *存在しないか無関係* である場合は **default-off / single-switch** である。

ルールを適用する: `workaround-check` と `docs-freshness` は
default-off である ── その主題 (upstream-workaround レジストリ、
Anthropic のドキュメントに対するドリフト) は、採用者が
ワークアラウンドの追跡を開始するか freshness ジョブを
接続するまで、新鮮なフォークには存在しないか無関係である。
`skill-invariants` は always-on である ── その主題
(Skill 構造的契約) は `.claude/skills/` を保持するすべての
フォークに存在する。dangling-reference 検出の主題 ──
テンプレート自身の `CLAUDE.md`/ADR/Spec/エージェント
相互参照 ── は初日からすべてのフォークに存在する
(テンプレート自身の構造的ファブリックである)。よって、
`workaround-check` カテゴリではなく `skill-invariants` カテゴリに
属する。テンプレートは自身の最初の顧客であり、
opt-in ステップなしに出荷時点でこのチェックを通過しなければならない。

さらに 3 つの構造的決定:

1. **`check-skill-invariants.sh` Check 4 に対するスコープ境界。**
   新しいディテクターは `CLAUDE.md`、`.claude/meta/adr/*`、`specs/*`、
   `.claude/agents/*` を所有する。Check 4 は **`SKILL.md` ファイル内**
   の相対パスリンクの唯一の所有者を保持する。ディテクターは
   `SKILL.md` の相対リンクをスキャンせず、Check 4 は `ADR-NNN`
   テキスト参照や `CLAUDE.md`/ADR/Spec パス言及をスキャンしない。
   2 つのチェックはファイルタイプ・リンクタイプの分割によって MECE であり、
   リンクはちょうど 1 つのチェックによって検証される。この分離は
   実装詳細ではなく構造的選択である: 2 つのチェックが共に失敗する
   単一のリンクは 1 つの欠陥に対して 2 つの CI 失敗と
   2 人のオーナーを生み、それがこの境界が防止しようとする
   ドリフトモードである。

2. **ADR-014 予約ルール免除はディテクターのハード制約である。**
   ADR-014 の Spec 予約ルール (および 2026-05-16 amendment) は、
   ファイルがまだディスク上に存在しなくても Roadmap の
   `spec: specs/NN-slug.md` リンクを設計上有効にする ──
   リンクはインデックスのプロパティであり、ファイルはマイルストーンが
   着手されたときに実体化する。ディテクターはそのようなリンクを
   **失敗させてはならない**。これはディテクターを弱めない:
   免除は正確な決定論的パターン (`specs/` プレフィックス、
   2 桁の `NN`、ハイフン、スラッグ、`.md` サフィックス) に
   キーイングされており、**Roadmap の `Design source` 列にある
   参照にのみ適用される** ── どこにあっても `specs/` 言及すべてに
   ではない。散文中に書かれた本当にダングリングな Spec パス、
   または予約形式ではない `specs/` 参照は、依然としてキャッチされる。
   免除は ADR-014 が設計上有効と宣言した集合に正確に絞り込み、
   それ以上に広げない。これにより偽陽性を除去しつつ穴を開けない。

3. **#04 がディテクターパターンを確立し、#05 と #06 が再利用する。**
   #04 を先に閉じることが最高レバレッジの順序 (Spec のフレーミング)
   である ── まさに再利用可能な形 ── `set -euo pipefail` スクリプトを
   `.claude/meta/scripts/` 配下に、パス指定の always-on ワークフローを
   `.github/workflows/` 配下に、`pass`/`warn`/`fail_check` アキュムレーター、
   行レベルの `<!-- ref-allow: -->` エスケープハッチ ── を構築し、
   #05 (Roadmap ドリフト CI) と #06 (bilingual parity CI) が
   再利用またはミラーするからである。#05/#06 を default-off として
   扱うことは subject-matter-presence ルールと矛盾する
   (Roadmap ドリフトと EN/JA パリティも always-present な
   構造的契約である)。よって、ルールはそれらのポスチャーも決定する。

本 ADR は決定とエージェント契約/ダウンストリームへの示唆を記録する。
スクリプトやワークフロー自体は本 ADR では **書かない**。
それらはダウンストリームの `implementer` タスクであり、
トレーサビリティのために帰結 → 中立に列挙する
(ADR-014 が従う規約と同じ)。

## 帰結

### ポジティブ

- テンプレート自身の構造的ファブリックが、opt-in なしに
  すべての push/PR で検証される。テンプレートは構造上グリーンで
  出荷され、フォークした採用者は設定ステップなしに
  既知の健全な相互参照ベースラインを継承する。
- 原則に基づき記述されたポスチャールール (subject-matter-presence) が、
  アドホックな「これも他のように default-off か?」という判断を
  置き換える。#05 と #06 は再議論することなく決定済みのポスチャーを
  継承する。ルールは監査可能で反証可能である。
- Check 4 に対するスコープ境界によりオーナーシップが明確になる:
  すべての相互参照はちょうど 1 つのチェックで検証されるため、
  単一の欠陥が 2 つの失敗や 2 人のオーナーを生むことがない。
- 予約ルール免除により ADR-014 の設計上有効な予約済みリンクを
  グリーンに保ちつつ、本当にダングリングな Spec パスを
  キャッチし続ける ── ディテクターと ADR-014 は
  ディテクターが ADR-014 を緩和させることなく
  相互に一貫したままである。
- インフラストラクチャレバレッジ: #04 が #05 と #06 が
  ミラーする再利用可能なディテクター形を構築する。
  これがギャップ分析が最高レバレッジと順位付けした理由である。
  1 つのパターン、3 つのマイルストーン。

### ネガティブ

- always-on であることは、偽陽性がオプトインした
  サブセットだけでなくリポジトリ全体の CI をブロックすることを意味する。
  緩和策: 行レベルの `<!-- ref-allow: -->` エスケープハッチが
  チェックを無効にすることなく行ごとに先行参照を吸収する。
  スコープは既知の文書ツリーに限定され、すべてのファイルには及ばない。
  非対称性は意図的である ── 見逃されたダングリング参照は
  その文書を読むすべてのエージェントがすべてのセッションで
  コストを払い、偽陽性は 1 回の抑制コメントでコストを払う。
- ディテクターと `check-skill-invariants.sh` は
  2 つのスクリプトと 2 つのワークフローに分かれた
  概念的なドメイン (相互参照整合性) を共有するようになる。
  将来のメンテナーは、あるリンクをどちらのチェックが
  所有するかを知るためにファイルタイプ/リンクタイプの
  分割を知る必要がある。境界はここに文書化されており、
  両スクリプトのヘッダーコメントに再記述しなければならない
  (ダウンストリームタスク)。これにより分割がどちらの側からも
  発見可能になる。
- 免除はディテクターを ADR-014 の決定論的な `specs/NN-slug.md`
  パス形式に結合させる。ADR-014 の予約パスパターンが
  変更された場合、免除の正規表現も変更しなければならず、
  自動的に 2 つを相互チェックするものは何もない。
  この結合は Roadmap の `Design source` 列のみ
  (最も狭い可能なサーフェス) にキーイングされた
  既知のメンテナンスエッジとして記録する。
- ポスチャールールは、エージェントチームと人間の読者が
  保持しなければならない新しい概念である。
  1 文であるが #05/#06 と将来のテンプレート CI に
  とって重要である。誤用 (例: subject-matter-present なチェックを
  default-off で出荷する) はテンプレートを静かに弱める。

### 中立

- 新しいエージェントなし、削除されるエージェントもなし。
  これは文書化されたポスチャールールを加えた
  CI レイヤーの追加である。Spec は本マイルストーンで
  エージェントプロンプトの変更が不要と述べており ──
  ADR-014 の CLAUDE.md-plus-traceability 形式と一致する。
- エスケープハッチ構文 (`<!-- ref-allow: -->`) と
  ADR 番号のゼロパディング正規化 (`ADR-7` ≡ `ADR-007`) は
  Spec が `implementer` に割り当てる実装詳細である。
  本 ADR はその正確な形式を定めず、免除と Check-4 境界が
  選択された形式で守られることだけを定める。
- ダウンストリームの `implementer` タスク (トレーサビリティのために記録。
  本 ADR では実施しない):
  - `.claude/meta/scripts/check-dangling-refs.sh` —
    `check-skill-invariants.sh` の構造 (`set -euo pipefail`、
    `git rev-parse` によるルート解決、`pass`/`warn`/`fail_check`
    ヘルパー、`fail=0` アキュムレーター、`exit "$fail"`) に従って作成する。
    (a) Roadmap `Design source` 列にキーイングされた ADR-014 予約ルール免除と、
    (b) Check-4 スコープ境界を本 ADR へのワンライン
    ポインターとともに文書化する目立つヘッダーブロックを含める。
  - `.github/workflows/dangling-ref-check.yml` —
    `skill-invariants.yml` の構造に従って作成する:
    always-on、スキャン対象ツリーとスクリプト・ワークフロー自体への
    パス指定のもとで `main` への `on: push/pull_request`、
    単一 `check` ジョブ、`permissions: contents: read`、
    `timeout-minutes: 5`、ジョブ名 `dangling-ref-check`。
  - `.claude/meta/scripts/check-skill-invariants.sh` —
    Check-4 側からも分割が発見可能なよう、境界を命名する
    ワンライン ヘッダーコメントを追加する
    (「ADR/Spec/CLAUDE.md/エージェント相互参照は ADR-015 に従い
    check-dangling-refs.sh が所有する」)。
  - 本 ADR の日本語版
    (`015-dangling-reference-detector.ja.md`) は
    `technical-writer` が所有する (本タスクではない)。

## 反対提案

深刻な反対立場は **代替案 A ── このディテクターをテンプレートの
他のすべての設定駆動 CI (`workaround-check.yml`、`docs-freshness.yml`)
のように default-off / single-switch にする** である。
ADR-012 の先例 ── 稻草人としてではなく却下された代替案を
真剣に扱う ── に従い、ここに記録する。論点:

1. ADR-006 は default-off をテンプレート CI 規約として確立し、
   「エルゴノミクスと規約」を理由に default-on の代替案を
   明示的に却下した。一貫性には価値がある:
   「テンプレート CI はオプトイン」と内面化したフォーク
   メンテナーは always-on なジョブに驚く。
2. Always-on であることは、偽陽性がオプトインした
   サブセットだけでなくリポジトリ全体の CI をブロックすることを意味する。
   初日からノイジーなディテクターは CI サーフェス全体への
   信頼を損なう。
3. Single switch はこのテンプレートで既知の、
   よく理解された制御である。再利用には概念的コストがゼロである。

**反対提案が採用されなかった理由:**

- ADR-006 が確立した規約は「テンプレート CI はすべて
  default-off」ではない。「*主題が新鮮なフォークに存在しない*
  CI は default-off」である。ADR-006 の主題は
  新鮮なテンプレートでは空の upstream-workaround レジストリであり、
  ADR-007 の `docs-freshness` の主題は
  接続されるまで無関係な Anthropic ドキュメントに対するドリフトである。
  `skill-invariants` ── 同じく ADR-007、同じテンプレート ──
  はまったく逆の理由で **always-on** である:
  その主題 (Skill 構造的契約) はすべてのフォークに存在する。
  よってテンプレートはすでに *両方* のポスチャーを持っており、
  subject-matter-presence によって選択されている。Dangling 相互参照は
  初日からすべてのフォークに存在し、このチェックを
  明確に always-on カテゴリに置く。
  反対は規則の 1 つのインスタンス (default-off) を
  規則自体と誤解している。
- 出荷時保証は重要である: default-off チェックは
  「テンプレートが #04 出荷時点で自身の相互参照チェックを通過する」を
  opt-in ステップなしに真にすることができず、
  テンプレートが自身の最初の顧客であるという趣旨に反する。
- 偽陽性の影響範囲は設計上制限されている ──
  文書ツリーのスコープと行レベルの `<!-- ref-allow: -->` エスケープハッチ ──
  そしてコスト非対称性は反対側に走る:
  見逃されたダングリング参照はその文書を読むすべての
  エージェントがすべてのセッションで払い、
  偽陽性は 1 回の抑制コメントとして払う。

**この反対提案を再評価するトリガー条件:**

- テンプレートのオーディエンスが `.claude/` 設計成果物レイヤーを
  日常的に削除するフォークに向けてシフトし、主題が
  もはや普遍的に存在しなくなった時点。
  その場合、ルール自体がチェックを再分類する。
- エスケープハッチとスコープにもかかわらず、
  ディテクターが派生リポジトリで慢性的にノイジーであると
  判明した場合 (偽陽性率が実際にコスト非対称性を
  逆転させるほど高い)。
- ADR-014 の予約パスパターンが変更され、
  狭い免除が不可能になり、
  always-on 保証を実質的に弱める
  より粗い免除を強いられる場合。

反対提案は、ポスチャー決定の最も深刻な異議の
歴史的記録として本 ADR に残る。これは
ADR-012 / ADR-014 の規約に従う。

## Amendment — 2026-05-16: opt-in/default-off 設定は WARN カテゴリであり、FAIL カテゴリではない

**元の決定のステータス:** 変更なし (Accepted — 2026-05-16)。
本 amendment は always-on ポスチャーの帰結を明確化するものであり、
それを覆すものではない。ADR-014 の規約 (「帰結の明確化は
amendment に折り込む。新しい ADR 番号は新しい構造的決定のために予約する」)
に従い、これは新しい ADR ではなく amendment である。

### トリガー

#04 品質ゲートの中で、ディテクターはテンプレート自身の
成果物に対して 2 つの偽陽性クラスを生成し、
`implementer` は `CLAUDE.md` と `specs/04-dangling-reference-detector.md` に
散在した `<!-- ref-allow: -->` 抑制で解決した。これは
Spec の Leading メトリック (「出荷時点でゼロの `<!-- ref-allow: -->`
抑制 …」) に直接違反した。品質ゲートが進む前に
`architect` に構造的裁定を求めた。

- **Class A (ドキュメントパターントークン):** `specs/NN-slug.md`、
  `specs/NNN-slug.md`、数値スロットがリテラル `N` 文字である `ADR-NNN`。
  これらはテンプレート自身の予約ルール表記を説明するメタ構文的
  プレースホルダーであり、ディテクターが `check_path_refs_in_file` で
  すでにスキップする `*`/`?`/`<`/`>` グロブ/テンプレートトークンと
  カテゴリ的に同一である。Class A は **プレースホルダー認識における
  ディテクターのギャップ** であり、参照欠陥ではない。
  既存のサンプル/テンプレートトークンスキップを拡張することで
  解決する ── Class A に ADR の変更は不要。ここにはトレーサビリティのためのみに記録する。
- **Class B (opt-in / default-off、デフォルトで存在しない設定):**
  `.claude/learn/config.json` (Learning Mode、default-off) と
  `.claude/compliance.yml` (compliance Skill、opt-in。`.example` のみ出荷)
  への参照。両方ともディスク上に存在しないことが確認されており、
  *意図的に* 存在しない ── 参照行の散文自体が不在を有効な状態として
  文書化している。これが本 amendment が記録する構造的決定である。

### 決定 (追加的)

**意図的に不在な opt-in / default-off 採用者作成設定ファイルへの
参照** は、古くなった/壊れた/タイポの参照とは構造的に
異なるカテゴリであり、ディテクターはそれを **FAIL にしてはならない**。
subject-matter-presence ルールの拡張として述べる:

> **Reference-intent rule (参照意図ルール)。** ディテクターは
> 作者の意図が *意図的に存在する、実際には存在しない*
> (リネーム、移動、削除、またはタイポ ── このディテクターが
> 存在するために捕捉する失敗モード) である参照を FAIL とする。
> 意図が *意図的に不在、実際に不在* であり、不在が
> 参照に共存して有効な状態として文書化されている参照は
> **その失敗モードではない**。ADR-014 予約免除は
> 意図的に不在の作成時インスタンスである
> (Spec ファイルはマイルストーンが着手されたときに実体化する)。
> opt-in/default-off 設定は実行時作成インスタンスである
> (採用者は機能を有効化した場合のみ作成する)。
> 両方とも設計上有効な不在であり、ダングリング参照ではない。

ディテクターは不在の `.claude/` ルートの `.json`/`.yml`/`.yaml`
パスを **WARN とし、FAIL としない**。ただし **免除が参照に
共存する構造的コンテキストにキーイングされている場合のみ** ──
ちょうど予約免除が Roadmap `Design source` 列にキーイングされており、
すべての `specs/` 言及にではないのと同様に。
キーイングシグナルは: 参照行が固定の opt-in 語彙トークン
(`absent`、`default-off`、`opt-in`) を持つ **か**、
兄弟 `<path>.example` がディスク上に存在する場合。
共存する opt-in シグナルを **持たない**、かつ `.example` 兄弟を
**持たない** 不在の `.claude/` 設定パスは **FAIL のままである** ──
むき出しのタイポした設定パスはその隣に「不在でよい」コンテキストを
持たず、依然として ディテクターが捕捉しなければならない
*意図的に存在する、実際には存在しない* 失敗モードである。

この絞り込みは意図的であり、予約免除の絞り込みを
正確にミラーする: 免除は文書化された設計上有効な
集合と同じ広さであり **それ以上に広くない**。
「すべての不在の `.claude/*.json|yml` に対してチェックを弱める」ではない ──
共存する不在の設計シグナルを持つものだけに対してである。

### 却下された Class-B オプションでない理由

- **ディテクターの文書化された allowlist (却下)。**
  特定のパスの列挙は subject-matter-presence ルールが
  置き換えようとしたアドホック判断パターンである。
  サイレントに open に失敗する (忘れられた新しい opt-in ファイルは
  偽の CI レッドを生み出し、開発者を散在した抑制に
  戻すよう圧力をかける ── 本 amendment が閉じようとしている
  まさに Spec メトリック違反) し、機能ごとのメンテナンスを追加する。
  原則に基づくパターンキーのルールはどちらのコストもない。
- **抑制を受け入れ、Spec メトリックを amendment する (却下)。**
  ディテクターが誤分類することを補償するために、
  単一の常時参照、compaction 耐久の成果物である `CLAUDE.md` に
  永続的な `ref-allow` ノイズを焼き付ける。
  正しい成功メトリックを実装ショートカットに合わせるために
  弱めることは適合の誤った方向である。
  Spec メトリックは書かれた通りに正しい。ディテクターが間違っていた。

### この amendment の帰結

- **ポジティブ。** 出荷時点でテンプレート自身の `CLAUDE.md` と
  Spec に機能的な `ref-allow` 抑制がゼロ ──
  Spec の Leading メトリックが *逐語的に* 満たされ、
  Spec の amendment は不要。
  設定 vs. 設計成果物の区別がルールとしてエンコードされ、
  メンテナンスされたリストとしてではない。
  #05 と #06 は予約免除に加えて 3 番目の原則的な参照カテゴリを継承する。
- **ネガティブ。** ディテクターは 2 つの原則的な免除
  (予約ルール、opt-in 設定 WARN) とプレースホルダートークンスキップを
  持つようになる。将来のメンテナーは 3 つの免除概念を保持しなければならない。
  それぞれはパターンキーであり、スクリプトヘッダーに文書化されており
  (ダウンストリームの `implementer` タスク)、
  サーフェスは発見可能だが、ディテクターの概念的負荷が
  1 つのルール分増加した。緩和策: Reference-intent rule は
  1 つの反証可能な文であり、#05/#06 が再導出するのではなく
  継承するためにここに記述する。
- **中立。** 新しいエージェントなし、エージェントプロンプトの変更なし。
  ディテクターの動作変更 (Class A: プレースホルダースキップを
  リテラル `N` 数値スロットトークンに拡張。Class B: opt-in シグナルが
  ある不在の `.claude/` 設定に対して WARN-not-FAIL) は
  ダウンストリームの `implementer` タスクである。
  本 amendment は *分類とキーイング制約* を定め、
  bash の正確な形式を定めない。これは元の ADR の
  中立セクションと一致する。
- **Roadmap。** 行 #04 が早まって `☑ done` に
  フリップされた。品質ゲートが修正されたディテクターに対して
  通過するまで `◐ in-progress` に戻す必要がある。
  Roadmap の書き込みオーナーシップは ADR-014 に従い
  `product-manager` (ステータス) にある。
  本 amendment はフリップが早まったことを記録するだけである。
- 日本語版
  (`015-dangling-reference-detector.ja.md`) は本 amendment を
  含む必要がある。その翻訳は `technical-writer` タスクであり、
  本 amendment の対象ではない。
